## 3. smoke 前必须修的 P0 门禁漏洞

## P0-1：elbow `topology_pass=false`，总 `pass` 却为 true

包内 elbow G0 JSON：

```json
{
  "topology_pass": false,
  "pass": true
}
```

原因：URDF 下游多一个 `right_hand_flange_link`，MuJoCo 没有同名 body；但最终 `pass` 公式没有包含 `topology_pass`。

这个 flange 是可解释的物理空壳：

- fixed leaf；
- mass=`1e-9 kg`；
- inertia diagonal=`1e-11 kg·m²`；
- 对总质量和目标关节惯量的贡献可忽略。

正确处理不是直接忽略 `topology_pass=false`，而是增加显式的归一化拓扑规则：

1. 只允许忽略 fixed leaf；
2. 忽略项不得包含动态 joint 或动态子树；
3. 单 link mass `<=1e-8 kg`；
4. 惯性张量最大元素 `<=1e-9 kg·m²`；
5. 输出 `ignored_dummy_links`、质量和惯量上界；
6. 其余非豁免 link 集合必须完全一致；
7. 最终：

   ```text
   G0 pass = normalized_topology_pass
             AND FK/COM pass
             AND mass pass
             AND I_eff pass
   ```

如果不实现显式 dummy 规则，就应让 elbow G0 FAIL；不能保留当前矛盾状态。

## P0-2：G0 没有绑定到产生 trace 的实际模型

当前 G0 JSON 没有保存 URDF/XML/canonical/checker 的 SHA256；汇总器只读取任意 `g0.json` 中的 `pass`。

包内 `elbow_dryrun.json` 已经演示了风险：它把**新 G0**和**旧错误 URDF 产生的 trace**放在一起，仍得到 `validity_pass=true`。虽然这里只是工具干跑，但说明门禁可以被错误版本串包绕过。

修复要求：

### G0 JSON 必须保存

```text
joint
urdf_sha256
mj_native_xml_sha256
mj_matched_xml_sha256
canonical_npz_sha256
asset_equivalence_check_sha256
asset_generator_sha256
```

### 每次运行 manifest 必须保存

```text
runner_sha256
model_used_sha256
canonical_npz_sha256
config/runtime-parameter SHA256
joint/condition
```

### 汇总器必须校验

- G0 joint 与当前 joint 一致；
- trace manifest 的 model hash 与 G0 对应资产一致；
- canonical hash 一致；
- native/matched condition 与 XML hash 对应；
- 任一缺失或不一致，validity FAIL。

## P0-3：`--g0-file` 缺失时仍可能 validity PASS

当前代码：

```python
validity_pass = validity_core and (g0_pass is not False) and G6_PASS
```

当 G0 未提供时，`g0_pass=None`，`None is not False` 为 true。

改成：

```python
--g0-file 设为 required
validity_pass = validity_core and (g0_pass is True) and G6_PASS
```

G0 JSON 解析失败、字段缺失或 joint/hash 不一致，都必须 fail closed。

## P0-4：G6 缺字段、缺 hash 或重复数不足时仍可能 PASS

当前 `compare_repeats.py`：

- 未要求 `n_repeats == 3`；一次运行也可能因为没有 pairwise 差而 PASS；
- trace 字段缺失只记 `checked=false`，没有进入最终 FAIL；
- manifest hash 缺失或不一致只记录，不影响 PASS；
- Isaac 旧数据缺 runner/model/config hash，当前结果仍 PASS。

修复为：

```text
每个条件 n_repeats 必须严格等于 3
全部 REQUIRED_TRACE_FIELDS 必须存在且 shape 一致
全部 REQUIRED_HASH_FIELDS 必须存在且三次一致
任一缺失、shape 不同、hash 不同或数值超阈值 -> G6 FAIL
```

smoke 单次运行时 G6 应为 `NOT_EVALUATED`，不能伪造三重复 PASS。

## 6. N5-R2 后如何把控科学方向

### 分支 1：armature 假设 SUPPORTED

条件：有效性全过，elbow improvement ratio `>=10%`、绝对 MAE 至少降低 `1e-3 rad`，RMSE 或 t50 同向。

下一步：

1. 报告 armature 能解释 elbow 瞬态差异的一部分；
2. 进入 N6-R，但按 arms/waist/wrist 分组，不一次性改 17 关节后只看一个总结果；
3. 保留 native、单组 matched、累计 matched、全 17 matched 四层对照。

### 分支 2：有效实验下 armature NOT_SUPPORTED

这时才是真正的负结果，不是失败。不要直接做 17 关节 N6-R；先用 elbow 主实验和 hip negative control 做单因素筛查：

1. frictionloss；
2. physics dt/control hold；
3. 显式 effort PD 与隐式 drive 语义；
4. passive damping；
5. solver/integrator；
6. limit/constraint 放最后，因为当前阶跃未触限位。

每次只改变一个因素，继续使用同一 G0/G1–G6 证据链。

### 分支 3：hip 在参数一致时仍有较大剩余误差

hip 不用于证明 armature，但可作为“非 armature 基线”。优先检查：

- Isaac importer 后实际惯量/armature readback；
- implicit drive 离散时序；
- 2 ms/5 ms physics dt；
- frictionloss/passive damping。

不要仅凭一条 hip 曲线直接宣布某个引擎机制为根因。
