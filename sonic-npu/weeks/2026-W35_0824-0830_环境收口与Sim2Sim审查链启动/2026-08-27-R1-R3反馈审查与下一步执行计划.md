## 1. 先说结论

这两轮工作不是失败，也不需要推倒重来。R1 已经修掉了原来最主要的 default offset、history 初始化、共同初态和 actual target 问题；R2/R3 的汇总结果进一步表明：

- G0a policy contract：报告为 **PASS**；
- G0b simulator adapter：报告为 **PASS**；
- cycle 0 的 observation、action、q_des、target、q、dq 最大差约为 `4.03e-7`，远小于 `1e-4`，说明启动时的接口已经基本对齐；
- 从 cycle 1 开始，两个引擎的状态明显分叉，`right_elbow_pitch_joint` 的 dq 差达到约 `11.32 rad/s`；
- 这次分叉应进入“短时动力学/执行器响应实验”，不应继续和接口门禁混在一起。

但是，现在还不能直接得出“armature 已经被证明是根因”，也不建议马上修改官方 MJCF 后把结果当作主基线。当前只能写：

> armature 不一致是与分叉位置和量级相符的首要假设，需要 runtime 参数回读和单关节干预实验验证。

因此，原计划要做两个关键修订：

1. 将原 G0c 的“5 个闭环周期都小于 `1e-4`”拆开：cycle 0 负责验证启动接口，cycle 1 以后归入 R4 短时动力学诊断。
2. 在 5 秒整机基线前，先完成一次证据补包、门禁脚本加固和固定基座单关节实验。

## 2. 当前结果可以支持什么

### 2.1 可以支持的结论

1. R1 的修复方向基本正确，metadata default q 已写入 action offset，repeat-first history 已在两侧实现，共同初态和 actual processed target 也有相应代码。
2. R2/R3 的 JSON、CSV 和 log 对 G0a PASS、G0b PASS、G0c FAIL、cycle 1 首次失败的记录基本一致。
3. cycle 0 的各接口字段都远小于预注册阈值 `1e-4`；报告中的 `≤2.4e-7` 写得不准确，正确上界约为 `4.03e-7`，但不影响“cycle 0 通过”的判定。
4. cycle 1 的主要状态分叉集中在右肘：q、dq、q_des、target 的首坏项都是 `right_elbow_pitch_joint`；action 的首坏项则是 `right_ankle_pitch_joint`，不能写成“所有字段都汇聚到右肘”。
5. 静态配置表显示上肢和腰部 armature 存在较大差异，而腿部多数关节一致。这个现象与右肘率先分叉相符，可以作为优先实验方向。

### 2.2 现在不能支持的结论

1. 不能写“G0a/G0b 已被附件独立复核通过”。R2/R3 ZIP 只有汇总报告，没有随包提供产生报告的原始 NPZ、manifest 和 stdout。
2. 不能写“armature 是已经证实的根因”。目前只有静态相关性，没有单变量干预结果。
3. 不能写“Isaac 实际用了 env 默认 Kp/Kd”。Isaac runner 在创建环境前已尝试用 ONNX metadata 覆写 stiffness/damping；但 manifest 中所谓 `kp_runtime_rt_order`、`kd_runtime_rt_order` 是从 policy metadata 重新构造的，不是真正的 runtime readback。
4. 不能把修改 armature 后的 MJCF 结果称为 Humanoid Lab 官方/原生 Sim2Sim 结果。它只能是 `ARMATURE_MATCHED` 干预组。
5. 不能进入 delay 或 gain sweep。目前两侧对非零 delay 的 CLI 行为不一致，且实际延迟 target 还没有双引擎运行证据。

## 3. 现在暴露出来的问题

### P0-1：原计划把接口门禁和动力学一致性混在了一起

原 G0c 要求两个引擎从共同初态闭环运行 5 个 policy cycles，并让 observation、action、q_des、target、q、dq 全部保持在 `1e-4` 内。

这个判据过宽。cycle 0 是首次执行物理步前的启动接口状态，可以用于验证 observation/action/target 契约；cycle 1 已经分别经历：

- Isaac：5 ms 物理步 × 4；
- MuJoCo：2 ms 物理步 × 10；
- 不同执行器实现、积分器、求解器和模型参数。

因此 cycle 1 以后本来就是动力学比较。继续要求五周期逐点相等，会迫使实验者先改物理参数来“通过接口门禁”，反而破坏原生差异的可解释性。

**修订决定：**

- `G0c-startup-interface`：只检查共同初态 readback 和 cycle 0 的完整接口链；
- `R4-A-closed-loop-prefix`：保留原来的 5-cycle 结果，但改名为短时动力学诊断，不再计入 interface gate；
- 旧的 G0c FAIL 结果永久保留，不覆盖，说明它是旧判据下的结果。

### P0-2：门禁脚本存在“不完整输入也可能 PASS”的风险

当前 `compare_interface.py` 有以下逻辑风险：

- G0b 不强制四个预期姿态和六个预期字段全部存在；字段缺失时直接 `continue`；
- G0c 也会跳过缺失字段；
- 如果最终 rows 为空，`all([])` 会返回 True；
- G0c CSV 的 `first_bad_frame` 仍写成 `-1`，与 JSON/log 的 cycle 1 不一致。

这意味着本次汇总虽然确实有 24 行 G0b 和 6 行 G0c，不是空比较，但脚本本身还不能作为长期可靠门禁。

### P0-3：R2/R3 反馈包缺少原始证据

需要补充但当前 ZIP 没有的文件包括：

- `canonical_initial_state.npz`；
- `isaac_golden_states.npz`；
- Isaac/MuJoCo 的 `policy_trace.npz`；
- `adapter_isaac.npz`、`adapter_mujoco.npz`；
- 两侧 `run_manifest.yaml`、`summary.json`、`stdout.log`；
- 本轮实际使用的 ONNX metadata 摘要、Isaac env 配置快照和 MJCF；
- Python、Isaac Lab/Isaac Sim、MuJoCo、onnxruntime 版本与 Git commit。

现有报告数值可以交叉核对，但无法从附件重新运行 comparator 或检查 runtime 参数。

### P0-4：armature 是首要假设，不是已证实根因

静态对照很有价值，但还缺三步：

1. 读取 Isaac 和 MuJoCo **实际运行时**的 armature、Kp、Kd、effort limit、velocity limit；
2. 固定基座，隔离接触和整机闭环；
3. 只改变 armature 一个因素，看右肘响应误差是否显著收缩。

在这三步完成前，不要把 MJCF 中的 armature 直接覆盖成 Isaac 值，也不要修改 gain 来追求五周期 PASS。

### P0-5：runtime Kp/Kd 记录目前名不副实

Isaac runner 的 manifest 字段 `kp_runtime_rt_order` 和 `kd_runtime_rt_order` 实际来自 policy metadata，不是从 articulation/actuator runtime 读回。后续必须把两类字段分开：

- `kp_requested_from_metadata`、`kd_requested_from_metadata`；
- `kp_runtime_readback`、`kd_runtime_readback`。

若当前 Isaac API 无法直接读到最终 actuator 参数，就明确写 `runtime_readback_unavailable`，并保存创建后的 actuator 配置对象，不允许把 requested 值冒充 readback 值。

### P1-1：metadata 缺关节时仍会硬编码补齐

`MimicOnnxPolicy` 发现 metadata joint names 少于 29 时，仍会追加 `right_wrist_roll_joint`。这与“缺失就报错、只能用显式兼容表”的设计说明矛盾。

处理方式：

- ALIGNED 主线必须直接报错；
- 如果历史 ONNX 确实存在 28-name/29-array 格式，建立独立、版本化的 compatibility table；
- manifest 中写 `compatibility_table_id`，不能在 policy loader 内隐式猜测。

### P1-2：G0a action 重推理没有使用真实 time_step

当前 G0a 对 S2/S3 observation 重推理时统一传入 `0.0`。如果 ONNX 的 `time_step` 输入参与输出，这只能证明“两个 observation 在同一个错误时间输入下给出相同 action”。

处理方式：使用 golden 中每帧的 `reference_time`/`time_step`；若 ONNX 的输入实际是 motion frame index，也必须在 contract 中明确单位，并保存到报告。

### P1-3：MuJoCo trace 缺少 14-body reference/actual 数据

Isaac runner 已记录 14-body reference/actual pose 和 velocity；MuJoCo runner 当前主要记录关节、root 和 torque，没有对称记录 14-body 数据。因此即使直接跑 5 秒，也无法按原计划离线计算两个引擎一致的 body MPJPE、orientation error 和 end-effector error。

处理方式：在 R5 前补齐 MuJoCo 的同名、同顺序、同坐标系 14-body 日志，并把 body names 写入 manifest。

### P1-4：报告和输出仍有小的不一致

- README 说 cycle 0 `≤2.4e-7`，实际最大约 `4.03e-7`；
- README 把 obs 首坏索引写成 22，JSON 中是全局 obs index 618；
- action 首坏是右踝，不是右肘；
- 文档有时写 `gate_summary.json`，脚本实际输出 `interface_summary.json`；
- repeat-first 情况下，`history_valid_length=min(cycle+1,5)` 不能表达“5 个槽已用首帧预填”。

这些不改变主结论，但要在下一版反馈中统一修正。

## 4. 修订后的门禁定义

### G0a：policy contract gate

必须同时满足：

- golden 文件存在且帧数大于 0；
- 770 维 observation 的所有预期 block 均被比较；
- deploy builder 与独立 clean-room builder 都参与；
- action 重推理使用每帧真实 time input；
- action 和 q_des 的比较结果存在且通过；
- 任一文件、字段、shape 或预期帧缺失时直接 FAIL。

### G0b：simulator adapter gate

必须精确出现四组状态：

1. `identity`；
2. `yaw_pos_90`；
3. `yaw_neg_90`；
4. `roll_pitch_nonzero`。

每组必须精确比较六个字段：joint position、joint velocity、root position、root quaternion、world linear velocity、body angular velocity。应得到 `4 × 6 = 24` 行；不是 24 行就 FAIL。

### G0c-startup-interface：启动接口门禁

只比较首次物理执行前的 cycle 0：

- canonical initial state SHA256 相同；
- q/dq/root pose/root velocity readback；
- observation 770；
- raw action 29；
- q_des 29；
- actual processed target 29；
- history buffer 初始化方式和完整内容；
- policy/motion/config/script/asset 指纹。

阈值沿用 `1e-4`，文件或字段缺失直接 FAIL。根据本次汇总，cycle 0 应能通过，但修补 comparator 并带原始数据重跑后才把新版 `overall_interface_gate_pass` 标成 True。

### R4-A：closed-loop prefix dynamics

比较 cycle 1–25（0.5 秒）或先复用已有 3 秒 trace 的前 25 个周期：

- q、dq、action、q_des、target；
- root pose/velocity；
- 14-body pose/velocity；
- 每关节 raw PD torque、clipped command、applied torque；
- 第一处分叉的 cycle、字段、关节和数值。

这一项允许 FAIL；它的目的就是观察动力学从哪里开始分叉。

## 步骤 N5：固定基座单关节因果实验

预计 60–90 分钟。这是下一项最有信息量的实验。

### 实验目的

判断右肘 cycle 1 的巨大 dq 差异是否主要由 armature 不一致导致，同时用一个 armature 已对齐的腿部关节作为阴性对照。

### 选择关节

- 主实验：`right_elbow_pitch_joint`；
- 对照实验：`right_hip_pitch_joint`。如果实际关节表显示该髋关节还有其他重大参数不一致，再选择参数最接近的 hip/knee 关节。

### 固定条件

- base 固定；
- 关闭接触影响，或把机器人置于不发生接触的姿态；
- q0 完全相同，dq0=0；
- 其余 28 个关节保持 q_des=q0；
- 使用相同 metadata Kp/Kd、相同 effort clamp 语义；
- 保留各引擎 native physics dt；
- 不调用 policy，不使用 observation/history；
- 不修改 gain、friction、solver 和 dt。

### 输入

```text
0.00–0.10 s: q_des = q0
0.10–0.50 s: q_des = q0 + 0.10 rad
```

若 `0.10 rad` 会触发 limit 或力矩饱和，统一改为 `0.05 rad`，并在运行前记录这一决定。

### 条件组

| 组 | Isaac | MuJoCo | 唯一变化 |
|---|---|---|---|
| NATIVE | runtime 原生值 | 官方/当前 XML 原生值 | 无 |
| ARMATURE_MATCHED | 同 NATIVE | 在 XML 副本或加载后的实验模型中只把被测关节 armature 改成 Isaac runtime 值 | 只改 armature |

不要覆盖官方 XML。副本命名必须包含 `INTERVENTION_ARMATURE_MATCHED`，manifest 同时记录原 XML hash 和修改后 XML hash。

### 每个 physics step 必须记录

- timestamp、q、dq、qacc、q_des；
- unclipped PD torque；
- clipped command；
- simulator applied torque；
- effort limit、armature、Kp、Kd、physics dt；
- 是否发生饱和。

### 输出指标

- q/dq RMSE；
- peak |dq|；
- 10%–90% rise time；
- overshoot；
- 0.5 秒末端误差；
- 峰值 raw/applied torque；
- 饱和持续时间；
- NATIVE 到 ARMATURE_MATCHED 的误差缩减比例。

### 预注册解释

- 如果只改 armature 后，右肘 q/dq RMSE 至少缩小 50%，而髋关节指标变化不超过 10%，则“armature 是右肘早期分叉的主要贡献因素”得到较强支持；
- 如果右肘改善小于 50%，不要继续同时改 gain 和 dt。先检查 actual torque/effort clamp，再按单变量顺序测试 gain、damping/friction、dt/solver；
- 无论结果如何，都不能写成“不同物理引擎只由 armature 差异造成”。

### 第二次反馈节点

完成 N4/N5 后立即反馈：runtime 参数 CSV、两关节所有条件的 raw trace、曲线、manifest 和一句不带推测的结果摘要。这个节点决定是否值得做 armature-matched 整机实验。

## 步骤 N6：0.5 秒整机闭环短时动态

预计 30–60 分钟。

### 怎么做

优先从已有 3 秒 raw trace 截取前 25 个 policy cycles；只有数据字段不足时才重跑。

先做 `NATIVE` 配对：

- 同 policy、motion、initial state、history、seed；
- 0 ms delay、gain scale=1；
- Isaac 5 ms×4，MuJoCo 2 ms×10；
- 官方/当前原生资产，不应用 N5 的 armature 修改。

如果 N5 明确支持 armature 假设，再追加 `ARMATURE_MATCHED` MuJoCo 干预组。不要用干预组替代 NATIVE。

### 必须输出

- 每周期最大 q/dq/action/q_des/target 差；
- 按关节排序的 cycle 1 dq 差异表；
- right elbow 与 right hip 的 q/dq/torque 曲线；
- root 和 14-body 指标；
- 首次出现 torque saturation 的时间和关节；
- NATIVE 与干预组的差异缩减比例。

### 完成判据

能回答三个问题：

1. 第一处真实物理分叉发生在哪个关节、哪个 physics/policy step？
2. 分叉之前两侧送入执行器的 target 和 requested Kp/Kd 是否相同？
3. armature 单变量干预能解释多少早期差异，剩余差异主要落在哪些字段？

## 步骤 N7：5 秒配对基线

只有 N1–N6 完成后才进入。

### 主基线

主结果必须是 `NATIVE`：两个项目各自当前真实运行配置，不覆盖官方/当前 MJCF。

### 可选干预基线

只有 N5/N6 已显示 armature 对齐有明确效果时，才追加 `ARMATURE_MATCHED`。报告中必须把它标成参数干预，而不是官方结果。

### 必须收集

- 两引擎 5 秒完整 policy trace；
- 同名同序 14-body reference/actual pose/velocity；
- q/dq/action/q_des/actual target；
- raw/clipped/applied torque；
- root height/roll/pitch；
- failure predicate 和首次失败时间；

- actual target 或 runtime gain 仍无法确认时，停止执行器归因；
- 任一 run 的 policy/motion/initial state hash 不同，整组作废；
- NATIVE 失败仍要保留，不允许用干预组覆盖。
