## 3. 阻塞正式跨引擎实验的问题

### P0-1：接口门禁实际已经失败

`01_lab_interface_gate/compare_real/` 的复算结果为：

| 项目 | 当前结果 | 原目标 | 判定 |
|---|---:|---:|---|
| `qpos_rel max_abs` | 0.048 rad | `1e-5` 量级 | FAIL |
| `qpos_rel RMSE` | 0.028714 rad | `1e-5` 量级 | FAIL |
| 统一重推理 action max_abs | 0.165081 | 未显式写入阈值 | FAIL |
| 统一 `q_des` max_abs | 0.030122 rad | 两侧应使用同一 contract | FAIL |

这不是 metadata 三位小数量化可以解释的误差。三位小数的单值量化误差约不超过 `5e-4`，而当前最大差是 `4.8e-2`。

原因已经定位：

- Isaac 当前 observation 的 joint position 相当于 `q - 0`；
- 部署 builder 使用 `q - metadata_default_q`；
- metadata default q 的最大绝对值为 0.048 rad。

**处理决定：**当前结果永久保留为 `AS_SHIPPED-G0-FAIL`。不要覆盖原 CSV/JSON，也不要把这个差异写成可人工豁免项。

### P0-2：前 4 帧被排除，掩盖了启动 history 不一致

当前 comparator 从 index 4 开始比较。这个做法只验证 history 填满后的 steady-state 布局，却跳过了真实闭环最关键的前 4 个动作。

复算第 0 帧：

- Isaac：每个 observation field 的当前值被复制到 5 个 history 槽；
- 部署/MuJoCo：`RingHistory` 前 4 个槽补零，只在最后一个槽放当前值；
- 实际独立 smoke 在第 0 帧已经出现：
  - observation 最大差 `15.8119`；
  - action 最大差 `1.6704`；
  - `q_des` 最大差 `0.3588 rad`。

即使第 4 帧以后 history 结构相同，两个闭环已经被前四次不同动作推向不同状态。因此后续门禁必须把 startup 和 steady-state 分开报告，并且 primary `ALIGNED` 实验必须让两侧采用同一种 history 初始化。

本周的主实验选择：**两侧均用第 0 帧 observation 预填 5 个槽**，与 Isaac reset 后的实际输入一致。官方部署的前置零填充保留为 `AS_SHIPPED` 诊断条件，不用于物理公平比较。

### P0-3：两侧初始 q 不同

两个 5 秒 smoke 的第 0 帧：

- root position：一致；
- root quaternion：最大差约 `8.6e-8`；
- dq：一致；
- q：最大差 `0.152502 rad`。

具体是：

| 关节 | motion frame 0 | Isaac 实际回读 | 差值 |
|---|---:|---:|---:|
| left knee | -1.050002 | -0.897500 | 0.152502 |
| right knee | -0.976960 | -0.897500 | 0.079460 |

Isaac 在 reset 时按 soft joint limit 截断了两个膝关节；MuJoCo runner 则直接写入 motion frame 0，其中左膝还低于合同表中的 `-1.0 rad` 下限。

**处理决定：**先由 Isaac reset 后的实际 readback 生成唯一的 `canonical_initial_state.npz`，再把同一份 q/dq/root pose/root velocity 写入 MuJoCo。两侧写入后必须再次回读，禁止只比较“计划写入值”。动作参考仍从 frame 0 开始，但报告中要说明共同初态相对 motion reference 已有初始膝关节误差。

### P0-4：Isaac 记录的 q_des 可能不是实际执行目标

Isaac runner 当前手工记录：

```text
recorded_q_des = action × metadata_scale + metadata_default_q
```

但真正执行的是 `env.step(raw_action)`。runner 设置了 action scale，却没有把 Isaac runtime default joint position 和 action term offset 改成 metadata default。当前 `qpos_rel` 差异也证明 runtime default 与 metadata default 不同。

因此必须增加三项 runtime 回读：

1. `runtime_default_q[29]`；
2. `action_term_offset[29]`；
3. `actual_processed_joint_position_target[29]`。

只有逐帧满足：

```text
recorded_q_des == actual_processed_joint_position_target
```

才能继续使用 `q_des` 和控制误差指标。

### P0-5：当前门禁没有验证 MuJoCo runtime adapter

`compare_interface.py` 直接把 Isaac golden 中已经整理好的以下数组喂给部署 builder：

- body-frame angular velocity；
- policy order 的 q/dq；
- golden previous action。

所以 `base_ang_vel=0`、`qvel=0`、`action history=0` 并不证明 MuJoCo 的原始 runtime state 已正确转换。它们只证明“同一个规范数组进入 builder 后得到同一个结果”。

后续必须拆成：

- `G0a policy-contract gate`：同一 canonical state 分别进入两个独立 observation builder；
- `G0b simulator-adapter gate`：向两引擎注入同一 q/dq/root state，再分别从真实 runtime 读取并转换到 canonical state。

### P0-6：20 ms delay 当前既会报错，也不是 20 ms

MuJoCo runner 以 2 ms 物理步计算 `delay_steps=10`，但 FIFO 只在每个 20 ms policy cycle 推进一次。因此即使能运行，实际也是：

```text
10 × 20 ms = 200 ms
```

并且 FIFO 初值为 10 个 `None`，第一个非零延迟 run 会把 `None` 送入 PD 计算。

**处理决定：**取消当前延迟实验。修复后先做已知脉冲测试，证明命令在第 10 个 MuJoCo physics step、即 20 ms 后出现，再允许执行 0/20 ms 对比。

## 4. 其他需要修正的问题

### P1：正式基线前必须修

1. MuJoCo 的 `d.actuator_force` 本身已经是 29 维，当前使用 `[6:]` 后只保存了 23 维。现有所有 `applied(29)` 实际 shape 都是 `(physics_steps, 23)`，现有 torque/saturation 指标不可用。
2. `world_to_init_motion_quaternion` 因多取一次 `[0]`，实际保存成 `(104,)`，不是 `(104,4)`。
3. MuJoCo `summary.json` 的 `init_root_z` 是运行结束后读取的 final z，字段名错误。
4. `--motion` 在 Isaac runner 中没有真正控制 env 使用的 motion；代码仍硬编码 repo 中的 `dance_9.npz`。manifest 可能哈希一个参数文件，但运行另一个文件。
5. `--seed` 在两个 runner 中没有完整应用；至少要保存 `numpy/torch/env` 的实际 seed 设置。无随机化时可以写 `not_used`，不能假装 seed 已生效。
6. `interface_summary.json` 没有整体 `gate_pass`，action/q_des 也没有阈值。后续必须机器可读地输出每层 PASS/FAIL。
7. 当前 failure check 在判定失败后仍执行一个 control interval，和“首次失败立即停止”的文字不一致。
8. 正式结果缺少 14-body reference/actual 状态和 body/anchor 主任务误差；目前只能判断未触发宽松 failure predicate。
9. 所有 MuJoCo smoke 目录都没有 `run_manifest.yaml`；summary 仅保存 policy hash，缺 motion/XML/config/script/commit/初态/映射哈希，不能满足正式 run 的复现合同。
10. `compare_interface.py` 即使超阈值也会正常退出，自动化流程会把 FAIL 当命令成功。后续 FAIL 必须写 `overall_gate_pass=false` 并返回非零退出码。
11. 当前 `convert_joint_order` 对缺失关节会静默填 0，metadata 28→29 也以硬编码方式追加 wrist。正式 runner 必须使用显式兼容表，并对 joint set/order 做 exact assertion；manifest 要写明这是 patched replacement chain。

### P2：文档和打包修正

1. `readiness_and_blockers.md` 仍说三个 runner 待实现、runtime joint order 未验证，与 ZIP 内实际结果冲突。
2. `evidence_ledger.csv` 仍把 smoke/gate 标成 `not_run`，并把环境、commit、静态代码证据都标成 A。按计划定义，静态代码证据应是 D；当前单引擎 smoke 是 B；只有同一 contract 的本周双引擎重跑才是 A。
3. `canonical_policy_contract.json` 的 `motion_len_frames` 仍是 null，且声称 metadata 全量，但原始字符串有省略号。
4. 生成 `canonical_policy_contract.json` 的 build script 没有打入 ZIP，不能从附件独立再生静态证据。
5. Isaac `video.mp4` 已由日志确认全黑，应作为失败证据，不可作为动作视频交付。
6. MuJoCo 唯一非黑视频来自 1 秒 run，实际只有 25 帧；5 秒 `smoke_v3_video` 没有视频。两端都在 20 ms policy tick 上按 30 Hz 门槛采帧，实际会退化成 25 fps，却以 30 fps 编码，导致视频时长变短。正式录像要改成 physics-tick 30 Hz 采样或明确编码 25 fps，并校验帧数/时长。
7. 20 秒 1280×720 RGB 帧全部留在内存可能额外占约 1.4 GB，Isaac Kit 环境有 OOM 风险；正式录像应流式写入。
8. ZIP 使用 Windows 反斜杠路径，macOS `unzip` 会在中文文件名处中断；后续打包应使用 `/` 路径并在 Windows、WSL、macOS 各做一次列目录和 CRC 测试。

### 步骤 R2：生成并验证共同初态

#### 怎么做

1. 在 Isaac 中按 start frame 0 reset；
2. 读取 reset 后的实际 q/dq/root pose/root linear/angular velocity；
3. 写入 `canonical_initial_state.npz`；

5. 两边再次读取 runtime state，转换到相同 policy order、wxyz 和单位；
6. 生成 `initial_state_comparison.csv`。

#### 通过标准

| 字段 | 标准 |
|---|---|
| joint names/order | exact |
| q/dq | `max_abs <= 1e-6`，如引擎写入精度不足则先预注册更宽阈值 |
| root position/velocity | `max_abs <= 1e-6` |

| 所有数值 | finite |

```json
}
```

每个 false 都必须带 `first_bad_cycle`、`field`、`index/joint_name`、`expected`、`actual`。

#### 硬停止条件

任意 G0 子门禁失败，都不能进入正式动态对比。只修第一个失败字段，再完整重跑三层门禁。

### 步骤 R4：短时动态与执行器隔离

G0 全部通过后，先运行 0.2–0.5 秒，而不是直接跑 20 秒。

#### 实验 A：闭环短时前缀

- 相同 initial state；
- 相同 deploy builder 和 repeat-first history；
- 0 ms delay；
- 50 Hz policy；
- native physics dt：Isaac 5 ms×4、MuJoCo 2 ms×10。

画出 q、dq、q_des、root、body MPJPE 随时间的第一处分叉。该结果定位“从第几个物理/策略周期开始分叉”，不做长期稳定结论。

#### 实验 B：固定基座单关节 step 或 open-loop q_des replay

优先选择一个 hip pitch 或 knee joint：

- 固定基座或禁用接触影响；
- 使用同一个 q_des step；
- 记录 0.5 秒 q/dq/raw torque/applied force；
- 验证 Kp/Kd、effort clamp、armature 和物理 dt 的实际响应。

只有该实验语义一致后，才能把后续控制响应差异与 actuator/physics 层联系起来。

### 步骤 R5：5 秒配对基线

#### 进入条件

- G0a/G0b/G0c 全 PASS；
- 短时前缀没有接口级突变；
- body/anchor 指标已经能从日志离线重算；
- Isaac 和 MuJoCo 实际 target 记录正确。

#### 必须收集

- 5 秒 policy trace；
- body/anchor 主指标；
- root height/roll/pitch；
- q/q_des/action 诊断；
- failure predicate 和首次失败帧；
- 一次相同条件 checksum 重跑。

视频不是此门禁的前置条件。Isaac headless camera 仍黑时，先交付曲线；完成数值基线后再用 GUI/viewport 录屏或修相机。

#### 通过后的准确表述

若两侧均跑满 5 秒，只能写“在该动作、共同初态和自定义 failure predicate 下跑满 5 秒”。仍需用 body/anchor 指标判断动作跟踪质量。

### 步骤 R6：20 秒正式基线

只有 R5 完整后执行一次每引擎 20 秒正式 run，再各做一次 5 秒前缀 checksum。

当前 `dance_9` 共有 29.7 秒，start frame 0 的 20 秒不会越界。若后续改 start frame，必须先检查 `start_frame + duration × 50 < 1485`。

正式结果至少生成：

1. body MPJPE / body orientation error；
2. anchor z / orientation error；
3. root height、roll、pitch；
4. 腿、腰、左右臂的 q tracking RMSE；
5. q_des-q、action rate；
6. task completion/failure time；
7. torque 指标仅在 29 维语义与 effort limit 对齐后报告。

这组结果仍应称为 `native-dt default-stack comparison`，因为两侧物理 dt、资产转换、collision geometry 和求解器同时不同；不能称为纯 solver 对比。

### 步骤 R7：最后才做 delay；gain 本周取消

#### delay 进入条件

- 0 ms 的 20 秒基线完成；
- MuJoCo FIFO unit test 证明输出精确滞后 10 个 2 ms physics steps；
- Isaac runtime 也实际回读为 4 个 5 ms physics steps；
- 两侧启动前历史 target 定义相同。

只做：

| Run | Delay |
|---|---:|
| baseline | 0 ms |
| stress | 20 ms |

不做 10 ms 和 gain sweep。该实验只描述当前策略在这一个动作和共同初态下对固定延迟的敏感性，不证明训练随机延迟带来了因果收益。

## 7. 最终可汇报的结论模板

如果只完成当前审查和 G0 修复，报告可以写：

> 对 Humanoid Lab 的直接 ONNX Sim2Sim 链进行了接口审计。初版 runner 在 Isaac 和 MuJoCo 中均可独立运行 5 秒，但严格门禁发现 source/deploy 在 startup history、default joint offset 和初始膝关节状态上不一致。这些差异在第 0 个策略周期已造成显著 action/q_des 偏差，因此初版结果不能用于物理引擎归因。后续通过 ALIGNED runner、共同初态和 runtime adapter 门禁消除接口混杂后，再进行短时和长期闭环比较。

- “接口门禁已通过”；
- “Isaac 与 MuJoCo 行为已经一致”；
- “5 秒不跌倒证明动作复现正确”；
- “当前差异来自求解器/摩擦/PD”；
- “20 ms 延迟实验已经可运行”。

## 8. 最终判断

后续计划需要明显收缩和重排，但不需要推倒重来。步骤 1–3 和大部分静态分析可以保留；现有动态产物也有价值，因为它们形成了一组清楚的 `AS_SHIPPED-G0-FAIL` 证据。

最优先的四件事是：

1. 统一 default q 和实际 action offset；
2. 统一 startup history；
3. 生成并回读共同可行初态；
4. 记录 actual processed target，并补 runtime adapter gate。

这四项全部通过后，再进入 0.5 秒、5 秒、20 秒动态实验。延迟和增益实验都应后移，其中 gain 本周直接取消。
