## 0. 先明确这两天要证明什么

这两天不是要把三个项目都重新训练一遍，也不是要把 Isaac 和 MuJoCo 的每一条轨迹调成完全相同。最终需要回答以下四个问题：

1. Humanoid Lab、Humanoid Gym、SONIC 分别怎样把训练侧策略搬到 MuJoCo？
2. 同一个策略进入第二个仿真器后，差异已经存在于策略接口，还是在接口之后的闭环物理层才出现？
3. 动作延迟、控制频率和 PD 增益变化后，策略的稳定性和跟踪能力怎样变化？
4. 哪些方法可以沉淀为 SONIC 后续 Sim2Sim 的通用检查和实验流程？

本计划把“Sim2Sim 做得好”拆成四层：

| 层级 | 要证明的内容 | 主要证据 |
|---|---|---|
| G0：接口正确 | observation、action、关节顺序、坐标系和 history 一致 | 连续 104 帧采集，后 100 帧逐字段对比 |
| G1：能够运行 | 策略在目标仿真器不报错、不出现 NaN、不立即跌倒 | 运行日志、存活时间、视频 |
| G2：行为接近 | 两侧完成相同任务，运动节奏和任务指标接近 | 并排视频、跟踪误差、足滑、躯干状态 |
| G3：具有鲁棒性 | 延迟、控制频率、PD 参数轻微变化后仍能运行 | 延迟和增益消融曲线 |

这两天必须完成 G0–G2；G3 做小规模实验，不进行大范围参数搜索。

这里的 G2 不预设“行为接近”的工程合格阈值。当前没有经过团队确认的等价阈值，因此本周只报告预注册指标的差值，不使用“物理对齐完成”“两侧行为一致”等强结论。

### 0.1 成功、失败和动作完成率的统一定义

- **协议成功：**同一策略、动作、起始帧和 canonical contract 下完成一次 run；`reset_count=0`；manifest 和最小日志完整。
- **任务成功：**在计划时长内没有触发共同 failure predicate，也没有 NaN/Inf。
- **动作完成率：**`min(首次 failure 帧, 计划帧数) / 计划帧数`。
- **存活时间：**从第一个有效策略周期到共同 failure predicate 首次成立；跑满计划时长应标记为“右删失”，不能写成永久稳定。
- **行为差异：**报告 body/anchor 跟踪、root、足滑、控制误差等预注册指标，不凭视频给出 pass/fail。

共同 failure predicate 必须在正式运行前冻结，并在两侧离线使用同一算法。第一版直接复刻 Lab mimic 的三个任务失败条件：

1. `abs(anchor_z_ref - anchor_z_actual) > 0.4 m`；
2. reference/robot projected-gravity 差异大于 `0.8`；
3. 左右 ankle-roll 和 wrist-roll 的 reference/actual 高度误差任一大于 `0.4 m`；
4. 任意关键状态、observation 或 action 出现 NaN/Inf。

`time_out` 不作为跌倒：正式 runner 将 episode length 设为大于运行时长。Isaac 原生 termination reason 仍另行保存；后续如果增加非允许部位接触条件，必须作为新版本 predicate 同时重算两侧数据，不能只改一侧。

### 0.2 证据等级

每条结论必须标注证据等级：

| 等级 | 定义 |
|---|---|
| A | 本周双引擎重跑，具有 manifest、同一 contract 和完整最小日志 |
| B | 本周单引擎重跑，具有 manifest 和日志 |
| C | 历史日志或视频，checkpoint/config 只能部分追溯 |
| D | 仅由代码静态分析得到 |

跨项目只比较实现方法、接口完整性和证据完备性；不能把 Lab 的 A 级数据与 Gym/SONIC 的 C 级历史视频做性能排名。

### 0.3 两天内不能支持的因果结论

- 接口门禁通过后，只能说明差异位于“接口之后的闭环物理层”，不能仅靠 `dance_9` 唯一归因到执行器、刚体、接触或求解器。
- 延迟实验只能描述当前策略对固定延迟的容忍度；没有无延迟随机化训练的匹配策略时，不能证明“训练延迟随机化导致鲁棒性提升”。
- SONIC back-transfer 失败只能说明该 checkpoint 在该 Isaac 评估链中失败；“策略产生引擎绑定”是候选解释，不是已隔离证明的原因。

### 4.2 Isaac runner 必须怎样工作

### 4.4 mimic observation 必须逐项复刻

ONNX 输入为：

- `obs`：shape `(1, 770)`。
- `time_step`：shape `(1, 1)`，float32。
- 输出：`actions`，29 维。

每个时刻共有以下 154 维 observation term，但部署侧不是把五个完整 154 维帧直接拼接。`ObsHistory` 为每个字段分别维护 5 帧 ring，先 flatten 某字段的 5 帧，再拼下一个字段，即 field-major：

| 字段 | 单帧维度 | 5 帧维度 |
|---|---:|---:|
| 当前参考动作 joint position + velocity | 58 | 290 |
| motion anchor orientation 前两列 | 6 | 30 |
| base angular velocity | 3 | 15 |
| measured q - default q | 29 | 145 |
| measured dq | 29 | 145 |
| previous action | 29 | 145 |
| 合计 | 154 | 770 |

770 维准确布局为：

```text
curr_motion_data[5×58]
  + motion_anchor_ori_b[5×6]
  + base_ang_vel[5×3]
  + qpos_rel[5×29]
  + qvel[5×29]
  + previous_action[5×29]
```

history 未填满时在前部补零；首帧 previous action 为零。Isaac 环境实际输出的 770 维布局仍必须由接口门禁验证，不能仅凭同一作者实现就假设一致。

### 4.5 每个策略周期的统一采样顺序

两个 runner 都必须使用以下语义：

```text
读取 state_t
  → 构造 obs_t
  → policy(obs_t) 得到 raw_action_t
  → action scale + default q 得到 q_des_t
  → 在接下来的一个 control interval 内执行 PD
  → 得到 state_(t+1)
```

若一侧记录的是执行前状态，另一侧记录的是执行后状态，会产生固定一帧错位，因此必须先统一采样语义。

## 步骤 7：运行 Humanoid Lab `dance_9` 受控跨引擎基线

### 实验编号

| Run ID | 引擎 | 用途 |
|---|---|---|
| LAB-B00-ISAAC | Isaac | 20 秒正式基线 |
| LAB-B00-ISAAC-CHK5 | Isaac | 5 秒前缀复现检查 |
| LAB-B00-MJ | MuJoCo | 20 秒正式基线 |
| LAB-B00-MJ-CHK5 | MuJoCo | 5 秒前缀复现检查 |

### 实验目的

验证同一个 ONNX、同一个动作和同一个控制周期，在 Isaac/PhysX 和 MuJoCo 中能否完成相同动作，并量化闭环差异。

### 必须固定的变量

- 策略：`motion_anchor_obs_model_23500.onnx`。
- 动作：`dance_9.npz`。
- 动作片段：从第 0 帧开始，持续 20 s。
- 随机种子：42。
- control dt：0.02 s。
- 动作延迟：0 ms。
- gain scale：1.0。
- observation noise：关闭。
- 外力 push：关闭。
- 域随机化：关闭。
- 初始 q、root pose、history 初始化：相同。
- canonical default q、action scale、Kp/Kd：两侧均来自同一导出的 contract。
- episode length：大于 22 s。
- adaptive phase sampling：关闭，`start_frame=0`。
- auto-reset：禁止；首次 failure 即停止。

允许保持不同的只有物理积分步长：

- Isaac physics dt：0.005 s，decimation 4。
- MuJoCo physics dt：0.002 s，decimation 10。

这组 native-dt baseline 比较的是两个项目默认完整栈，差异同时包含引擎、积分步长、资产转换和碰撞几何影响，不能称为纯 solver 效应。如果主线提前完成，可以再做一个 MuJoCo `dt=0.005 s, decimation=4` 的 matched-dt probe；它仍不能消除 URDF/MJCF 和 collision 差异。

### 怎么执行

按照步骤 5 的命令运行，将 duration 改为 20，并分别使用正式 run ID。每个引擎完成一次正式基线，再用完全相同条件运行一次 5 秒 checksum 检查。5 秒检查用于检测确定性/复现性，不作为独立统计样本，也不计算置信区间。

### 每次结束后立即检查

```text
[ ] video.mp4 时长约 20 秒
[ ] policy_trace 有约 1000 个策略周期
[ ] reset_count=0；若提前 failure，则日志在首次 failure 处结束
[ ] root quaternion 始终有限
[ ] 29 维 q/dq/action/q_des/tau 均存在
[ ] run_manifest 中策略、动作和资产哈希完整
[ ] 正式 run 与 CHK5 的前缀 action/checksum 一致，或已量化记录运行时非确定性
[ ] 没有跌倒时也记录明确的 fall=false
```

### 必须计算的指标

#### 主任务指标

- 动作完成率。
- 存活时间和跌倒时间。
- 初始 yaw/水平平移对齐后的 body position error（MPJPE）。
- body orientation error。
- body linear/angular velocity error。
- anchor position/orientation error。

#### 诊断指标

- 29 关节 tracking RMSE，以及腿部、腰部、左臂、右臂分组 RMSE。
- root/reference 高度误差和姿态误差。

#### 控制指标

- `q_des - q` RMSE。
- `tau_pd_raw` 和 simulator-reported applied actuator force 各自的 RMS/峰值；只有语义和 limit 对齐后才比较 saturation ratio。
- action 一阶差分 RMS 和按时间归一化的 `Δaction/Δt`。
- simulated dt/control dt 与 inference wall time 分开报告。直接 runner 不报告 ROS2 scheduler/transport jitter。

#### 条件触发的接触指标

- 左右脚接触占空比。
- 单支撑和双支撑持续时间。
- 接触期间足端水平滑动速度。
- 接触冲量。

第一版最小 runner 若无法在时间盒内取得语义一致的接触法向力，只保留 root、body、q/q_des/action/done；接触指标标记 unavailable，不得阻塞基线。

### 怎样比较

- 前 0.5–1.0 s 可以比较同起点的短时轨迹差异。
- 闭环轨迹开始分叉后，不再要求逐帧 q 完全重合，比较任务级和统计级指标。
- contact force 不做逐采样点硬对齐，使用冲量、接触时序和足滑。
- quaternion 使用姿态夹角，不直接对四个分量做 RMSE。

### 本步骤必须产出的图

1. root height、roll、pitch 随时间变化。
2. 左右 hip pitch、knee、ankle pitch 的 q 和 q_des。
3. 代表关节 torque 和 raw action。
4. 左右脚 contact 和 foot slip。
5. 按身体分组的 tracking RMSE 柱状图。

### 本步骤必须产出的视频

- MuJoCo 单独视频。
- 同一时间轴并排视频。

## 步骤 8：Humanoid Lab 动作延迟消融

### 实验编号

| Run ID | 引擎 | 固定延迟 |
|---|---|---:|
| LAB-D20-ISAAC | Isaac | 20 ms |
| LAB-D20-MJ | MuJoCo | 20 ms |

0 ms 结果直接复用步骤 7 的 baseline。10 ms 为全部主线提前完成后的可选中间点，不是硬交付。

### 实验目的

描述当前 Lab 策略对 20 ms 固定执行器延迟的容忍度。该实验不证明训练随机延迟是容错提升的原因。

注意：Lab 代码中的 `max_delay=4` 表示 4 个 Isaac 物理步。Isaac physics dt 为 5 ms，因此最大约 20 ms，不是 4 ms。

### 怎么做

1. 保持 baseline 的策略、动作、初始状态、增益和控制频率不变。
2. 延迟语义统一为“q_des 进入 PD/actuator 前的物理步级 FIFO”，不能一侧延迟 raw action、另一侧延迟 torque。
3. Isaac 用 4 个物理步实现 20 ms；MuJoCo 用 10 个物理步实现 20 ms。
4. 两侧各运行一次，与 0 ms baseline 比较。
5. 只有主线提前完成时，才增加 10 ms 中间点。

### 必须收集的结果

- 存活时间和跌倒时间。
- 关节 tracking RMSE。
- root 姿态误差。
- `q_des-q` RMSE。
- torque RMS、峰值和饱和比例。
- 非平稳 `dance_9` 不用单一“相位差”数字；只比较跟踪时序曲线。若要估计相位/频响，另做正弦 probe。
- 足端滑移。
- 所有指标相对 0 ms baseline 的退化比例。

### 要画的图

- 0/20 ms 两点斜率图，纵轴为主任务误差、root orientation RMS、存活时间和 q/q_des RMSE。足滑/torque 只有语义验证完成后再加入。

### 怎样解释结果

- 两侧都随延迟相似退化：策略延迟鲁棒性在两个引擎中表现一致。
- MuJoCo 明显更敏感：检查 MuJoCo PD 更新时机和动作队列位置。
- 20 ms 仍稳定：只能说明当前策略在该动作和初态下容忍 20 ms 固定延迟。
- 指标不单调：优先检查延迟实现是否放在了错误的采样位置。

## 步骤 12：统一计算指标和生成图表

### 实验目的

把三个项目的原始日志转成相同结构的指标，避免最后只能描述视频观感。

### 12.1 时间对齐

按以下顺序处理：

1. 检查 timestamp 是否单调递增。
2. 检查每个 run 的 policy Hz 是否符合配置。
3. Lab 基线按 `reference_time` 和 `policy_step` 对齐。
4. 短时轨迹只比较开始后的 0.5–1.0 s。
5. 长时闭环使用任务级统计，不强制逐帧重合。

### 12.2 指标定义

#### 关节跟踪误差

```text
joint_tracking_error = q_actual - q_reference
joint_control_error  = q_actual - q_des
```

同时报告：

- 全关节 RMSE。
- 按身体分组 RMSE。
- 按 joint range 归一化的 RMSE。

joint range 必须来自步骤 4 冻结的 canonical limit 表，不能让两个引擎各用自己的 limit 做归一化。对 mimic，关节 RMSE 是诊断指标，主指标是 yaw/translation-aligned body MPJPE、body orientation error 和 body velocity error，因为训练的主要正奖励围绕 anchor/body 跟踪，直接 joint-position tracking reward 权重为 0。

#### 姿态误差

先计算两个 quaternion 的相对旋转，再转换成最短旋转角。不要直接比较 quaternion 四个分量，因为 `q` 和 `-q` 表示同一姿态。

#### 足端滑移

只在该脚处于接触状态时统计足端水平速度：

```text
foot_slip = mean(norm(foot_velocity_xy)) during contact
```

若计算接触指标，必须预注册相同 foot body/geom 列表、法向力进入/退出阈值、滞回和最小持续时间。Isaac 使用 contact sensor 聚合指定脚部 body；MuJoCo 使用每个 contact 的 `mj_contactForce` 聚合脚部法向力。定义不能在看完结果后改变。

#### 力矩指标

- `tau_pd_raw` RMS/peak。
- actuator command after limit RMS/peak。
- simulator-reported applied actuator force RMS/peak。
- 只有 canonical effort limit 和 applied-force 语义完成逐关节验证后，才报告 `abs(applied) >= 0.99 * effort_limit` 的比例。

#### 控制时序

- simulated physics dt/control dt。
- inference time mean/P99。
- wall-clock loop period 仅用于说明计算开销。
- ROS2/DDS scheduler/transport jitter 只在实际官方双进程链运行时报告；直接 sequential runner 不得用 wall time 代替部署通信延迟。

7. **Gym 结果**：轻量 runner 的优点和隐式契约风险。
8. **SONIC 结果**：接口修正、目标域微调和 back-transfer 失败分别支持什么、不能支持什么。
9. **三项目经验总结**。
10. **局限性和后续工作**。

建议最终经验总结围绕以下七点：

1. 先冻结接口契约，再讨论物理参数。
2. joint order、default pose、action scale 和 history 是 Sim2Sim 的第一优先级。
3. policy/control dt 必须一致，PD 应在每个物理步更新。
4. 模型、策略、动作和配置必须有哈希和 manifest。
5. 当前策略在训练中使用了延迟和域随机化；正式测量时必须固定或关闭。只有匹配的无随机化策略对照才能证明它们带来因果收益。
6. 单进程直接 runner 适合快速验证；ROS2/DDS 部署链更接近真机，但会引入调度和通信抖动。
7. 视频用于展示，短时 same-state 门禁和长时任务指标才用于判断。

# 硬停止规则

1. 接口门禁未通过，不调物理参数。
2. 策略或资产哈希不同，不比较运行结果。
3. observation/action 的采样时刻不同，不比较逐帧轨迹。
4. 只有视频、没有日志，不宣称完成定量对齐。
5. 不同机器人之间不直接比较绝对 q RMSE、torque 或 contact force。
6. 单次偶然成功不视为稳定；至少保留重复运行或明确说明只运行一次。
7. 任何修改都必须写入 manifest 和实验记录，不能只保留最终“最好看”的条件。
8. Windows 可用内存低于 3 GB 时停止启动新的 Isaac Kit。
9. Isaac 崩溃后先检查并结束残留 Kit，再启动一次；不同时运行多个 Kit。
10. 到达时间盒后按砍项顺序收缩范围，不牺牲接口门禁和基线数据完整性。
11. 第一天 16:00 两侧 smoke 未同时通过，停止录像美化、接触指标和消融，转入 blocker/静态证据路线。
12. 第二天 10:30 接口仍未通过，不进行任何延迟、增益或物理参数实验。
13. 第二天 12:00 没有受控配对基线，停止继续开发高级工具，转入失败报告、证据台账和后续计划。
