## 1. B.1 补丁的验收结论

### 1.1 已确认通过的内容

对 `R4F_N5R_b1_patch.zip` 做了独立检查，已确认：

- 压缩包 SHA256 为 `70113df393149f3cbabdc41b709bb6db019ea8bfa1c7b2b3bfc18fb21fd90db6`，与反馈一致。
- 包内 `SHA256.txt` 对全部文件的校验通过。
- 7 个 Python 脚本均能通过 `py_compile`。
- 修复后的 elbow、hip 隔离资产空间尺度正常，不再出现 link 被推到约 24.5 m 的问题。
- elbow G0：normalized topology、FK、质量、COM 和等效惯量均通过；dummy flange 的忽略规则是显式且受阈值约束的。
- hip G0：原始和归一化拓扑均通过；FK、质量、COM 和等效惯量均通过。
- 旧 trace 配新 G0 的负测试会失败。
- G6 缺少 runner/model 哈希的负测试会失败。
- 三次重复数、必需字段、哈希一致性和逐点确定性检查已经明显比旧版严格。

因此，不需要推翻 B.1，也不需要再开展一轮大规模代码改造。

### 1.2 必须先补的三个小缺口

这三个修改控制在 20–40 分钟内完成。完成后直接运行 smoke，不再单独制作另一轮审查包。

#### B1-F1：G0 必须真实绑定 matched XML

当前问题：

- elbow 调用 G0 compare 时，如果漏传 `--xml-matched`，脚本会把 native XML 的哈希复用为 matched 哈希。
- 实测此时仍输出 `G0_PASS`，native 和 matched 哈希完全相同。
- 这会导致“armature matched 干预”实际未加载，却被门禁误认为已绑定。

修改方法：

1. `asset_equivalence_check.py` 的 compare 模式对 elbow 和 hip 都强制要求 `--xml-matched`。
2. 把 `mj_matched_xml_sha256` 加入 required hash 列表；缺失时 `pass=false` 且进程 `exit 1`。
3. 不再用“没有传 matched 就把 native 当 matched”的隐式逻辑。
4. hip 的 native/matched 本来就是 no-op，也仍然显式传入两个文件；随后断言二者 SHA256 相同。
5. elbow 额外断言 native/matched 的模型差异只包含目标关节 `right_elbow_pitch_joint` 的 armature 数值变化，不能混入质量、惯量、阻尼、摩擦或其他关节变化。

验收方法：

```text
负测试：elbow compare 不传 --xml-matched
预期：G0_FAIL，exit=1，hash_missing 包含 mj_matched_xml_sha256

正测试：显式传 elbow native 和 matched
预期：G0_PASS；两个哈希不同；资产差异审计只有目标 armature

正测试：显式传 hip native 和 matched
预期：G0_PASS；两个哈希相同
```

#### B1-F2：汇总器必须要求 G0 自身的全部绑定字段存在

当前问题：

- `n5_r_summarize.py` 会比较已经存在的哈希，但 G0 中某个必需哈希字段本身缺失时，部分路径不会 fail-closed。
- Isaac 的 model hash 缺失时还存在用 runner hash 回退的路径；runner 代码哈希不能代替模型资产哈希。

修改方法：

1. G0 JSON 必须存在且非空：URDF、MJ native、MJ matched、canonical、checker 和两类 generator 哈希。
2. 任何一个字段缺失，`g0_hash_binding` 记录明确原因，`G0=false`。
3. 删除 `model_used_sha256 or runner_sha256` 这类回退；model 缺失只能判失败。
4. trace manifest 中的 joint、canonical、model、runner 必须与当前运行逐项对应。

验收方法：

```text
复制一份合法 G0，分别删除 matched、canonical、checker 字段。
每个案例都运行正式汇总入口。
预期：每个案例均 G0=false，不能生成可解释的 PASS。
```

#### B1-F3：正式 `dance_9` runner 必须记录真实模型资产哈希

当前问题：

- 单关节 step 分支已经能记录隔离模型哈希。
- Isaac 一般基线分支的 manifest 中仍可能出现 `hashes.model=null`。
- 这不会阻塞单关节 smoke，但会破坏原计划中 `dance_9` 双引擎基线的资产可追溯性。

修改方法：

1. Isaac 正式基线记录实际加载的 URDF/USD 资产路径与 SHA256；若运行时从 URDF 转换 USD，两个哈希都记录。
2. MuJoCo 正式基线记录实际使用的 XML 路径与 SHA256，不能只记录配置文件里声明的路径。
3. 两侧记录 policy ONNX、motion NPZ、canonical contract 和 runner SHA256。
4. 启动时打印这些路径，结束时写入 manifest。

验收方法：

```text
跑 2–5 秒最短 baseline。
打开两侧 manifest，确认 policy、motion、model、canonical、runner 均为非空 SHA256。
重新在磁盘计算哈希，必须与 manifest 完全一致。
```

## 2. 下一步一：运行修复后的单关节 smoke

### 2.1 实验目的

只回答两个问题：

1. 修复后的等价隔离资产能否在 Isaac 和 MuJoCo 中稳定、可追溯地运行。
2. 新门禁和 manifest 能否正确区分合法运行、缺失资产、错误绑定和 hip no-op。

单次 smoke 不用于估计 armature 的最终效应，也不用于发表“改善百分比”的科学结论。

### 2.2 执行矩阵

只执行 6 个条件，每个条件 1 次：

| 编号 | 引擎 | 关节 | 条件 | 运行次数 |
|---|---|---|---|---:|
| S1 | Isaac | elbow | native | 1 |
| S2 | Isaac | hip | native | 1 |
| S3 | MuJoCo | elbow | native | 1 |
| S4 | MuJoCo | elbow | matched armature | 1 |
| S5 | MuJoCo | hip | native | 1 |
| S6 | MuJoCo | hip | matched no-op | 1 |

运行前逐项确认：

```text
[ ] elbow/hip 的 G0 都重新生成并 PASS
[ ] elbow native/matched 哈希不同，且差异只有目标 armature
[ ] hip native/matched 哈希相同
[ ] canonical NPZ 哈希与 G0 一致
[ ] runner、模型和 canonical 哈希均写入 manifest
[ ] 每次使用全新的输出目录，不覆盖旧结果
```

### 2.3 每条 trace 必须收集的结果

- 时间戳、policy step、physics step。
- `q_target`、`q`、`dq`。
- computed torque 和 simulator-applied torque；若某侧无法取得同语义值，明确标记 unavailable。
- root position、quaternion、linear/angular velocity。
- target joint、Kp、Kd、armature、physics dt、control dt。
- saturation 标记、接触数量和终止原因。
- 完整 manifest 及 runner/model/canonical 哈希。

至少生成：

- elbow 四条件阶跃响应叠加图。
- hip 四条件或两引擎/两模型阶跃响应叠加图。
- `q_des-q` 与 torque 曲线。
- 一张 gate 汇总 JSON/CSV。

### 2.4 smoke 的正确判定方式

单次 smoke 没有三重复，因此 G6 应当是 `NOT_EVALUATED`。这会使面向正式全量实验的 `validity_pass` 为 false，这是预期行为，不代表 smoke 失败。

smoke 继续条件必须同时满足：

```text
smoke_pass_excluding_g6 == true
G0 == PASS
G1/G1_root/G2/G3/G5 == PASS（按当前汇总器定义）
g0_hash_binding 没有缺失或不一致理由
无 NaN/Inf、无错误资产、无异常 root drift、无非目标关节漂移
hip native 与 matched 逐点完全一致
```

不能使用以下判法：

- 只看进程 `EXIT=0`。
- 要求 smoke 的 G6=PASS。
- 从一次 elbow 曲线直接报告 armature 改善百分比。

### 2.5 smoke 后的分流规则

#### 情况 A：所有硬门禁通过

不等待 N5-R2 的 18 次全量，立即转入第 3 节的 Humanoid Lab `dance_9` 基线。

#### 情况 B：G0、哈希绑定、q0、root、非目标关节或 hip no-op 失败

立即停止，不运行 `dance_9`，反馈以下最小包：

- 6 条或已完成 trace。
- G0 JSON。
- 汇总 JSON。
- 失败 run 的 manifest 和控制台日志。
- 对应曲线。

只修第一个确定的错误，不同时调整物理参数。

#### 情况 C：硬门禁通过，但 elbow 结果仍与预期相反

仍然可以继续 `dance_9` 基线。smoke 的任务是证明实验有效，不是保证 armature 一定改善。把该现象记录为后续候选问题，暂不追 frictionloss、solver、PD 时序等长支线。

## 3. 下一步二：回到原计划，完成 Humanoid Lab `dance_9` 基础配对

### 3.1 实验目的

使用同一个 ONNX、同一个 `dance_9.npz`、同一控制周期和同一初态，取得 Isaac/PhysX 与 MuJoCo 的基础端到端对比证据。

这项实验回答“默认完整栈在相同策略接口下表现有多接近”，不能单独把差异归因为 armature、solver 或接触模型。

### 3.2 第一阶段：5 秒双侧基线

先各跑 5 秒，避免一开始就花时间录制无效的 20 秒结果。

固定条件：

```text
policy: motion_anchor_obs_model_23500.onnx
motion: dance_9.npz
start_frame: 0
seed: 42
control_dt: 0.02 s
fixed_delay: 0 ms
gain_scale: 1.0
noise/push/domain_randomization: off
auto_reset: off
canonical initial state/history/default q/action scale/Kp/Kd: identical
```

执行：

1. Windows 原生 Isaac 运行 5 秒并录制视频。
2. WSL MuJoCo 运行 5 秒并录制视频。
3. 确认 observation=770、action=29、约 250 个策略周期、无 NaN/Inf。
4. 确认 manifest 的策略、动作、资产、canonical、runner 哈希完整。
5. 生成同时间轴并排视频和基础曲线。

5 秒最低产出：

- `LAB-SMOKE-ISAAC/video.mp4`
- `LAB-SMOKE-MJ/video.mp4`
- `LAB-SMOKE-SIDEBYSIDE.mp4`
- 两侧 `policy_trace.npz/csv`
- 两侧 `run_manifest.json`
- `lab_5s_comparison.csv`
- 基础曲线 PNG

### 3.3 第二阶段：优先完成 10 秒可交付基线

如果 5 秒双侧均能运行，则先把 duration 延长到 10 秒。10 秒结果已经足以作为时间不足情况下的本周基础对比交付。

只有在 10 秒结果正常且剩余时间充足时，再延长到原计划的 20 秒正式基线和 5 秒 checksum 复现检查。

优先级如下：

```text
双侧 5 秒视频+曲线
  > 双侧 10 秒可交付基线
  > 双侧 20 秒正式基线
  > 额外重复或物理消融
```

### 3.4 必须绘制的最小曲线

时间不足时也不能省略以下 4 组：

1. root height、roll、pitch。
2. 右 hip pitch、knee、ankle pitch 的 `q` 与 `q_des`。
3. right elbow pitch 的 `q`、`q_des`、raw action。
4. 代表腿关节与 elbow 的 torque；若 applied torque 语义未对齐，则分开画 computed/applied 并写明限制。

若已有可靠接触字段，再补：左右脚接触、foot slip。接触字段取不到或语义不一致时标记 unavailable，不能因此阻塞基础基线。

### 3.5 必须汇总的指标

- 是否完成动作、存活时间、首次 failure 时间与原因。
- root 高度和 roll/pitch 的范围、均值或 RMSE。
- 代表关节及身体分组的 tracking RMSE。
- `q_des-q` RMSE。
- action 一阶差分 RMS。
- torque RMS/峰值；只有 limit 和语义一致后才比较 saturation ratio。
- Isaac/MuJoCo 前 0.5–1.0 秒的短时轨迹差异。

注意：闭环轨迹明显分叉后，不要求逐帧关节完全重合，改用任务级和统计级指标。

### 6.2 本周可以形成的结论

只有证据完成后再填数值，但结论类型可以预先限定为：

1. 哪个项目的 Sim2Sim 接口最完整、最容易复现。
2. Lab 在相同策略接口下，Isaac 和 MuJoCo 的短时轨迹及端到端动作表现有何差异。
3. Gym 的轻量部署方式有什么优点和证据缺口。
4. SONIC 当前结果能支持什么，仍缺少什么验证。
5. 资产等价、joint order、初态、历史观测、PD 时序和运行证据中，哪些是 Sim2Sim 的高优先级检查项。

不能形成的结论：

- 未重跑 N5-R2 前，不能恢复“armature 改善 X%”的结论。
- 单次 smoke 不能估计稳定的因果效应。
- `dance_9` 的完整栈差异不能直接归因为某一个引擎机制。
- 不同动作、不同策略、不同证据等级的三个项目不能做性能排行榜。

### 6.3 建议总结的 Sim2Sim 经验

1. 先冻结策略接口，再研究物理差异。
2. 资产转换必须先过 FK、COM、质量、目标轴和等效惯量门禁。
3. 配置值不等于运行值，关键参数必须 runtime readback。
4. 模型、策略、动作、canonical、runner 必须全部哈希绑定。
5. 负测试必须走与正式数据相同的入口。
6. smoke、有效性门禁、重复性验证和因果实验必须分层，不能共用一个“PASS”概念。
7. 同一动作的双引擎视频和曲线是最低可复查证据，但视频不能代替数值指标。
8. 闭环轨迹分叉后应转向任务级和统计级比较。
9. 发现结果与预期相反时，先检查实验等价性，不急着调参解释。
10. 时间有限时优先保住最小完整证据链，而不是不断扩大消融矩阵。

## 9. 反馈与自动继续规则

为避免等待反馈浪费剩余时间，按以下规则执行：

1. B1 三个小修改完成后无需再发代码包审查，直接跑 isolation smoke。
2. isolation smoke 有任何硬门禁失败时立即反馈，不继续物理实验。
3. isolation smoke 全部硬门禁通过时，直接开始 Lab `dance_9` 双侧 5 秒基线；不要自动跑 N5-R2 18 次。
4. 双侧 5 秒有一侧崩溃、NaN、错误 reset、明显接口维度错误或 manifest 缺哈希时，停止并反馈。
5. 双侧 5 秒能运行但表现不同，不停止；保存视频和曲线，这本身就是需要分析的对比结果。
6. 反馈包优先包含结果和证据，不需要再次复制全部项目代码。

下一次最有价值的反馈点是：

```text
6 条件 isolation smoke 汇总
+ Lab Isaac/MuJoCo 5 秒视频与 trace
+ 两侧 manifest
+ 4 组最小曲线
+ 已填一半的三项目证据台账
```

拿到这组反馈后，再决定是否把剩余时间投入 20 秒基线、N5-R2 三重复，或直接收口周报。
