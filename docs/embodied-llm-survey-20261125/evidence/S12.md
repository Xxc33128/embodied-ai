## 01 一页看懂 HALO

HALO（Humanoid Autonomy, Learned in simulation, running Onboard）是 Apple 的人形机器人自主系统：完全用**程序化生成的仿真数据**训练出视觉-语言-动作能力，部署在 Unitree G1 上**完全机载运行**，在 6 个从未见过的真实家庭环境中 zero-shot 达到 91% 成功率。核心论断：仿真可以取代人作为数据引擎——数据量只受算力约束，不受人力约束。（E3，论文记载；91%／360 次试验／6 个环境已对摘要页核对）

| 关键数字 | 含义 | 证据 |
|---|---|---|
| 91% | 真机成功率，360 次试验 × 6 个未扫描、未见于训练的真实环境（仿真侧同为 91%） | E3；91%、360、6 已对摘要页核对，"仿真侧同为 91%"未复核 |
| 300 h | 纯合成配对数据（视频+语言+动作），162,698 条 episode，1,000 个程序化生成家庭 | E3；1,000 个家庭已对摘要页核对，并有场景清单 `datagen/common/manifests/render_scenes_1000.txt` 与 `datagen/README.md:114-115` 佐证（E2）；300 h 与 162,698 未复核 |
| 0 | 训练所用真实世界数据帧数、真机轨迹数、遥操作小时数 | E3；摘要页的表述是训练中未见真实家庭 |
| 0.5 / 3 / 50 Hz | 三层级联的运行频率（编排 → 生成 → 跟踪），全部机载（Mac mini + Jetson Orin NX） | E3，论文口径；代码侧：生成器 333 ms EDF deadline、real 模式默认 0.4 s 节流（E1，调研报告 §3.3），跟踪器控制周期 0.02 s（E2，`tracker/deploy/g1/configs/g1_v2_depth.yaml:29`） |
| 48 h × 250 H100 | 数据合成算力；generator 训练 64 × B200，tracker 训练 4 × H100 | E3；"64 GPU"与发布配置一致（E2，`generator/configs/qwen3_5_2b_dit_vision_frozen.yaml:10,25`），其余未复核 |
| 70% | 多任务链真实环境成功率（单任务 91% → 链式衰减主因：上一步结束姿态使目标出视野） | E3，未复核 |

一句话分工：**大模型管「做什么」，生成器管「怎么动」，跟踪器管「动得成」。**三层各拿一个频率、各做一种判断、各担一类误差。（E3，概括）

## 02 总体架构与数据流

系统由**机器人上三层**与**离线两模块**组成。原 html 的架构图自上而下是这样一条链（文字说明）：

1. 人的自由语言指令（例："坐到扶手椅上"）。
2. **① Orchestrator 编排器**（~0.5 Hz，Mac mini，背包）。模型是现成的 Qwen3.6-35B-A3B（MLX 4-bit，不训练；默认模型名见 `orchestrator/halo_orchestrator/interface.py:19`）；职责是把自由语言拆成子任务序列，并闭环监督——成功推进／失败重试／硬安全规则。**输出：从技能词表中选一个技能名**（hold · stand · crouch_under · push_box · follow · sidewalk · go_to_chair · sit · crawl_through · go_to_box · go_to_human）。（E2，`orchestrator/halo_orchestrator/skills.yaml:24-129`；E1，调研报告 §5）
3. ↓ **固定条件串**（如 "walk to the chair"——训练合约，一字不能改）。（E2，`skills.yaml:92`）
4. **② Motion Generator 运动生成器**（~3 Hz，Mac mini）。模型是冻结的 Qwen3.5-2B 编码器 + DiT 动作头（自训，flow matching）；职责是看一帧图、听一句话、接住当前运动惯性，画出未来 5 秒全身运动学蓝图。**输出：(150, 36) 运动规划张量**（5 s @ 30 Hz）。（E1，调研报告 §3.1）
5. ↓ **plan** 经 ZeroMQ 下发；**get_trim** 把"未来 0.5 s 将执行的部分"回灌给 ② 作前缀。（E1，调研报告 §3.3；"0.5 s"对应 15 帧 @ 30 Hz）
6. **③ Motion Tracker 跟踪器**（50 Hz，Jetson Orin NX，机器人头部）。模型是 RL 策略（自训），TensorRT FP16，C++ 实时进程（PREEMPT_RT）；职责是拿深度图 + 本体感觉把蓝图物理落地，应对计划外几何（地面坡度、未建模障碍）。**输出：(29,) 关节目标位置** → 力矩感知裁剪 → 电机侧 PD。（E1，调研报告 §4.3、§4.7；`tracker/deploy_cpp/include/rt_deploy/g1/action_decoder.hpp:68-81`）
7. 机器人真的走过去坐下；观测（RGB／深度／本体感觉）回流各层。
8. 离线支撑（图中虚线框）：**datagen** 数据引擎（不上机器人，生产全部训练数据）；**system** 的 ZeroMQ+protobuf 消息层、启动器、web 监视器（halo_serve 以 333 ms EDF deadline 实现"3 Hz"）。（E1，调研报告 §2、§6）

| 层 | 回答的问题 | 看什么 | 换代周期 | 证据 |
|---|---|---|---|---|
| ② Generator 之前 | 语义+场景 → 该做什么动作 | RGB（慢、丰富、语义） | 0.33 s（计划级） | 周期 E1（333 ms deadline，调研报告 §3.3）；其余 E3 |
| ③ Tracker | 这个动作在物理世界怎么落地 | 深度 + 本体感觉（快、精确、几何） | 0.02 s（伺服级） | E2，`g1_v2_depth.yaml:29` |
| ① Orchestrator | 自由语言 → 技能序列；成败判定 | 一帧 RGB + 文字状态包 | ~2 s（任务级） | E3；代码侧节奏由 generator 决定（每 plan 一帧 obs，E1，调研报告 §5） |

## 03 运行时三层：输入与输出

### 3.1 Orchestrator——只能「从菜单点菜」的规划监工

标签：~0.5 Hz · Mac mini · Qwen3.6-35B-A3B（现成）· `orchestrator/halo_orchestrator/`

| 输入 | 规格与说明 | 证据 |
|---|---|---|
| System prompt | 角色声明（reply ≤ 20 词、禁数字）+ 6 工具说明书 + 两条硬安全规则 + 技能目录（when_applicable / done when）+ 传感器指南。字节稳定 → KV 缓存前缀（`prompts.py`） | E1，`orchestrator/halo_orchestrator/prompts.py:88-93`（四条角色规则）、`:157`（两条硬安全规则）、`:175-180`（传感器指南）；技能目录 E2，`skills.yaml`（`crawl_through` 与 `sit` 两项的说明在 `functions.json` 叠加层里）；KV 前缀缓存 E1，调研报告 §5 |
| 图像 | **一帧**自我中心 RGB，缩放到不超过 448×280 的 JPEG（质量 88），data URL 附加。没有视频、没有深度、没有地图 | E1，`orchestrator/halo_orchestrator/interface.py:16-29`；"没有视频、深度、地图"为 E3 |
| 状态文本包 | mission 原文 + 计划清单（各步 DONE/RUNNING）+ 遥测写成英文句子（SETTLED 状态、base_height、停滞计数、下一步提示） | E3；遥测来源（generator 每个计划在 `g1/gen_status` 发布 joint_activity、subtask、plan_travel）为 E1，调研报告 §3.3 |

| 输出 | 格式（强制 JSON schema，解码层拦截非法值） | 证据 |
|---|---|---|
| T1 计划编写 | `{"reply" ≤ 400 字符, "steps"[≤ 8]: {"id", "skill" 枚举}}`——reply 排在 steps 之前（先承诺的话约束后面的计划） | E1，`orchestrator/halo_orchestrator/schemas.py:17,28,35,37`（`:28` 注明字段顺序有意义：先写 `reply` 即对计划作出承诺） |
| Agent 闭环 | `set_plan / complete_step(success) / retry_step / insert_step(skill) / ask_operator / finish_mission`，必带 `say` ≤ 120 字符 | E1，`schemas.py:58-67`（每次输出一个 `action`） |

关键约束：

- **技能名 → 训练条件串的映射表**（`skills.yaml`，拼写是训练合约）。示例按上游原文：`go_to_chair` → `"walk to the chair"`、`sit` → `"sit down on the chair"`、`crawl_through` → `"crawl under the desk"`。（E2，`skills.yaml:92,102,108`）
- living 目标禁止自行 complete（代码级强制改写）；必须站直（base_height ≥ 0.6 m）且运动 settle 才能判定完成。（E1，调研报告 §5）
- 视觉判据写进 prompt 原文：原 html 写「能俯视桌面 → crawl；桌面高过相机 → crouch」。两句都能在上游原文查到——`crawl_through` 的适用条件是"俯视桌面、能从上方清楚看到其上表面"（`orchestrator/halo_orchestrator/functions.json:19`，E2），`crouch_under` 的是"桌面与相机齐平或高于相机，不俯视其上表面"（`skills.yaml:47`，E2）。

### 3.2 Motion Generator——看图听话、直接画轨迹的生成模型

标签：~3 Hz · Mac mini · Qwen3.5-2B 冻结 + DiT 自训 · `generator/models/`

| 输入 | 规格与说明 | 证据 |
|---|---|---|
| RGB 一帧 | 224×224（全程唯一图像输入，无视频） | 分辨率 E2，`generator/configs/qwen3_5_2b_dit_vision_frozen.yaml:22`（默认值见 `generator/configs/config.py:29`）；"唯一图像输入、无视频"为 E3 |
| 技能串 | 固定字符串之一（训练条件串，改写即分布外） | E2，`skills.yaml`；E1，调研报告 §5 |
| 前缀 15 帧 | **15 帧姿态（36 维 × 15，不是图像）**：tracker 正在执行的计划中未来 0.5 s 的部分，经 `get_trim` 回灌——强制新计划从机器人当前运动状态无缝续接 | E1，调研报告 §3.2、§3.3 |

| 内部 | 两棒接力 | 证据 |
|---|---|---|
| 编码器 | 冻结 Qwen3.5-2B 一次前向 → 取末层隐状态 → 切出 **64 个图像 token + ≤ 32 个文本 token**（2048 维）→ 双投影头降到 512——"看图听话" | E1：按 vision_start／vision_end 标记切出图像 span（`generator/models/vision_language_encoder.py:223-228`）、隐层宽 2048（同文件 `:13,31`）、图像与文本双投影（`generator/models/motion_generator.py:133-139`）、64 个图像 token（调研报告 §3.1）；"≤ 32 个文本 token"未定位（E3，上游取图像 span 之后的全部 token、按批内最长 prompt 补齐，见同文件 `:396-398`） |
| DiT 动作头 | 8 层 × 512 × 8 头；150 个动作帧自注意 + 对条件 token 交叉注意；AdaLN 注入每帧噪声水平 t。flow matching：t ~ Beta(1.5,1)，15 步 Euler 从噪声积分到动作 | E1／E2：层数与头数 `generator/models/motion_decoder.py:181-182,210`，hidden_dim 与 num_heads 见 `generator/configs/qwen3_5_2b_dit_vision_frozen.yaml:46,48`，Beta 分布 `generator/training/flow_matching.py:28,53`，Euler 积分 `generator/models/motion_generator.py:290`、步数见同一配置 `:45`；其余 E1（调研报告 §3.1、§3.2） |

## 04 离线双模块：数据引擎与系统骨架

### 4.1 datagen——「无中生有」的合成数据工厂

原 html 的流程图是 a → b → c → d 四步（文字说明）：

- **a 造房间**：Infinigen 程序化生成 1,000 个房间（20–80 件家具），Blender 全局光照一次性烘焙成贴图（38 min/间）。——1,000 个场景：E2（`datagen/common/manifests/render_scenes_1000.txt`、`datagen/README.md:114-115`）；烘焙：E1（`scene_gen/scripts/bake.py`，调研报告 §2.4）；家具数与 38 min：E3，未复核
- **b 造动作**：任务拆段（文本+路径点+关键帧）喂 Kimodo 扩散模型；每段 best-of-16，几何验证器筛（30 项检查 / 21 硬，滑脚·穿板·超限）。——E1，调研报告 §2.2、§2.3
- **c 塞进房间**：占据栅格上 SE(2) 采样，整条路径无碰撞嵌入；episode = seed + placement record，与渲染解耦。——E1，调研报告 §2.1、§2.4
- **d 渲染视频**：头置鱼眼相机逐帧回放，域随机化（曝光/色温/运动模糊/噪声…）；LeRobot 格式落盘。——E1，调研报告 §2.4、§2.5

产量：300 h / 162,698 episodes，48 h × 250 H100，全程零人工。（E3，论文，未复核）注：过滤为**软过滤**——best-of-N 全败仍保留最高分一条（硬通过率 77.3%，tracker 只吃通过子集）；开源版仅含 SIT 任务入口。（E1，调研报告 §2.3、§0.1）

## 07 设计哲学：与经典 VLA 的分野

本节是原作者的解读，整体 E3；括注处给出所依据的代码事实。

| 维度 | 经典 VLA（π0 / OpenVLA 一族） | HALO |
|---|---|---|
| 「去哪」的决策者 | 模型输出坐标 / bbox / 末端 waypoint 等显式符号 | **无显式坐标**：orchestrator 的输出里没有数值字段（E1，`schemas.py:12-18,58-67`，计划步只有 `id` 与 `skill` 枚举）；空间信息以图像特征 → 150×36 连续轨迹直通（yaw-only gauge 里的位移列即"坐标"，E1，调研报告 §3.1） |
| 接口带宽匹配 | 单一端到端 | LLM→VLA 接口是低带宽高可靠的**符号**（从技能词表选一，11 选 1）；VLA→tracker 接口是高带宽平滑的**轨迹** |
| 技能词汇表 | 开放（schema 随手加，零样本泛化） | **封闭**：加一个技能 = 人工写 prompt+关键帧 → 造数据 → 重训（以周计；"论文自述头号局限"未复核） |
| 数据经济学 | 依赖真实遥操作/动捕配对数据 | 把语言理解从 VLA 训练目标中剥离 → 条件串集合封闭 → **纯合成数据路线可行** |
| 参照系 | HomeBody = 大脑（GPT Astra）+ 经典解析技能——「显式坐标」路线 | HALO = 小脑（本地 35B）+ 学习技能——「隐式轨迹」路线；两者互为对方主要局限的解药 |

值得记住的一句：整个系统**没有用到一帧真实世界数据、一条真机轨迹**——真机能力全部来自「程序化仿真 + 域随机化 + 执行器建模」的迁移设计，这正是标题里 *from Simulation* 的含义，也是复现时最该验证的主张。（E3，论文；摘要页的表述是训练中未见真实家庭）

三个直接结论：

1. **Infinigen（datagen step1）只能放在大内存节点**：它需约 60 GB RAM（E2，`datagen/README.md:23`），GPU 机的 31 GB 不够。
2. **GPU 机的磁盘约束已解决**（11-13 清理后数据盘余 146 GB、系统盘余 9.2 GB）；HALO 环境建在数据盘，不往系统盘装大件。
3. **昇腾实际可用 = 2 卡**；被占用的卡将来若能释放，可作可选提速，不纳入基线计划。

### 分工要点

原则是**数据本地性**：datagen 全链（场景／运动／渲染）在昇腾节点本地闭环，GPU 机只接收小体积产物（tracker 的 npz clips），避免大数据跨机。

| 任务 | 放哪 | 依据 |
|---|---|---|
| datagen step1 场景（Infinigen + bake） | 大内存节点 CPU（多进程并行 5–10 个场景） | 约 60 GB RAM 硬需求（E2，`datagen/README.md`）；Cycles 可走 CPU 渲染 |
| datagen step2 运动（Kimodo，约 17.5 GB 权重，官方实测 80 GB 卡） | 昇腾 2 卡（最大的移植攻关点，见风险 R2） | 三段链里的文本编码（Llama-3-8B + 2 × LLM2Vec）与节点上既有编码服务同构；三模型跨 2 卡放得下（E3 估算） |
| datagen step3 渲染 | 大内存节点 CPU，MuJoCo 后端保底；Isaac 后端在 T4 上作可选质量升级 | 仓库自带 MuJoCo CPU 变体（E1，调研报告 §2.4）；不占用 T4 的训练时段 |
| generator 训练（frozen 配置：只训 DiT + projections） | 昇腾 2 卡，torch_npu DDP | encoder 仅 forward，绕开线性注意力 backward 缺 flash-linear-attention 的坑（E1，调研报告 §7.10）；节点上有 910B3 上 transformers 训练的既有经验 |
| orchestrator LLM | 昇腾节点上起一个中型 Qwen | 接口是 OpenAI chat 形状、官方明示可换后端（E1，调研报告 §5）；论文的 35B MLX 是真机配置，闭环演示规模可缩小 |
| tracker 三阶段训练（Isaac Lab 2.3.2，须 NVIDIA） | T4，`--num_envs` 缩减（8192 → 1024–2048），`--max_iterations` 相应调整 | Isaac Sim／PhysX 无 NPU 版本；CLI 可覆盖 `--num_envs` 与 `--max_iterations`（E1，`tracker/training/scripts/rsl_rl/train.py:30,153-154`）；16 GB 显存是 env 数上限的约束（E3，冒烟时标定） |
| tracker ONNX 导出 + generator 开环 eval | T4 | 走 CUDA 环境最稳 |
| `run_sim.py` 闭环联调 | 首选昇腾节点单机（CPU MuJoCo + 卡上 generator 推理 + vLLM orchestrator + onnxruntime CPU tracker）；备选 Mac（MPS 回退，仅 debug） | 单机闭环免去跨机通信 |
| 文档／代码审查 | Mac | 既有角色不变 |
