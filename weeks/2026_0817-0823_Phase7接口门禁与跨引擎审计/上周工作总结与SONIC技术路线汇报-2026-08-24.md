## 0. 核心结论

上周的主要任务是搭建 GR00T/SONIC 所需的 Isaac 环境。经过 WSL、Windows Isaac 4.5 和 Windows Isaac 5.1 三条路线的排查，最终形成了一套能够稳定启动、加载 G1、运行物理仿真、执行数据采集和训练入口冒烟的 Windows Isaac 5.1 环境，同时保留 WSL 侧的 MuJoCo、TensorRT 和部署链路。

在完成环境搭建后，我进一步做了三类探索：

1. 参考已有方法，在新环境中复现关节阶跃与正弦响应测试；
2. 尝试建立 Isaac–MuJoCo 的模型审计和控制接口门禁；
3. 结合资料调研，整理了一套 18-case 分层物理验证方案。

这些探索说明新环境已经具备进一步实验的基础，但目前不能宣称 Isaac 与 MuJoCo 已完成物理对齐。团队已有其他对齐实验正在进行，后续方向需要在本次汇报后与 MT 进一步讨论。

### 1.1 上周的主要任务

### 1.2 为什么同时涉及 Isaac 和 MuJoCo

SONIC 是 G1 的全身控制器，上层可以输入运动令牌、人体动作或遥操作目标，下层输出 29 个关节的控制动作。

当前项目的资源条件更适合采用分工模式：

```text
运动数据 → MuJoCo/CPU 采样 → NPU 训练候选策略
                                  │
                                  └─→ Isaac/GPU 做参考验证与问题定位
```

- MuJoCo 更轻量，适合持续采样、部署准备和训练侧工作；
- Isaac/PhysX 与官方训练环境更接近，适合参考验证；
- 两个引擎不是简单的参数一一对应关系，需要先排除接口问题，再讨论物理差异。

## 2. 环境搭建路线

### 2.1 WSL：先跑通 MuJoCo 和部署链路

在 WSL2 Ubuntu 22.04 中完成了：

- MuJoCo 3.2.7 仿真；
- TensorRT 10.13 与 C++ 部署程序编译；
- Unitree SDK、CycloneDDS 和相关符号链接修复；
- `run_sim_loop.py` 与 `deploy.sh sim` 双进程联调；
- G1 模型加载策略并播放动作。

这一阶段证明 MuJoCo 与部署链路可以工作，但 WSL 无法可靠提供 Isaac 所需的 RTX/Vulkan 图形能力。

### 2.2 WSL Isaac：确认路线不可行

虽然在 WSL 中完成了 Python、Isaac Sim、Isaac Lab、PyTorch 和 CUDA 依赖组合，但 Isaac RTX 初始化仍依赖当前 WSL 无法稳定提供的 Vulkan/图形路径。

最终没有继续在 WSL 中反复降级和补包，而是将平台职责拆开：

- WSL：MuJoCo、TensorRT、ROS 和部署；
- Windows：Isaac Sim、Isaac Lab 和 PhysX；
- Mac：代码整理、审计、文档和轻量测试。

### 2.3 Windows Isaac 4.5：依赖修复后仍失败

Windows 4.5 路线中处理了：

- RTX 5060 对 CUDA 12.8/PyTorch wheel 的要求；
- torch nightly 的 `torch.jit`、`c10.dll` 等兼容问题；
- NumPy 2.x 与 Isaac Sim 的冲突；
- Isaac 自带旧 VC++ runtime 遮蔽系统新版 DLL 的问题。

依赖层修复后，Kit 106.5 仍在 `rtx.scenedb.plugin.dll` 中确定性崩溃，因此停止继续修补 4.5。

### 2.4 Windows Isaac 5.1：形成稳定环境

切换到 Isaac Sim 5.1 后，通过隔离实验发现，4.5 和 5.1 的共同崩溃点不在项目代码，而在宿主图形环境。

最终解决组合为：

1. NVIDIA 驱动从 610.88 回退到 580.88；
2. 禁用 Parsec 和 MuMu 虚拟显示适配器；
3. 清理约 10.6 GB CrashDumps，恢复系统盘空间；
4. Windows headless 入口显式固定 D3D12；
5. 通过环境变量接受 EULA。

修复后，原 smoke 脚本在不修改业务逻辑的情况下通过：应用约 32 秒 ready，100 个物理步正常完成。

## 3. 关键问题、定位过程与解决方法

### 3.1 最关键问题：RTX 渲染器确定性崩溃

**现象：** Isaac 4.5 和 5.1 都在创建 World/PhysX 之前，于 RTX/Hydra 初始化阶段发生固定位置的 access violation；GUI、headless 和不同 experience 均可复现。

**排查方法：**先后排除项目代码、Isaac 版本、TLAS 参数、CUDA interop、Storm 渲染器和 VC DLL 等因素，最后保持脚本不变，只改变驱动与虚拟显示环境。

**结果：**驱动回退并禁用虚拟显示后，原脚本直接通过。这个对照实验把问题从“Isaac 代码异常”收敛为“宿主驱动和显示栈兼容问题”。

### 3.2 版本兼容矩阵

RTX 5060、Isaac Sim、Isaac Lab、Python ABI、PyTorch、CUDA 和 NumPy 之间存在强耦合。最终冻结组合为：

| 组件 | 冻结状态 |
|---|---|
| Isaac Sim | 5.1.0.0 |
| PhysX | 107.3.26 |
| Isaac Lab | distribution 0.48.0；源码 commit `5c2ec81` |
| Python | 3.11.9 |
| PyTorch | 2.7.0+cu128 |
| NumPy | 1.26.0 |
| GPU/驱动 | RTX 5060 Laptop 8 GB / 580.88 |
| 渲染后端 | D3D12 |

经验是：不能简单安装“最新版”，大包安装后需要重新核对 NumPy、Torch build tag、Python ABI 和 Isaac pin。

### 3.3 Headless、URDF importer 与程序退出

- Windows headless 若被切换到 Vulkan，URDF importer 会在原生 C++ 调用处静默挂起；解决方法是所有入口显式固定 D3D12。
- EULA 交互无法稳定通过后台管道输入；改为环境变量统一接受。
- `simulation_app.close()` 可能在 Windows 收尾阶段挂死；采集脚本改为先原子落盘 JSON/NPZ，再限时关闭。
- 使用 `py-spy` 抓取挂起栈，比单纯降低日志级别更容易定位原生死锁。

### 3.4 其他工程问题

| 问题 | 处理方式 |
|---|---|
| WSL Vulkan 不可用 | 停止 WSL Isaac 路线，转向 Windows 原生 |
| Isaac 5.1 URDF collider 导入为 0 | 个人探索版中取消 instanceable，解析 URDF 并重新生成 primitive colliders |
| MuJoCo 新版本拒绝全局重名 | 修改地面、纹理和材质重名 |
| Windows CRLF 导致资产哈希变化 | 文本资产哈希前统一换行 |
| 16 GB 内存和系统盘不足 | Git/LFS 串行、单 Kit 运行、缓存迁移、定期清理 CrashDumps |
| 国内网络与 PyTorch wheel 来源不同 | 普通包、Hugging Face 和 cu128 wheel 分别使用合适来源，安装后核验 |

## 4. 环境跑通后的验证结果

### 4.1 运行能力验证

当前环境已经确认能够完成：

- Isaac Sim/Isaac Lab 正常启动和物理步运行；
- G1 模型加载、运行时模型导出和数据采集；
- `sonic_release/last.pt` 发布 checkpoint 的加载与接口采集；
- Windows 训练入口的短时冒烟；
- MuJoCo、TensorRT 和部署链路在 WSL 中运行。

需要保留一个边界：现有 artifacts 能证明发布 checkpoint 被加载并产生策略接口数据，但不足以证明已经完成稳定的闭环动作回放，因此本次不把“官方策略稳定复现”列为已完成结论。

### 4.2 训练入口容量扫描

在 RTX 5060 Laptop 8 GB 上，对 4–2048 env 做了短时冒烟，每档均完成 5 iteration 并正常退出。

| env 数 | 吞吐 steps/s | 观察 |
|---:|---:|---|
| 4 | 35–39 | 最小可用档；1 env 不满足 4 mini-batch 整除要求 |
| 128 | 832–1159 | 已具备可用并行能力 |
| 256 | 1450–2137 | 适合日常调试 |
| 512 | 2805–3690 | 性能与资源较平衡 |
| 1024 | 4460–5652 | 当前机器的高吞吐档 |
| 2048 | 746–998 | 显存约 7.44/8.15 GB，吞吐反而下降，接近临界 |

这个实验的结论不是“完成训练”，而是确定了当前硬件的可用范围：256–512 env 适合日常调试，1024 env 可用于短时高吞吐测试，2048 env 不适合作为常规配置。

## 5. 参考复现：P1 关节动态响应

### 5.1 实验定位

P1 不是我独立提出的新方法，而是参考已有验证思路，在本人搭建的 Windows Isaac 5.1 环境中重新运行。

实验在固定基座条件下选择左髋俯仰、左膝和左踝俯仰三个代表性关节：

- 阶跃：正负方向，幅值 0.05、0.1、0.2 rad，共 18 组；
- 正弦：0.5、2、5 Hz，共 9 组；
- 总计 27 组 NPZ；
- 记录关节位置、速度、目标、施加力矩、root 漂移和其他锁定关节漂移。

### 5.2 从 artifacts 复算的结果

阶跃结果：

| 关节 | 90% 响应时间 | 典型超调 | 观察 |
|---|---:|---:|---|
| 左髋俯仰 | 约 45 ms | 约 10.5% | 超调和关节耦合最明显 |
| 左膝 | 约 35 ms | 约 1% | 响应快、超调较小 |
| 左踝俯仰 | 约 35–40 ms | 接近 0 | 阶跃跟随较平稳 |

正弦结果：

| 关节 | 0.5 Hz | 2 Hz | 5 Hz |
|---|---|---|---|
| 左髋俯仰 | 增益 1.007，近零相位差 | 增益 1.029，滞后约 10.2° | 增益 1.005，滞后约 36.8° |
| 左膝 | 增益 0.997，近零相位差 | 增益 0.991，滞后约 9.7° | 增益 0.936，滞后约 24.6° |
| 左踝俯仰 | 增益 1.006，近零相位差 | 增益 0.984，滞后约 9.6° | 增益 0.909，滞后约 22.7° |

初步观察：低频目标基本可以跟随；频率升高后出现明显相位滞后；不同关节的超调、带宽和耦合程度不同。0.2 rad 髋关节阶跃中，其他锁定关节最大漂移约 0.052 rad，是后续执行器或约束对比中值得关注的现象。

当前 P1 仍是 Isaac 单引擎预基线，尚未与 MuJoCo 运行同条件成对实验，不能据此得出两个引擎谁更准确。

## 6. 个人探索：模型与接口测量工具

### 6.1 运行时模型审计

个人探索版实现了 Isaac/MuJoCo runtime exporter、29-DoF canonical mapping 和参数 diff。

当前审计结果：

| 项目 | Isaac | MuJoCo |
|---|---:|---:|
| Bodies | 30 | 30 |
| Joints | 29 | 29 |
| Actuators | 29 | 29 |
| Colliders | 54 | 40 |
| Physics dt | 0.005 s | 0.002 s |
| Decimation | 4 | 10 |
| Control dt | 0.02 s | 0.02 s |

参数审计得到 615 项相同、830 项不同、1807 项缺失、4 项未映射。该计数受碰撞字段和引擎特有参数影响，不能解释成“对齐率”；其价值是把原本隐藏在 USD/URDF/MJCF 和运行时对象中的差异显式列出来。

### 6.2 collider 修复探索

Isaac 5.1 导入后最初出现 collider 数量为 0。个人探索版通过取消相关 prim 的 instanceable 状态、解析同一 URDF 并重新 author primitive collider，使 collider 增加到 54。

环境冻结 sanity 中：

- 显式 PD 和 implicit drive 两条路径的最低 root z 均约 0.064 m；
- 前向和俯仰扰动下最低 root z 分别约 0.077 m 和 0.075 m；
- observation NaN 数为 0。

但 18 个手部 mesh collider 尚未补齐，该实现仍属于个人探索版本，不能表述为团队正式资产修复方案。

### 6.3 100-state 控制接口门禁

门禁的思路是：给两个引擎完全相同的 100 组状态，在进入物理仿真前比较控制链：

```text
observation/history
→ policy action
→ clipped/canonical action
→ joint target
→ applied torque
```

现有 artifacts 中：

- 100 帧、930 维 actor observation；
- 14/14 exact check 通过；
- 12/12 numeric block 通过；
- 当前保存的 observation、action、target 和 torque 数值差异均为 0；
- checkpoint、motion 和 state-set 的 SHA-256 在两侧一致。

这一结果只能称为“个人门禁工具的初步验证”。原因包括：

1. 采集 NPZ metadata 对应较早提交 `dd0b6b2`，最终 fingerprint 对应 `45ed748`；
2. 两侧控制字段精确相等，需要继续警惕共享公式造成的循环验证；
3. 团队正在用真实策略运行链做独立的 observation/action 对比，项目级接口结论尚未收口。

因此，本次不表述为“项目已经证明 Isaac 与 MuJoCo 接口完全一致”。

### 6.4 MuJoCo joint-step runner smoke

MuJoCo 侧 6 个代表性关节的 runner 已成功产生 4500 步 trace，说明 case 生成、资产指纹、数据记录和指标汇总链路能够工作。

但 smoke 中仍观察到需要复核的指标，例如部分关节 rise time/settling time 为空、踝关节稳态误差较大、最大 penetration 约 6.9 mm。因此它只能证明 runner 可运行，不能作为物理效果已经合格的证据。

## 7. 对齐方案：作为讨论备选，不作为既定路线

### 7.1 为什么要分层验证

同一个策略在第二个引擎中失效，可能来自：

- observation、history 或关节顺序不同；
- action scale、PD、力矩限制或控制周期不同；
- 质量、惯量和质心不同；
- 碰撞几何、摩擦或接触求解器不同；
- 策略本身绑定训练引擎。

如果前几层没有排除，直接调摩擦会把接口错误吸收到物理参数中。

### 7.2 个人整理的 18-case 框架

```text
6 个 joint-step
  → 隔离控制时序、PD、armature 和关节响应

4 个 zero-torque free-fall
  → 隔离重力、质量、惯量、碰撞和触地时刻

8 个 fixed-PD landing
  → 观察接触冲量、穿透、滑移、root motion 和力矩饱和
```

已整理 13 个 fit case 和 5 个 holdout case。第一轮保持 Maxwell MuJoCo 参数不变，只建立成对基线；取得数据后，再按时序、刚体、执行器、碰撞几何、材料和 solver 的顺序逐族分析。

当前状态：用例、指标和 MuJoCo runner 已准备，Isaac adapter probe 已做过基础检查，但完整 Isaac benchmark CLI 仍有挂起，18-case 双引擎数据尚未取得，物理参数修改量仍为 0。

## 8. 相关方案调研

本节重点不是罗列相关工作，而是回答两个问题：其他项目具体怎样实现跨仿真或仿真到真实迁移，以及其中哪些做法能够转化为当前项目的工程步骤。现场汇报可以只讲 8.1 的对比表和 8.8 的参考顺序，其余内容作为 MT 追问时的展开材料。

### 8.1 路线对比

| 参考项目 | 实现路线 | 主要解决的问题 | 对本项目最有价值的部分 |
|---|---|---|---|
| SONIC 官方 sim2sim | Isaac Lab 训练，导出 encoder/decoder ONNX；独立 C++ 真机部署栈通过通信接口连接 MuJoCo 进程 | 完整部署和通信链在进入真机前能否工作 | 复用真实部署代码，将官方物理环境作为基线 |
| MuJoCo Playground | MJX/MuJoCo Warp 批量训练，原生 MuJoCo 独立评测 | 减少训练与部署之间的模型转换 | 共享模型和任务配置，训练与确定性评测分离 |
| Humanoid-Gym | Isaac Gym 训练并导出单体 JIT；Python `sim2sim.py` 直接在 MuJoCo 内重建观测、动作缩放和 PD | 检查策略能否跨引擎零样本运行 | 借鉴轻量策略适配器和第二引擎门禁 |
| Isaac Lab PhysX↔Newton | 同一任务配置选择不同后端，双向训练和播放 | 系统地区分任务、接口和求解器差异 | 完整的任务契约检查表和 2×2 评测矩阵 |
| Legged-Gym | 执行器模型、物理随机化、观测噪声和外部扰动 | 提高策略对模型误差的容忍度 | 在标称模型可信后逐项加入随机化 |
| ASAP | 用目标域轨迹学习增量动作，再在补偿后的源域微调策略 | 处理显式参数难以表达的稳定残差 | 成对数据闭环后的数据驱动补偿方案 |

这些方案不是同一层次的替代关系。SONIC、Humanoid-Gym 和 Isaac Lab 主要提供跨引擎验证方式；MuJoCo Playground 通过统一生态减少差异来源；Legged-Gym 通过随机化增强鲁棒性；ASAP 处理常规建模后仍然存在的残差。

### 8.2 SONIC 官方 sim2sim：复用真实部署链

[GR00T-WholeBodyControl 官方 quickstart](https://github.com/NVlabs/GR00T-WholeBodyControl/blob/main/docs/source/getting_started/quickstart.md) 将仿真和控制拆成两个进程：

```text
MuJoCo 仿真进程 `run_sim_loop.py`
        ↕ 状态与控制命令
C++ 部署进程 `deploy.sh sim`
        → 加载 ONNX、构造观测、输出关节命令
```

官方当前的 G1 sim2sim 是 29 维全身策略。仓库中的旧 15 维链路只是“腿部 12 维 + 腰部 3 维”的历史控制器，上肢由固定 PD 保持，不能与当前 release 混用。本地核验也确认：官方 decoder 输入为 64 维 token 加 930 维本体观测，最终输出 29 维 action；同事使用的 `last.pt` 与官方 release 文件一致。

官方 MuJoCo 物理环境可以直接复用，应作为第一候选基线。它已经给出质量、惯量、碰撞几何、关节限位、力矩范围、被动关节参数、地面摩擦、物理步长和分关节 PD。当前 alignment runner 并未原样使用这套配置：

| 项目 | 官方 sim2sim | 当前 alignment/Maxwell |
|---|---|---|
| 入口模型 | `scene_43dof.xml`，包含 29 个 body joints 和手部 | `scene_29dof_alignment.xml`，仅 29 个 body joints |
| Physics dt | 0.005 s | 0.002 s |
| 地面摩擦 | 1.0 | `0.5 0.005 0.0001` |
| 被动参数和 PD | MJCF 默认值 + 官方 `MOTOR_KP/MOTOR_KD` | 覆盖 per-joint armature，并重新计算 stiffness/damping |
| Solver | 未见相同显式覆盖 | `impratio=30`、iterations=200 |

因此建议保留两条独立基线：`M0-official` 原样运行官方 scene、MJCF、WBC 配置和 runtime 行为；`M1-current` 保留现有 Maxwell/alignment 修改。先在相同 case 上比较 M0、M1 与 Isaac，再决定是否调整参数。官方配置能证明其部署链可用，但不能直接证明与 PhysX 等价。

### 8.3 MuJoCo Playground：通过统一生态减少转换边界

#### 其他项目如何实现

[MuJoCo Playground](https://github.com/google-deepmind/mujoco_playground) 以 MuJoCo 模型和任务定义为中心，支持 MJX/JAX 和 MuJoCo Warp 上的大规模并行训练，并保留原生 MuJoCo 运行器用于可视化和评测：

```text
同一套 MJCF、任务配置和随机化定义
        ├─→ MJX / MuJoCo Warp：批量采样和 PPO 训练
        └─→ Native MuJoCo：独立回放和确定性评测
```

其训练入口将 observation normalization、action repeat、episode length、随机种子和 domain randomization 显式配置。这样做并不保证 MJX、Warp 和原生 MuJoCo 逐位一致，但由于它们共享模型语义和任务结构，需要人工对齐的边界少于 Isaac–MuJoCo。

#### 对当前项目的启发

- 若后续主训练长期位于 MuJoCo，可以让 MuJoCo 成为资产、动作定义和评测协议的主来源，Isaac 只承担外部抽检；
- 训练 runner 与确定性 benchmark runner 应分开：前者追求吞吐，后者固定随机种子、初始状态和日志字段；
- 标称配置和随机化配置必须同时保留，避免策略虽然在随机化中存活，却无法解释标称模型的误差；
- 可借鉴其配置组织方法，但 JAX/MJX/Warp 依赖的 NVIDIA GPU 训练路径不能直接搬到当前“CPU MuJoCo 采样 + NPU 更新”架构。

### 8.4 Humanoid-Gym：把第二引擎作为部署前门禁

#### 其他项目如何实现

[Humanoid-Gym](https://github.com/roboterax/humanoid-gym) 在 Isaac Gym 中训练 PPO，先通过 `play.py` 导出 JIT 策略，再由单独的 `sim2sim.py` 在 MuJoCo 中执行：

```text
Isaac Gym PPO checkpoint
        → 导出 JIT policy
        → MuJoCo 加载 MJCF
        → 重建 observation 与多帧 history
        → 关节重排、action scale、PD 和控制周期
        → 检查站立、步态与命令跟踪
```

它要求为新机器人显式处理 URDF/MJCF 关节映射和默认关节位置。其默认低层策略使用多帧观测，说明 history 的拼接顺序和重置方式也是部署契约的一部分。MuJoCo 在这里主要是一个与训练环境独立的部署验证器，而不是通过成对轨迹拟合出来的 PhysX 克隆。

#### 对当前项目的启发

- MuJoCo checkpoint 进入 Isaac 后如果快速失效，应先按“接口契约失败”处理，而不是马上调摩擦；
- 最小检查表应包括关节顺序、默认姿态、observation 字段/单位/坐标系、history、action scale、裁剪、PD、力矩限制和控制周期；
- 建议为每个 checkpoint 固化一份 machine-readable manifest，记录模型哈希、关节表、观测维度、归一化和时序；
- 第二引擎首先应作为门禁：判断能否站立、能否存活、能否跟随简单命令。通过后才适合分析更细的轨迹差异。

### 8.5 Isaac Lab PhysX↔Newton：冻结同一个任务契约

#### 其他项目如何实现

[Isaac Lab 官方迁移指南](https://isaac-sim.github.io/IsaacLab/develop/source/how-to/transfer_policies_between_physx_and_newton.html) 允许同一个注册任务通过 physics preset 选择 PhysX 或 Newton/MJWarp 后端。后端可以拥有不同的求解器预设，但不能静默改变策略面对的任务。

官方要求逐项核对：

1. **Actions：**项顺序、关节/刚体顺序、维度、目标类型、scale、offset 和 clipping；
2. **Observations：**字段顺序、宽度、history、单位、坐标系、噪声和 clipping；
3. **Policy state：**归一化统计量、RNN 状态、重置、命令和 actor 使用的输入；
4. **Timing：**physics `dt`、decimation、策略周期和 action-hold；
5. **Mechanism：**活动 DoF、关节/刚体顺序、mimic 或 equality constraint；
6. **Episode：**reset、命令分布、termination、horizon 和 success definition。

其目标是相似的任务行为，而不是逐帧或逐位相同的轨迹。官方还建议完成全部训练—播放组合，而不是只看一个迁移方向：

| 训练后端 | 播放后端 | 本项目对应含义 |
|---|---|---|
| MuJoCo | MuJoCo | MM：本地 checkpoint 的源域基线 |
| MuJoCo | Isaac | MI：本地 checkpoint 的跨引擎结果 |
| Isaac | Isaac | II：Isaac checkpoint 的源域基线 |
| Isaac | MuJoCo | IM：Isaac checkpoint 的反向迁移结果 |

#### 对当前项目的启发

- 把 action、observation、policy state、timing、mechanism 和 episode 六类内容整理成正式接口清单；
- 100-state gate 对应其中的接口层，但还需要真实策略闭环和 episode 层验证；
- 尽可能完成 MM/MI/II/IM 四格，才能区分“任务本身有问题”“只有单向接口成立”和“策略绑定求解器”；
- 不要求 Isaac 与 MuJoCo 的 contact force 逐点完全相同，应比较任务行为和可解释的隔离指标。

### 8.6 Legged-Gym：用域随机化提高容错，而不是掩盖错误

#### 其他项目如何实现

[Legged-Gym](https://github.com/leggedrobotics/legged_gym) 的 sim-to-real 方案包含 actuator network、摩擦与质量随机化、观测噪声和随机外力。训练时，策略看到的不是单一精确模型，而是围绕标称模型的一组可能系统，因此对真实执行器、接触和传感误差更不敏感。

典型实现可以理解为：

```text
可信的标称机器人模型
        → 随机质量、质心、摩擦和执行器响应
        → 加入观测噪声、延迟或随机推力
        → 在分布内训练策略
        → 在未见过的标称条件和扰动条件上评测
```

#### 对当前项目的启发

- 域随机化不是 Isaac–MuJoCo 参数对齐的替代品；如果关节顺序或 action scale 错了，扩大摩擦范围只会掩盖问题；
- 可以在 18-case 得到基线后，根据两侧实测差异给随机化范围，而不是凭经验给很宽的区间；
- 建议按参数族逐步加入：先质量/质心，再执行器增益与延迟，再摩擦/恢复系数，最后加入传感噪声和扰动；
- 每增加一类随机化，都保留标称 case 和 holdout case，观察鲁棒性提升是否伴随跟踪精度明显下降。

### 8.7 ASAP：用目标域轨迹学习剩余差异

#### 其他项目如何实现

[ASAP 论文](https://arxiv.org/abs/2502.01143) 不要求先找到一组能够完全解释目标域的物理参数，而是在基础策略已经可以运行后采集目标域状态—动作轨迹，再学习增量动作模型：

```text
源域预训练 motion-tracking policy
        → 在目标域运行并采集状态—动作—下一状态
        → 在源域重放相同状态和动作
        → 学习 Δa = πΔ(s, a)，缩小下一状态残差
        → 将 Δa 放入源域，微调基础策略
        → 最终部署微调后的基础策略
```

它吸收的是质量、柔顺性、延迟、接触等显式模型难以完整表达的综合残差。增量模型主要用于构造更接近目标域的训练环境，最终目标不是在部署端永久串联一个补丁控制器。

#### 对当前项目的启发

- 可以把 MuJoCo 作为源域、Isaac 作为目标域，用 Isaac 成对轨迹学习 MuJoCo 侧的残差补偿，但这是基于论文方法的工程外推，并非项目已经验证的结论；
- 启动前提是接口 gate、资产版本、初始状态、时间戳和 checkpoint provenance 全部闭环；
- 必须划分 fit motion 与 holdout motion，只有未参与拟合的动作也改善，才能说明模型学到了可泛化残差；
- 当前阶段不宜直接采用：如果目标轨迹中仍混有关节映射或 history 错误，增量模型会把接口错误一起学进去。

### 8.8 可转化为本项目的参考顺序

综合以上方案，可以得到一条由低风险到高复杂度的路线：

```text
G0  以 SONIC 官方 sim2sim 为部署参考，冻结资产、checkpoint 和配置版本
 ↓
G1  借鉴 Humanoid-Gym/Isaac Lab，核对 observation、action、history、关节顺序和时序
 ↓
G2  建立 MM / MI / II / IM 四格策略基线
 ↓
G3  用 joint-step、free-fall、PD-landing 取得可归因的成对物理数据
 ↓
G4  只调整质量、惯量、PD、armature、摩擦等可解释参数族
 ↓
G5  参考 Legged-Gym，按实测差异设计域随机化，并检查 holdout
 ↓
G6  仍有稳定、可重复残差时，再评估 ASAP 式增量动作模型
```

当前可以直接复用的是 G0–G2 的工程方法，以及 G3 的小型隔离实验。G4 需要完整的双引擎数据，G5 需要可信的参数范围，G6 还需要稳定的成对轨迹。因此，参考项目没有给出一套可复制的“PhysX 参数转 MuJoCo 参数”，但给出了清晰的决策顺序：先减少和检查接口边界，再获得可解释数据，最后才使用随机化或数据驱动补偿。
