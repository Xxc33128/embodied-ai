# RPent 更换 LLM 与启动测试指南

更新：2026-10-09。适用：现有远程 Linux / NPU 环境，不在 Mac 上跑仿真。

## 1. 用哪个适配套件？

**直接用 RPent 自带的 `api` planner。它基于 PydanticAI，把同一套机器人工具接到不同 LLM。** 换模型通常只需改 provider 前缀、model ID、API 地址、凭据和推理档位，不需要改 π0.5、SAM3 或仿真。〔E1：S1、S2〕

调用链：

```text
其他 LLM API
    ↕ PydanticAI：消息、图像、tool calling、usage
RPent ApiAgentLoop
    ↕ 同一 Toolkit：观察、定位、动作、记忆、finish
π0.5 + SAM3 + LIBERO / MuJoCo
```

| 模型提供的协议 | `--model` 写法 | 凭据变量 | 说明 |
|---|---|---|---|
| OpenAI-compatible Chat Completions | `openai-chat:实际模型ID` | `OPENAI_API_KEY` | 适合提供此协议的模型网关或本地服务；兼容程度要测试 |
| OpenAI Responses | `openai-responses:实际模型ID` | `OPENAI_API_KEY` | 服务必须实现 Responses；不要拿 Chat-only 地址接它 |
| Anthropic Messages | `anthropic:实际模型ID` | `ANTHROPIC_API_KEY` | 服务须支持对应的消息、工具与图片格式 |

当前安装版本中，`openai:` 也路由到 Responses；建议写明 `openai-chat:` 或 `openai-responses:`，避免协议混淆。品牌名不能决定协议，模型 ID 必须以服务端实际部署为准。这里不假定任何具体第三方模型都能直接运行。〔E1：S1、S7〕

**边界：这是一份已核对源码与 CLI 的接入指南，不是新模型验收报告。** 本次没有提交付费模型请求，也没有启动新 episode。普通 API 入口不会自动生成此前深测的全部计时字段。

## 2. 先选对比较方式

- **只想知道新模型能否跑通 RPent：** 按第 3–6 节做单集接入测试，可以暂时使用已分配的 π / SAM 服务。
- **想比较模型能力或速度：** 基线模型和新模型都使用同一 `api` planner 重跑。原 Codex 120 集与 8 集深测只作历史参考，不直接混算为“只换了模型”的对照。

原因：Codex SDK 与 API planner 的默认指令、会话管理、工具封装和结束行为不同。API planner 当前还会裁剪历史图片：累计图片字节预算 4 MiB，至少保留最近两张；Anthropic 分支会请求 prompt caching。它们都会影响输入和时长。〔E1：S2〕

同名 `medium` 也不代表不同厂商投入了相同推理预算。比较“产品效果”时记录各自有效档位；比较档位影响时，应在同一个模型上做 `low / medium` 对照。〔E3：实验设计〕

## 3. 进入现有环境，配置新模型

### 3.1 进入容器

在 Mac 终端执行：

```bash
ssh "$RPENT_SSH_HOST"
docker exec -it rpent-npu bash
```

以下命令都在**容器内的 Bash** 执行。`RPENT_SSH_HOST` 由使用者在本机设置为自己的 SSH 别名；`RPENT_DATA_ROOT` 在容器内设置为实验工作根目录。公开版不提供机器地址、实际目录或凭据位置。

```bash
set +x
umask 077
: "${RPENT_DATA_ROOT:?请先设置实验工作根目录}"
cd "${RPENT_DATA_ROOT}/rpent"
source /usr/local/Ascend/ascend-toolkit/set_env.sh
export MUJOCO_GL=osmesa
export PYOPENGL_PLATFORM=osmesa
rpent --robot libero --help
rpent-check-llm --help
```

若命令不存在，说明没有进入本指南核对的容器/安装环境；不要直接升级运行中的环境。当前安装版本：`pydantic-ai-slim 2.48.0`、`openai 3.19.2`、`anthropic 1.8.0`。〔E2〕

### 3.2 配置服务

下面以 **Chat Completions 兼容接口**为例。交互输入避免把 key 写进 shell history；不要启用 `set -x`。

```bash
read -r -p '服务端模型 ID：' RPENT_MODEL_ID
read -r -p 'API base URL（含服务要求的路径前缀）：' RPENT_API_BASE
read -r -s -p 'API key：' OPENAI_API_KEY
printf '\n'
export OPENAI_API_KEY
export RPENT_LLM="openai-chat:${RPENT_MODEL_ID}"
export RPENT_API_BASE
export RPENT_EFFORT=low
```

`RPENT_*` 是本指南的 shell 变量，下一步通过 CLI 传给程序；它们不是 RPent 内置的配置入口。base URL 不应包含 key、签名参数或用户名密码。

其他协议只需替换：

```bash
# Responses 服务：凭据仍是 OPENAI_API_KEY
export RPENT_LLM="openai-responses:${RPENT_MODEL_ID}"

# Anthropic Messages 服务：重新输入它自己的凭据
read -r -s -p 'Anthropic-compatible API key：' ANTHROPIC_API_KEY
printf '\n'
export ANTHROPIC_API_KEY
export RPENT_LLM="anthropic:${RPENT_MODEL_ID}"
```

上面两段是**二选一的替代配置**，不是依次执行。`--base-url` 只适用于 `--planner api`。〔E1：S1、S3〕

`low` 是本指南的接入示例，不是已证明最优设置。CLI 接受 `none / low / medium / high / xhigh`；能否执行仍由模型与 provider 决定。API loop 会把 `none` 转为 `Thinking(effort=False)`，**不能据此保证所有厂商均关闭了隐藏推理**。若服务拒绝推理参数，须检查 provider 映射，不能悄悄丢弃参数后仍记作同档位实验。〔E1：S1、S2〕

## 4. 配置机器人服务与固定记忆

模型接入测试不需要重新部署 π0.5/SAM3，但需要有效的服务地址：

```bash
read -r -p '已分配的 VLA endpoint：' RPENT_VLA_ENDPOINT
read -r -p '已分配的 SAM3 endpoint：' RPENT_SAM_ENDPOINT
read -r -p '本批冻结的 LIBERO memory 目录：' RPENT_MEMORY_DIR
export RPENT_VLA_ENDPOINT RPENT_SAM_ENDPOINT RPENT_MEMORY_DIR

test -d "$RPENT_MEMORY_DIR" || { echo 'memory 目录不存在'; exit 1; }
```

endpoint 使用当前服务实际的协议、容器可访问地址和端口。不要连接另一集正在使用的 VLA；不要为了换 LLM 重启或停止他人的服务。现有环境的连接和服务启动方式见工作区私有 `rpent-repo/AGENTS.md` 与 `节点执行脚本目录`；其中旧设备分配不能当作当前空闲资源表。

如果服务尚未部署，先在已分配资源上部署冻结版本的 π0.5/SAM3，再继续。下面的命令显式传入 endpoints，不会替你部署这两个服务。省略 `--env-endpoint`，让每个 RPent 进程创建自己的仿真。〔E1：S5〕

记忆使用 `--memory-profile local --memory-dir ...` 指向已冻结语料，所有模型使用同一份。它必须有有效的 `MEMORY.md` 或 `global / suite / task_only` 内容；不要使用空目录冒充原实验记忆，也不要临时换成另一套 HF memory。当前 evaluation 模式的 MemoryManager 是只读访问；仍需用哈希核对语料。〔E1：S5〕

## 5. 先检查 API 连通性

```bash
rpent-check-llm \
  --planner api \
  --model "$RPENT_LLM" \
  --base-url "$RPENT_API_BASE" \
  --timeout-s 60
```

只有检查通过才进入下一步。**这个检查只有文本、没有工具，不验证图片、tool calling 或配置的推理档位。** 能回答一句话，不等于能控制 RPent。〔E1：S4〕

常见情况：

| 现象 | 下一步 |
|---|---|
| 401 / 403 | 核对 key 权限与服务地址是否对应 |
| 404 或协议字段报错 | 核对 Responses / Chat / Anthropic 路由及 URL 前缀 |
| 400 | 看服务端错误详情：模型名、推理参数、输出预算、图片字段都可能导致它；不要只盯模型名 |
| 429 / 额度不足 | 停止新集，等待或由用户处理额度；不要无限重试 |
| 文本能通，episode 在图片或工具阶段报错 | 这是接口能力不兼容，按第 8 节排查 |

## 6. 启动第一集：双罐入篮 t0 / seed0

第一集作为**接入 smoke test**，与正式结果分开保存。示例预算为 100 轮、8192 输出 token、3600 秒 planner 上限、10000 环境步；这些不是“自动继承旧深测协议”。正式比较前需要固定并记录预算。〔E1：参数存在；E3：示例预算〕

```bash
mkdir -p "${RPENT_DATA_ROOT}/llm-adapter-runs"
RPENT_RUN_DIR=$(mktemp -d "${RPENT_DATA_ROOT}/llm-adapter-runs/smoke.XXXXXXXX")
export RPENT_RUN_DIR

rpent \
  --robot libero --libero-type pro \
  --planner api \
  --model "$RPENT_LLM" --base-url "$RPENT_API_BASE" \
  --reasoning-effort "$RPENT_EFFORT" \
  --suite libero_10_swap --task 0 --seed 0 \
  --max-turns 100 --max-tokens 8192 \
  --planner-timeout-s 3600 --max-episode-steps 10000 \
  --memory-profile local --memory-dir "$RPENT_MEMORY_DIR" \
  --no-auto-merge-memory \
  --vla-endpoint "$RPENT_VLA_ENDPOINT" \
  --sam3-endpoint "$RPENT_SAM_ENDPOINT" \
  --output-dir "$RPENT_RUN_DIR"
RPENT_EXIT_CODE=$?
printf 'process_exit_code=%s\n' "$RPENT_EXIT_CODE" > "$RPENT_RUN_DIR/process-status.txt"
printf '本集输出：%s\n' "$RPENT_RUN_DIR"
```

不要加 `--explore`、`--interactive` 或 `--dashboard`。这些会引入不同的记忆、人工交互或会话生命周期。新模型应正常走相同任务提示与工具，不能在测试过程中人工教它解题。

检查本集输出：

```bash
find "$RPENT_RUN_DIR" -maxdepth 3 -type f \
  \( -name 'transcript_*.json' -o -name 'run.log' -o -name '*.mp4' \)
```

接入通过需要确认：模型确实调用了工具、图像能够送入、参数能解析、工具结果能送回并继续下一轮、正常 finish 或正常任务失败能够留痕。模型只输出“我会抓取”而不调用工具，不算通过。

**进程退出码 0 不等于任务成功。** 当前 CLI 在没有 planner error 时可能正常退出，即使任务没有完成。检查环境成功谓词/`terminated`、工具返回、finish、轨迹与录像是否一致；不能只信模型文字里的“成功”。transcript 原生记录 `model / elapsed_s / finish / stats / messages`，不应假定必然有独立的 `environment_success` 字段。〔E1：S3、S6〕

每次必须使用新输出目录：当前 transcript 以追加模式写入，同目录重跑可能把多个 JSON 对象接在一起。基础设施失败保留原目录并另开 attempt；普通任务失败保留为任务失败，不为了提高成功率自动重跑。〔E1/E3〕

## 7. 扩展到两场景正式对照

先在同一 API planner 上跑基线模型，再跑候选模型。每模型：

| suite | task | seed | 场景 |
|---|---:|---|---|
| `libero_10_swap` | 0 | 0、1 | 双罐入篮 |
| `libero_10_swap` | 9 | 0、1 | 杯子入微波炉并关门 |

每模型 4 集，两个模型共 8 集。这个规模用于接入和初步比较，不足以支持广泛排名；要做稳定结论需增加重复与任务覆盖。〔E3〕

重复第 6 节命令，修改 `--task / --seed` 并创建新目录即可。**正式计时前还必须完成下列工作，不能直接把共享服务 smoke 当作严谨对照：**

1. 冻结当前代码、补丁、任务资产、π/SAM 权重、记忆、提示和工具 schema；记录哈希。现节点代码有本地修改，只有 git commit 号不足以复现。
2. 每集新建 planner 会话和仿真，重启该集专用 VLA，固定 VLA RNG seed 为 `20260929`；环境 `--seed` 与 VLA RNG 是两件事。当前普通 CLI **没有 VLA seed 参数**，需要由专用启动器设置 Python / NumPy / Torch / NPU seed。已有深测 `timed_vla.py` 可作为维护者移植参考，但依赖其 `timing_hooks` 与运行环境，不能直接当作通用启动器拷贝运行。〔E1/E2〕
3. 固定同一组预算与记忆配置；每集开始/结束验证资产哈希。明确 SAM 的服务复用策略并对各模型保持一致。
4. 先串行跑，不直接沿用旧 `batch_scheduler.py`：它绑定原批次状态、模型及额度检查。若扩成新调度器，必须使用新 batch/state、独立 attempt、provider 对应的额度与错误处理。
5. 同时记录实际返回模型标识、请求的推理设置及有效配置；网关别名可能改变后端，不能仅以命令行 model 作为实际模型证据。
6. 对比成功率、成功集耗时、全部 attempt 成本、逻辑请求数、传输重试、工具数、π块数和环境步数。不同 provider 的 usage 缺失与缓存口径单独标注。

**旧 Codex 数据不覆盖、不改判分，也不与新 API 批次混成一个成功率分母。**

## 8. 模型接不进来时，改哪一层？

| 缺什么能力 | 处理位置 | 要验证什么 |
|---|---|---|
| API 协议不匹配 | 先改 provider 前缀与 base URL | 同一模型是否能接收对应请求格式 |
| provider 未被当前依赖支持 | `build_api_model()` / PydanticAI provider | 在独立环境补依赖或 provider，不升级正在跑实验的环境 |
| 厂商思考开关格式不同 | `ApiAgentLoop._build_agent()` / model settings | `Thinking` 是否正确映射；记录实际请求选项，不能静默忽略 |
| 图片格式不兼容 | `_build_tools()` 返回内容 / provider 编码层 | 图片是否真正送达；大小、编码、角色位置是否被接受 |
| tool call ID、参数、结果回传不兼容 | provider 消息转换层 | 调用 ID 对应、JSON schema 参数、错误返回、多轮续接 |
| 完全没有兼容协议 | 实现 `Planner.solve()` 并注册 `build_planner()` | 输入 system/user/tools，执行工具，返回 `PlannerResult` 的 finish/messages/stats/error |

优先改 provider 适配层，不改机器人动作实现、提示任务含义或环境成功谓词。自定义 planner 应从 `toolkit.get_tools_spec()` 获取定义，通过 `toolkit.execute_tool()` 执行，避免另造一套动作语义。〔E1：S1〕

纯文本模型可以用 `--no-images` 做**单独实验组**；它会减少模型观察信息，不能以此作为与多模态基线公平一致的接入方式。只支持文字聊天、不支持可靠工具调用的模型，不能仅替换 model 名就进入本流程。〔E1/E3〕

## 9. 怎样继续做精细耗时测试？

普通 API planner 已记录累计输入/输出 token、cache read/write token、requests、turns_used 和 tool_calls；它**没有自动提供云端 prefill / hidden thinking 秒数**。内部序列化还会移除 transcript 的图片字节，因此 transcript 不是完整出站上下文快照。〔E1：S2、S3〕

如需与深测报告同级别的统计，在新 runner 中接入下列埋点后再做正式计时：

- LLM：每个逻辑请求和传输 attempt 的 ID、开始/结束、首响应事件、返回模型、usage、重试原因。分开 logical request 与 transport retry。
- 工具：调用 ID、起止时间、工具名、成功/失败；重叠区间取并集。
- 动作：原语、π handler、动作块、仿真步及渲染的同机 monotonic span；保留父子关系，不重复相加。
- 输入审计：各消息/图像块的类型、字节数、哈希、有效 token；原始内容放私有目录，公开只留脱敏统计。
- 云端阶段：只有 provider 返回对应阶段遥测时才填 prefill / thinking。否则保持未知，不能把 TTFT 或整个请求时长当作 thinking。

不要直接把旧 Codex OTLP 提取器用于 API planner；它依赖 Codex 的事件结构。深测的本地计时 hooks 可以评估移植，但必须重新验证开销、字段完整性和输出动作一致性。〔E3：适配要求〕
