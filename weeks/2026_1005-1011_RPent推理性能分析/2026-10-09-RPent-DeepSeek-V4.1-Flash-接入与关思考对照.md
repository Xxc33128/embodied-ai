## 2. 接入事实与两个必须处理的适配坑

配置：provider `huawei-cloud`、`api: openai-completions`、`baseURL https://api.modelarts-maas.com/openai/v1`、`apiKeyEnv HUAWEI_CLOUD_API_KEY`（节点上用 `OPENAI_API_KEY`，通过私有环境注入，未进任何仓库）。
CLI 形态：`--planner api --model openai-chat:deepseek-v4.1-flash --reasoning-effort {medium,none}`（api planner 走 `asyncio.run` + `async with agent.iter()`）。

坑 1：**openai 3.19.2 不用 `httpx`，用独立包 `httpx2`**。第一版插桩只包了 `httpx`，结果一条请求都没记到（Part A 通、Part B 零行）。修法是把 `httpx` 与 `httpx2` 都覆盖，并在后续导入时用 meta path finder 兜底。
坑 2：**pydantic-ai 对未知模型 id 会静默丢弃推理档位**。`Thinking(effort=…)` 只是写 `ModelSettings(thinking=…)`，而 `supports_thinking` 默认 `False`，于是 `thinking` 被无声剥掉——wire 上根本不带 `reasoning_effort`，`medium` 与 `none` 会发出**完全相同**的请求。
     这不是可忽略的噪声：若不处理，"关思考对照"这一臂根本不存在，而日志里却记着 `none`，属于典型的"参数被静默丢弃仍记作同档位实验"。
     修法是在 provider 适配层显式声明该模型 id 的推理能力（`supports_thinking=True`、`thinking_always_enabled=False`、`enabled_by_default=True`），并在预飞里**断言 wire 上确实带上了期望档位**（§7 预飞 28 项全过）。

## 6. 耗时口径：能测什么、不能测什么

**能直接测**：整请求墙钟（`send → 响应读完`）、token 计数、返回模型 id、finish_reason、以及本地各组件 span。
**批次内结构性不可测**：本批 api planner 走**非流式**请求，一次请求只有一个观测点——排队、prefill、解码、网络在该次请求里糊成一个数，客户端拆不开。

**A 阶段补测（2026-10-10，只读批次、不动批次）**：把本批自己的出站体快照（真实消息历史、17 个工具 schema、9 张图像）翻成流式重放——9 个体 × 42 次发送（4.02M input token），另做一次字节阶梯。由此 TTFT / TPOT / 上传税从"不可测"变成**实测**：

**两集崩溃的定性：既有悬崖，非 shim 引入**

`t9_s0 medium` 与 `t9_s1 medium` 以 `exit=1` 终止，错误均为 pydantic-ai 抛出的 `UnexpectedModelBehavior: Model token limit (8192) exceeded before any response was generated`，触发条件（`pydantic_ai/_agent_graph.py:2114`）是**响应只有思考、无可见内容无工具调用**且 `finish_reason='length'`，且该分支**不重试**。三点证据把它与 shim 切开：

1. 数据自证：两集最后那一发都是 `completion_tokens=8192`（正好撞顶）、`chunk_count` 3015 / 3073、无可见内容——额度被推理吃光；
2. 冻结批 306 次请求**从未出现 `finish_reason='length'`**（仅 `tool_calls` 304 / `stop` 2），但**最接近的一次是 8184/8192，差 8 个 token**——悬崖在非流式下同样存在，只是没越过去；
3. A/B 显示流式既不提高截断率也不拉长推理长度，即**wire 模式不改变生成**。

结论：`--max-tokens 8192` 对 medium 档推理偏小，是本接入配置的**既有脆弱性**；B2 这批只是抽到了更长的推理（同一身份的工具调用次数在 43–80 之间随机波动，行为方差本就很大）。修复方向是提高 `--max-tokens`（如 16384）。

**口径结论（重要）**：B2 与 10/09 正式批**整集口径不可比**（B2 有 2 集崩溃、且逐集工作量随机波动），但**逐请求时延口径可比且可直接引用**——本批 8 集共 178 个请求全部带真实 TTFT / 思考窗口 / TPOT。

## 9. 遗留

- **`--max-tokens 8192` 偏小**：medium 档在 t9 上会把全部输出额度用于推理，触发 pydantic-ai 的硬失败（不重试），B2 两集由此 `exit=1`；冻结批最接近的一次是 8184/8192。建议提高该值后重跑 t9 medium 两集。
- 服务端 prefill / 隐藏 thinking / 排队时长在本接入方式下**结构性不可测**；若要真值，需要在网关侧开对应阶段遥测，或改用能暴露首 token 与阶段事件的响应形态。
- 本批 8 集只覆盖 Long Swap 两个任务，样本量不足以做任务级结论；关思考对照在 4 对配对上是**混合方向**，只能作为这两个任务上的证据，不能外推为通例。
- `effective-env.txt` 由批次脚本写的初版为空（脚本自身环境不含这些变量），已改为运行时实拍补齐；脚本本体保持冻结未再改动。
