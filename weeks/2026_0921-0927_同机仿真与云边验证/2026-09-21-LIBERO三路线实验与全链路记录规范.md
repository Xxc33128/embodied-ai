## 3. 耗时分段【E3】

1. **准备与冷启动**：进程创建、库导入、模型加载、首次编译／设备初始化、warmup、仿真创建、reset、稳定步、连接建立分别记录；与稳定态分开。
2. **观测**：控制步开始/结束、物理推进、观测获取、渲染、图像旋转/缩放/编码、状态打包。若底层 step 将物理与渲染合并，保留真实整体 span，并标子段尚不可观测，不能凭差值命名为纯物理时间。
3. **π 请求**：预处理、序列化、请求原子落位、服务端发现、读取与反序列化、输入转换、主机至设备、推理、设备至主机、后处理、响应序列化/落位、客户端轮询发现/读取、动作校验。
4. **GPT 链路**：发送准备、桥接写入/读取、服务确认、首次可见文本、首次工具参数增量、完整工具调用就绪、最终输出/usage。单独记录网络失败、限流和重试。无法观测的云端排队/prefill/decode 不强行拆分。
5. **调度与执行**：候选就绪、GPT 修改完成、动作校验完成、动作可执行、首个 env.step、每步结束、chunk 结束、成功检查；其中“动作可执行到首步执行”即调度等待。
6. **记录成本**：图像写盘、视频编码、JSONL/npz 写入、最终汇总分别计时；异步写盘需保存排队、完成和丢帧计数。不得将录像写盘耗时全算作 MuJoCo 时间。

采用层级 span；总耗时按墙钟关键路径计算，不能把重叠 span 或父子 span 直接相加。保留未解释残差。每回合同时给控制步数、仿真秒数和墙钟秒数，避免等待被加速视频隐藏。

进程内计时使用 `monotonic_ns/perf_counter_ns`；跨机器保存 host/clock 标识和 UTC 对齐误差，不能直接相减两台机器的单调时钟。同主机进程也需验证时钟域。NPU 计时必须处理异步执行：端到端完成计时与设备事件/同步计时区分；诊断性同步会改变运行节奏，单独标记。完整 policy.infer 的时间不能命名为纯 NPU kernel 时间。

## 4. Token、TTFT、TPOT 的口径【E3】

### Token

保留服务端原始 usage 以及其累计/增量属性；归一化 input、cached input、output、reasoning token 字段。reasoning 若属于 output 子集，不再加一次。累计事件取对应作用域最终值或做有依据的差分，不把累计值逐条相加。记录每个模型生成段和整回合，包含纠错与失败尝试；缺失为 null 加原因。

π0.5 另记 prompt token 数（仅在 tokenizer/服务端可得时）、图像数量与分辨率、动作 horizon、实际执行步数和采样步数。其连续动作生成不套用 GPT 的自回归输出 Token/TPOT 概念。

### TTFT 与动作就绪

- `t_send`：本次生成请求实际发出。工具循环的后续生成，以本次工具结果发送为候选起点，并明确客户端代理口径。
- `t_first`：传输读取线程收到首个非空输出增量，不能用消费队列的时刻，避免把工具执行期间的积压算进 TTFT。
- 若接口只提供文本 chunk，记录 `time_to_first_text_delta`，作为客户端 TTFT 代理；说明一个 chunk 可能含多个 token。
- 工具参数首个增量、完整工具调用到达分别记录。收到首个解释文本不等于机器人已有可执行动作。
- `time_to_action_ready`：从本次观测/请求基准到完整动作指令解析、校验完成；机器人调度主要看此指标。

### TPOT

当同一生成段的首/末 token 到达时刻与对应输出 token 数 N 都可确认，且 N>1：

`TPOT = (t_last_token - t_first_token) / (N - 1)`。

按 chunk 到达时间推算时标 `TPOT_estimated_client`，写明分块与 token 计数依据。公开文本 token 与含隐藏 reasoning 的总 output token 不匹配时不计算。不得用整回合总时间除 output tokens：里面含仿真、工具、通信与多次生成。仅有回合累计 usage、完整响应或首个完整工具调用时，精确 TTFT/TPOT 记 null；保留可观测的响应时间。N≤1、缺首尾或输出未排空时写明缺失原因。

任务环境终止后要有有界的模型收尾/usage 排空阶段；timeout 时记录 usage 不完整，不能把未收到 usage 当作零 token。保存工具结果回发、模型收尾和取消事件，不把等待最终报告计入最后一条动作的推理时间。

## 5. 视频与回放【E3】

- 动作视频：双视角 20fps（若采用此值须明确它是回放速度），保留 step/仿真时间；此视频可省略等待，但要显著标注。
- 墙钟回放：按事件真实时间保持上一帧，展示“π 推理／GPT 等待／动作执行”等状态；可用带时间戳帧和播放器重建，不要求为长等待重复存几万张图片。
- 每轮保存关键帧与链接：抓取前后、第一次放置、第二目标切换、GPT 接管、失败、终局。全部逐步帧仍保留，不能只留成功片段。
- 中断也输出已有视频或可重建帧索引、日志和失败原因。视频未完成时该回合不能标成“证据包完整”。

## 6. 并发部署与比较【E3】

目标是 **8 张卡 × 1 个独立 π0.5 worker，单 worker batch=1**，运行独立回合/队列；不是用八卡切分同一次推理。每 worker 有独立设备绑定、req/resp、输出目录和随机数状态。Direct 使用 CPU 仿真和云端 GPT，不为它占一张 π 卡。

Student 和 Hybrid 共用这八个 worker 的任务池；同一 worker 内按顺序处理回合。必须记录实际并发 worker 数、活动 GPT 会话数和资源竞争。单张卡能否运行多个副本、本轮不验证，不据内存余量推断吞吐翻倍。

分两类测量：

1. **单路延迟基线**：已预热、固定并发负载，跑代表 case，记录三路线响应与执行时间。
2. **并发产能**：1→2→4→8 的档位检查（八卡合成探测不能代替这些正式闭环档位），比较每小时有效回合数、p50/p95 响应、超时率、主机 CPU/内存、NPU 利用率、磁盘写入。

正式长任务按吞吐收益使用八卡；若 GPT 限流或 CPU 渲染/写盘饱和，独立限制 GPT 会话并发与仿真实例数。八张 NPU 不保证 GPT 八路可用，更不保证整轮耗时降为八分之一。
