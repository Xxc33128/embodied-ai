# GPU＋Isaac 与 MuJoCo＋LIBERO 路线比较

> v1.0 · 2026-09-20  
> 当前主线：GPU＋Isaac 仿真、NPU 策略推理、Mac 接入云端模型。MuJoCo＋LIBERO 保留为候选，最终选择待定。本记录更新了此前计划中“优先转向同机 MuJoCo”的建议。

## 1. 第一阶段先查清瓶颈

当前不宜先认定通信、GPT 或仿真器是主要瓶颈。先在现有主线上记录一次完整任务，把观测生成、传输、模型请求和动作执行的时间对应起来，再决定优化顺序。【E3】

需要回答：任务失败发生在哪一步？主要时间花在模型等待、仿真与渲染，还是执行与推理之间的暂停？增加硬件能否解决，还是应该减少调用、缩短上下文或调整执行方式？【E3】

原计划中的“约 90 分钟”是待核对的历史基线，本轮没有重新验证。客户端可测的等待需要完整保留；拿不到云端内部遥测时，不将其细分为确定的排队、视觉编码或推理耗时。【E3】

## 2. 两条路线的优劣势

这里比较的是两个完整实验方案：A 为当前 GPU＋Isaac 双臂主线，B 为服务器 CPU＋MuJoCo 的 LIBERO 单臂方案。它们同时改变了部署、任务和机器人，不能把最终成绩差异全部归因于仿真器。【E3】

| 比较项 | A：GPU＋Isaac（当前主线） | B：CPU＋MuJoCo／LIBERO（候选） |
|---|---|---|
| 与当前工作的连续性 | 沿用双臂任务，便于延续已有实验 | 需要建立独立的单臂基线，不能直接复用双臂成绩 |
| 部署与通信 | Mac、GPU 仿真机、NPU 推理机之间的链路需要分别测量 | 仿真和推理可放在同一服务器，减少一段跨机传输；仍有渲染、进程交换和云端等待 |
| 场景与控制 | 适合继续研究双臂协同及现有任务 | 现有 LIBERO 配置为单臂；不能据此证明双臂能力 |
| 测试扩展 | 取决于当前场景、资产与任务接口的可用程度 | 可复用任务、初态和原生评分，适合策略回归和扰动测试 |
| 性能风险 | GPU 资源、渲染及跨机传输可能成为瓶颈，具体占比待测 | CPU 软件渲染、内存与进程调度可能限制吞吐，同机也可能增加资源竞争 |
| 结果解释 | 仍须核对代码、场景、权重与评测协议；“用了 Isaac”不等于官方复现 | 小规模结果适合工程验证；与 RoboDojo 的机器人、权重和动作空间不同 |

部署优劣是工程判断【E3】；当前 LIBERO 接口与资产范围有源码、清单支持【E1/E2，见文末】。MuJoCo 本身并不限制单臂，RoboDojo 分支也已有双臂 MuJoCo 移植。因此后续还可考虑“保留双臂任务、只调整仿真部署”的第三种对照，但本阶段不扩展为另一条完整主线。【E1/E3】

### LIBERO 值得保留的原因

现有工程包含 240 个任务—条件条目，适合用统一入口测试 Student-only、Direct 和 Hybrid，并检查位置、物体或环境变化下的表现。相比重新移植一批场景，它更适合作为补充评测工具。【E1/E2】

它的局限也要保留：单臂结果不代表双臂能力；现有动作接口是 7D，策略生成 10 步、执行 5 步，不能直接套用 RoboDojo 的 50/15。已有审计还发现，部分语言扰动没有进入实际模型输入，部分环境条件没有形成预期场景变化。条件数量不等于有效泛化覆盖。【E1/E2】

**暂定安排：继续以 A 查瓶颈，用 B 补充方法验证。** 最终是否调整主线，依据同任务对照、开发成本和评测目标决定，不依据少量不同任务的视频判断。【E3】

## 3. 如何同时衡量准确性与性能

机器人任务中的“准确性”应落实为任务成功、操作质量和失败恢复，而不只是模型回答是否正确。性能也不能只看 tokens/s 或芯片利用率。【E3】

| 指标 | 记录方式 | 用途 |
|---|---|---|
| 任务成功率 | 成功数／计划尝试数，列出失败与未完成原因 | 判断提速是否牺牲任务表现 |
| 完整任务耗时 | 从启动到终态的实际墙钟；成功和失败分别报告 | 避免把提前失败当作运行更快 |
| 有效吞吐 | 成功任务数／所有尝试的总墙钟 | 同时反映速度和完成能力；仅在同任务、同预算下比较 |
| 决策响应时间 | 从采集观测到合法动作可执行；报告 P50、P95 和样本数 | 衡量真正可用于控制的响应，而非仅首 token |
| 等待与观测时效 | 动作队列空闲时间；动作执行时距观测采集的时间 | 检查停顿、旧观测及动作过期 |
| 每成功任务成本 | 全部尝试的 API 与计算成本／成功任务数 | 比较更换模型或部署是否划算；零成功时不计算有限值 |

补充记录碰撞、掉落、动作突变和恢复成功率。VLM 单独记录误报与漏报，尤其是漏掉失败的情况。能耗只有在取得可靠遥测后才比较。【E3】

第一阶段先测串行时间分布；后续若采用异步执行，按实际重叠关系计算关键路径，不把推理和执行时间重复相加。各机器用自己的单调时钟测持续时间，以请求编号关联，不能直接相减不同机器的单调时钟值。【E3】

## 4. 双臂能力能训进 VLA，为什么还需要 GPT？

双臂协调本身不是必须调用 GPT 的理由。如果 VLA 已能稳定完成某类双臂任务，就应先保留 VLA 单独执行的基线。GPT 值得验证的潜在收益是理解临时指令、安排多阶段任务、解释陌生失败并提出恢复方案；这些能力是否在当前场景中带来收益，需要实验验证。【E3】

建议把决策时机分开：

- **需要高层决策时：** 新任务开始且需要分解、目标发生变化、连续执行没有进展、出现已知策略无法处理的异常，或状态判断持续不确定。
- **不必反复决策时：** VLA 在已验证任务范围内正常执行、阶段进度符合预期，且没有异常信号。简单状态变化可由已有判据或本地模型处理。
- **不能等待云端时：** 碰撞风险、限位或紧急停止应交给本地控制和保护机制，不等 GPT 返回。

以上为待测试的调度建议【E3】。正常动作、常见故障和陌生故障应分别比较 VLA-only、固定频率审核及事件触发审核，检查 GPT 到底增加了多少成功案例，又增加了多少等待和错误干预。

## 5. “VLA 高频、LLM 低频”是否可行

这是值得验证的候选结构，但“高频”应区分控制器执行频率、VLA 动作块生成频率和 LLM 决策频率。VLA 一次生成多步动作，并不需要每个控制步重新推理。【E3】

单机器人在线控制更关注 batch 较小条件下的延迟与抖动；LLM 可以低频处理较复杂的任务上下文。不过，低频不意味着 prompt 应尽量长：保留固定任务规则、当前状态与必要历史，分别测试短摘要和完整上下文，并记录缓存是否命中。【E3】

响应能否足够快，应由动作缓冲决定。例如控制频率为 25 Hz 时，15 步只覆盖 0.6 秒；若下一次可执行决策的 P95 超过这个窗口，就不能仅靠这 15 步保证连续执行，需要更早启动推理、继续由 VLA 补动作，或暂停。仿真暂停方案可用于研究，但不能直接证明真实机器人满足实时要求。【E3，条件示例】

π0.5 的“生成 50、执行 15、暂停再观察”首先验证的是滚动重规划。异步版本还要处理新旧动作块的衔接和过期观测。Physical Intelligence 的 RTC 工作专门研究了这类问题，可作为后续参考，不能将其结果直接视为当前实现的性能。【E3；[RTC 官方说明](https://www.pi.website/research/real_time_chunking)】

“jev”在当前材料中没有明确的项目链接，本记录仅采用“小 batch 高频 VLA、低频 LLM”的描述，不将其归因到具体实现。【E3】

## 6. 加入 Qwen3.8-Max 等决策模型对照

Qwen3.8-Max 可作为云端决策候选。官方文档列出了图像输入、工具调用和结构化输出能力，并提供固定快照 `qwen3.8-max-0902`。这些能力支持开展接口适配，但不能证明机器人任务上的效果，也不说明它适合本地 NPU 部署。【E3；[官方模型说明](https://www.alibabacloud.com/help/en/model-studio/qwen3-8-max)】

建议先让 GPT 和 Qwen 在同一组任务、图像、工具接口和决策预算下对照。记录实际模型版本、推理设置、任务成功率、完整决策时延和账单费用。先做少量完整回合，确认接口正确后再扩展。若希望比较更低成本的小模型，另设一组，不能把 Max 的名称直接等同于低成本。【E3】

模型标价低不一定意味着每成功任务更便宜：多次重试、较长输出或成功率下降都可能抵消单价优势。当前仅将 Qwen 列入候选，本轮未发起模型调用。【E3】

## 7. 对芯片、推理引擎和模型架构的要求

| 层面 | 主要挑战 | 第一阶段应测什么 |
|---|---|---|
| 芯片与主机 | 小 batch 的实际延迟、显存与内存带宽、Host–Device 数据交换，以及 CPU 渲染是否供得上观测 | 预热后的推理时间、拷贝与渲染时间、CPU／NPU 占用、资源共享时的尾延迟；不只比较峰值算力 |
| 推理引擎 | 视觉预处理、算子支持与回退、编译／预热、KV cache，以及 VLA 和 VLM 同机调度 | 单独运行与共同运行的差异；冷启动和稳态分开；是否因排队或批处理增加控制等待 |
| 模型架构 | 动作块长度与反馈速度的取舍，多次去噪／迭代的计算开销，以及高层决策是否真正必要 | 50/50 与 50/15、短与长上下文、VLA-only 与事件触发 LLM 的对照；降低精度后还需复验任务表现 |

这些是性能诊断方向，不是已经确认的瓶颈。【E3】第一阶段的产出应是一份瓶颈排序和对应证据。后续选择满足任务成功率与响应时限、且成本较低的方案；在完成测试前，不认定任何组合为最优。
