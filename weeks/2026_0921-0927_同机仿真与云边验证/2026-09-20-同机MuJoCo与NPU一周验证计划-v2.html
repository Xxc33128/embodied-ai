MuJoCo 在宿主 CPU 运行，π0.5 在 NPU 推理，Mac 负责 GPT 接入与管理。单臂建立可复现测试，双臂单独验证兼容性。

1. 这一周究竟解决什么

主问题：能否在同一台 NPU 服务器上完成 MuJoCo 仿真、观测生成与 π0.5 推理，让 Mac 只负责 GPT 接入和实验管理？优先减少一台独立 GPU 仿真节点及其通信、部署和时钟归因负担。成功标准是链路可靠、耗时可解释、评测能重复；不预先承诺更快、9 秒完成或正式 benchmark 成绩。【E3：本计划建议】

本周必须交付：一条 NPU 服务器同机闭环、一份按阶段计时的记录、一组单臂策略对照，以及一份双臂场景的独立可用性结论。只制定计划，不表示实验已经启动。

本周暂不加入：新 VLM 选型、DROID 数据处理、训练、完整 72 格评测、强制 50/15 流式改造。这些会分散同机闭环验证的关键工作。

2. 解开困惑：部署位置与机械臂数量是两个选择

问题本周选择理由与边界
仿真放在哪里？优先 NPU 服务器的宿主 CPU普通 MuJoCo 物理与 OSMesa 软件渲染在 CPU 上；NPU 负责模型推理。不是把物理仿真移植到 NPU 算子。【E1/E3】
先用哪个场景？单臂 LIBERO-PRO 为主线现有工程已有原生环境接入及 case 清单，先用它核验链路。单臂成功不证明双臂成功。【E1/E3】
双臂怎么办？RoboDojo 双 X5 为独立兼容检查原分支已有 MuJoCo 双臂移植和 Linux CPU 软件渲染部署记录。MuJoCo 并不只支持单臂；双臂工作重点是已有环境与 NPU 服务的接口验证。【E1】
什么时候保留 GPU＋Isaac？需要原生 RoboDojo 可比性或当前 CPU 渲染不满足要求时保留为参考或后续回退方案；本周不为了做形式上的 A/B 额外建设一整条 GPU 管线。【E3】

三条候选路线：① 原生 Isaac 双臂：适合原任务运行时对齐；② MuJoCo 双臂：适合保留四瓶入桶任务，仍有移植偏差；③ MuJoCo 单臂 LIBERO-PRO：适合标准任务扩展。本周以③建立测试方法，以②确认双臂可达性；①保留参考。

3. 明确每台机器做什么

NPU 服务器 / CPU：MuJoCo 物理 → 相机渲染 → 观测整理 → 动作执行 → 成功判定与日志。

NPU 服务器 / NPU：π0.5 接收图像、状态和指令 → 生成动作块。仿真与策略可分容器，使用本机共享卷或已有服务接口。

Mac：实验启动与观察、GPT 接入适配。服务器仅在策略需要 GPT 时与 Mac 交换观测和响应，学生策略闭环不应绕行 Mac。

云端：执行 GPT 模型计算。Mac 调 GPT ≠ GPT 在 Mac 本地推理。

目标数据流：服务器 CPU 仿真 ⇄ 同机 NPU 推理；需要 GPT 时才走 服务器 ⇄ Mac 接入层 ⇄ 云端 GPT。当前 route A/B 真实接口仍需联调，以上是目标拓扑，不是已验收状态。【E1/E3】

同机消除的是独立仿真机到推理机的网络传输，不会消除图像编码、文件 I/O、进程排队、Host–Device 拷贝或云端等待。共享服务器也可能出现 CPU／内存争用。【E3】

5. 五天逐项执行：做什么、留下什么、如何停止

日期 / 工作具体操作交付物通过条件 / 未通过怎么办
D1 周一
冻结版本，验证同机学生闭环		① 对账 Mac、公开仓、服务器实际文件 SHA256；登记今早修复。② 核对仿真／策略容器与交换目录，LIBERO 使用自己的权重。③ 单环境运行观测→NPU 推理→动作执行；再跑一个有明确步数上限的完整 episode。④ 测物理、渲染、交换、推理各阶段。run_manifest.json；部署差异表；一条完整 episode 记录；阶段时延表。至少一个 episode 正常到达成功或预算耗尽终态；无接口、错目录、NaN 或日志缺失；失败任务也可以证明链路可用。失败则 D2 继续修链路，不扩大实验。
D2 周二
接通 GPT，冻结小面板		① 确定 Mac GPT 接入层与服务器 episode loop 的真实连接。② Direct、Hybrid 各跑 1 个开发 episode。③ 冻结两个任务×五个 init；登记 fixture 初态差异。④ 固定模型、prompt、horizon、预算与成功判据。真实请求／响应记录；10 个 case 的 panel.json；模型配置指纹；GPT 调用时间线。三方法可执行，GPT 响应能解析为合法工具调用，拒绝／超时可留痕。未通过则只交学生链路与 GPT 阻塞报告，不声称三方法对照完成。
D3 周三
完成单臂核心对照		在同一面板上依次跑 Student-only、GPT Direct、GPT Hybrid：每方法 10 集，共 30 集。Hybrid 沿用现有协议，不同时改事件门控或流式机制。分轮交错运行方法并记录顺序，降低时段偏差。逐 episode 结果、成功数／分母、动作日志、完整视频或可追溯帧、Token 与墙钟。每个计划 case 都有结果或明确 infrastructure failure／未完成原因；禁止丢弃失败重抽。报告探索性差异，不承诺小样本统计显著。
D4 周四
同机瓶颈与双臂兼容检查		① 先在单臂固定条件下测 1 worker；CPU／渲染为瓶颈且资源允许时再测 2 workers，每档 5 集。② 双臂独立环境做 reset、三路图像、状态 14D、推理 50×14、短动作执行的逐项检查；通过后最多跑 1 集开发回合。CPU／渲染／NPU／队列时间表；吞吐记录；双臂逐项检查表及失败日志。并发测试无请求串线、错配或过期动作；双臂结果仅分为接口通过／开发闭环完成／阻塞。双臂最多占半天，阻塞后归档，不拖延单臂交付。
D5 周五
复核与决策		① 复核分母、失败分类、计时覆盖和成功判据。② 用固定 case 复跑 1 集检验复现入口。③ 汇总同机瓶颈、单臂对照及双臂状态。④ 给下一周建议与确切复现命令。HTML 结果报告；代码与配置版本；日志索引；一页继续／优化／回退建议。数据能追溯到部署与配置；未完成项明示。仅在有相同任务、相同协议的另一部署测量时，才给出“减少了多少通信时间”的数值。

预算与范围：核心 30 集；开发联调与性能探针另计，不能混入核心成功率。D2 依据开发回合估算“剩余调用次数×单次墙钟”和 Token 预算。若无法在本周完成，预先将所有方法等比例缩到同一 case 子集并记录新版本；不得依据成绩选择保留样本。本计划不授权启动付费大批实验。【E3】

6. 时间到底怎么量

指标开始 → 结束解释
物理时间读取 simulation time 的增量与墙钟分列；仿真可以快于或慢于实时，28 秒模拟时间不是 28 秒墙钟硬下限。
物理推进墙钟调用 step 前 → step 后若 step 同时渲染，先记合并段，再用内部打点拆开；不能重复相加。
渲染与编码渲染开始 → 图像就绪；编码开始 → 载荷就绪分别记录图像数量、分辨率、字节数、录屏开关。
策略请求端到端客户端提交 → 完整动作返回包括交换、排队和推理；服务端 compute 是其中子段，不能再加一遍。
服务端推理设备同步后的模型开始 → 设备同步后输出就绪若仅计异步提交时间，会低估 NPU 执行；同步打点对性能有影响须注明。
GPT 请求端到端Mac 发送 → 可执行完整结果到达有流式事件再记录 TTFT；首 token 不等于首个可执行动作。无 provider 遥测则不拆云端排队／prefill／隐藏推理。
服务器等待 GPT服务器发出请求 → 合法动作返回包含服务器⇄Mac、Mac 处理和云调用；各机用本地单调时钟计 duration，以 request_id 关联。
整集与阻塞episode 开始 → 终态；控制队列等待区间异步阶段取时间区间并集／关键路径，不能把重叠推理和执行时间直接相加。

最小 trace 字段：run_id、episode_id、request_id、machine、process、stage、start_monotonic、duration_ms、status、bytes；manifest 记录版本、权重哈希、任务、init、频率、动作协议、渲染后端、模型与推理参数。跨机 monotonic 时间戳不能直接相减；需要单向网络时间时才额外校时并报告误差。【E3】

计时验收：对整集关键路径能解释至少 90% 的墙钟，余量单列 unknown。P50/P95 必须带请求数；仅 5–10 集的 episode P95 作为描述值，不当 SLA。成本按每次尝试及每成功任务分别算；无功耗仪或可靠遥测就不报告能耗结论。

7. 最终如何下结论

观察结果可下的结论下一步
同机链路稳定，学生闭环不经过 Mac低成本同机拓扑可用；部署节点减少扩大标准任务覆盖，逐步加入扰动；不外推双臂成功率。
CPU 渲染占大头、NPU 经常等待瓶颈在观测生产／CPU 资源，而非 NPU 算力先测渲染与录像开销；改变策略输入分辨率或频率属于新配置，需重新验证质量。
GPT 等待占大头去掉独立 GPU 节点仍无法解决主要墙钟问题下一阶段单独研究调用频率、上下文和异步控制；不同时改多个因素。
双臂 MuJoCo 接口通过双臂也能采用 CPU 仿真＋NPU 推理部署单独安排双臂正式回归与物理／评分对齐。
需要原生 RoboDojo 成绩或移植偏差过大当前 MuJoCo 结果不足以支撑原生 benchmark 结论保留／恢复 Isaac 参考路线；两种环境分别报告。

8. 相对原计划，具体改了什么

  • 将“GPU 仿真默认前提”改为“宿主 CPU 同机仿真优先验证”。
  • 将单臂主线与双臂兼容检查分开，避免同时换部署、任务与模型后无法归因。
  • 取消“90 分钟→9 秒”验收承诺；先确认可测量的瓶颈，再提出优化目标。
  • 不再要求从客户端精确推算云端内部阶段，无法获取的指标明确记为 unavailable。
  • 不把 50/15、25 Hz、700 步作为两场景通用参数。
  • 将 VLM 选型、数据集扩展和完整泛化矩阵移到下一阶段，保留本周可完成的小面板。
