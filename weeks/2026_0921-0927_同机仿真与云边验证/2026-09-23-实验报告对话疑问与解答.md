# LIBERO 实验报告：对话疑问与解答

版本：v1.1 · 日期：2026-09-28

这份文档整理本次报告讨论中提出的疑问，以及由这些疑问引出的记录要求。重复问题合并，保留具体例子。它是报告的阅读说明；完整结果、统计表和原始证据仍以文末链接的专题记录为准。

证据标识沿用工作区约定：【E1】表示引用已有源码审计或日志核验结论，【E2】表示配置事实，【E3】表示机制解释或待实验验证的推断。本文的 E1 是对权威记录的引用，不代表此次重新运行了实验。没有确定答案的地方明确列为“尚未确认”。

## 一、实验到底测什么，报告应该写到什么程度？

### 1. 三条路线分别是什么？

【E2】Student 是 π0.5 根据观测和任务产生动作；GPT Direct 是 GPT 根据观测输出末端目标位姿及夹爪状态，再由主机转换为控制动作；Hybrid 是 π 先提出动作，GPT 审核后放行、修改或接管。三条路线都需要根据执行后的新观测继续决策。

因此，比较单位既包括整回合，也包括“观测 → 决策 → 执行 → 新观测”的完整单轮。不能只看模型调用耗时。

### 2. 为什么任务编号旁必须写具体任务要求？

【E2】编号不足以说明目标，尤其 Task 扰动会改变实际要求。报告应同时展示 benchmark、task、条件、init 和实际输入指令。目前新版报告包含：

| 实验 | 实际要求 |
|---|---|
| LIBERO-10 · task 0 · Ori · init 0 | 把字母汤罐和番茄酱罐都放进篮子 |
| Goal · task 0 · Task · init 0 | 打开柜子的底层抽屉 |
| LIBERO-10 · task 9 · Ori · init 0 | 把黄白色杯子放进微波炉，然后关门 |

旧版 LIBERO-10 task 0 的 Task 条件则要求“奶油奶酪和番茄酱放进篮子”，不能与新版 Ori 的字母汤罐目标混淆。底层抽屉任务的历史文件名含 middle，但本次输入指令和成功目标均为 bottom。

### 3. 最早的 18 格和现在的逐轮报告是什么关系？

【E2】最早是两个任务 × Ori/Task/Pos 三条件 × 三路线，均只跑 init 0，共 18 格。之后发现旧协议不能完整拆分每次决策的用量，专门重跑了 LIBERO-10 task 0 / Ori 的三路线，并追加底层抽屉、微波炉两任务。

新版当前为九个有效回合、610 轮决策、3,008 个控制步，其中 428 轮调用 GPT。新旧协议不同，不能把新采集的性能数值直接填回旧回合作为其测量值。

### 4. 为什么不只给整集总时间，而要展开完整的一轮？

【E3】整集总时间回答“完成任务花了多久”，单轮记录回答“这一轮看见什么、为什么这样决定、等待在哪里、执行后发生什么”。两者用途不同。单轮分析还需要汇总所有轮次的均值，避免挑选一轮代表全部。

【E1】现在保留逐轮选择、整轮时间图、执行阶段放大图，以及全回合统计。均值以完成的决策为分母，零步拒绝轮也保留；初始化、模型加载和最终视频编码不混入控制循环均值。

### 5. 现在报告记录哪些内容？

【E1】每轮记录包括：任务与新增输入、双视角图像、机械臂状态、Hybrid 的 π 候选、GPT 原始及格式化 JSON、公开理由与进度评估、输入/缓存/输出/推理 Token、TTFT、TPOT 估算、可见输出分片、分项耗时、实际执行动作、末端/关节及 qpos/qvel 轨迹、执行后观测和视频定位。

公开的 reason/assessment 是模型输出的解释，不能称作完整内部思维过程。服务端没有暴露的排队、网络分段、内部计算细节也不能伪装成实测值。

### 6. 八张卡能不能全部用上？

【E1】已完成八路 π 合成请求探测，32/32 请求成功；旧版正式 18 格运行也使用过八张 π 卡。单 worker 为 batch=1。八卡并发可以提高多个独立回合的吞吐，但不会让同一回合跳过“等待动作结果再决策”的依赖，也不保证整套仿真与 GPT 链路获得八倍加速。CPU 渲染、存储和 GPT 并发仍可能限制速度。详见八卡探测及旧版运行记录。

## 二、模型看到了什么，输出又表示什么？

### 7. 罐子在哪里，要模型自己识别吗？有没有直接给坐标？

【E1】GPT 获得两视角图像、任务、机械臂自身状态及历史；Hybrid 额外获得 π 候选动作。没有直接给模型目标物体的真值位置或原生成功标签。它需要从图像和上下文判断目标身份、空间关系以及下一步操作。

机械臂末端坐标只说明手在哪里，不等于告诉模型罐子在哪里。π 同样根据自己的视觉与状态输入生成动作；学习到的场景规律可能帮助判断，但不能据此断言它知道当前物体的真值位置。

### 8. 为什么 GPT 单独运行会抓错，而另外两条路线没有？

【E3／尚未确认唯一原因】可能涉及物体身份识别、语言目标对齐、图像到空间位置的估计、抓取点选择或动作执行误差。一次抓错不足以断言“GPT 视觉辨识度低”，也不能预设 VLA 必然更差。

排查应将同一轮的实际指令、两张输入图、公开理由、目标位姿和实际轨迹并排查看：它口头认定的是哪个物体？目标设到了哪里？机械臂是否跟上目标？这是三个不同问题。旧版 Task 条件尤其需要确认输入是扰动后的新指令。

### 9. 用户贴出的那份 JSON，是 GPT 一次完整输出吗？

【E1】是一次 Hybrid 决策输出。各字段的阅读方式如下：

| 字段 | 含义 |
|---|---|
| request_id | 标识这次请求，供输入输出与轨迹配对 |
| mode=student | 本轮放行 π 候选动作 |
| steps=5 | 计划执行五个控制步，仍受剩余预算和提前终止影响 |
| reason | 对本轮选择的公开理由 |
| edit | 若选择修改模式时使用的修正量；student 模式不执行它 |
| target | 若选择末端接管模式时使用的目标；student 模式不执行它 |
| assessment.task_progress | 已完成、正在尝试和剩余子任务 |
| execution_status/evidence | 对已经发生的执行及证据的描述 |
| expected_next_intent | 当前任务需要的下一步意图 |
| predicted_next_intent | 对 π 候选动作意图的预测 |
| intent_status/evidence | 两种意图是否一致及其公开依据 |

该例的意思是：当前还没有执行动作，夹爪张开，先允许 π 做初始接近。它同时承认具体目标选择尚不明确。不能把这句话解读为已确认会抓到正确罐子，也不能把 JSON 中的 target 当作本轮实际执行目标。

### 10. 输入输出怎样才能看得清楚？

【E1】输入按任务、当前观测、机械臂状态、π 候选分段；输出按决定、理由、子目标、执行证据和实际动作分段。未生效的 edit/target 折叠，完整 JSON 保留缩进版及逐字原文。阅读视图只改善呈现，不改写模型原始内容。

### 11. 末端位置、四元数、8D proprio 分别是什么？

【E1／输入约定】末端位置 XYZ 的单位是米，描述末端在世界坐标系的位置。四元数按 wxyz 排列，描述朝向，不是四个角度；q 与 −q 表示同一旋转。

8D proprio 的排列是：

```text
[x, y, z, rx, ry, rz, finger_left, finger_right]
 └位置3维┘ └轴角向量3维┘ └两根手指关节位置2维┘
```

【E3／读数解释】用户例子中的位置约为 (−4.61 cm, −0.36 cm, 70.20 cm)。轴角向量的方向表示旋转轴，长度表示旋转角，单位弧度；不能把它当作 roll/pitch/yaw。例子接近绕 x 轴旋转 π，但不是严格只绕 x 轴。

两根手指的正负号来自关节坐标约定，不表示“一根开、一根关”。约 +0.0387/−0.0387 m 是两指关节位置，不能在未核对机械几何时直接当作实际夹口宽度。

## 三、动作怎样执行，五步究竟能走多远？

### 12. GPT Direct 输出目标位置后，五步一定到达吗？

【E1】不保证。主机根据本轮起始末端与目标的差值生成最多五步的控制动作，段内不逐步按新误差重新计算。物理动力学、控制器响应、接触和夹爪约束都会造成偏差。

在新版罐子任务 Direct 的 97 轮中，结束位置距本轮目标的中位误差约 1.16 cm；40 轮在 1 cm 内，68 轮在 2 cm 内。位置误差小也不等于姿态正确或抓取成功。数据出处见决策表现分析。

### 13. 能不能估算到底需要几步到目标？

【E3】可以计算理想动作尺度下的粗略步数，但它不是实际到达时间预测。本接口的满幅单步参考尺度约为平移 0.011 m、旋转 0.085 rad，不能直接用“剩余距离 ÷ 固定速度”保证收敛。

例如无接触、控制充分跟随时，3 cm 的单轴位移按满幅尺度约需三步；实际命令可能被均分为五步，执行也可能滞后或越过目标。要得到可信答案，需要逐步反馈控制的到达实验，而不是只按当前五步轨迹做线性外推。

### 14. 指定夹爪关闭后，是到目标位置才夹吗？

【E1】当前 Direct 动作段中，闭合命令从第一步就与移动一起生效；没有隐含的“先到目标再闭合”。因此距离物体还远时就发关闭，可能提前夹起。命令开始生效不等于瞬间完全闭合，也不等于已经抓住物体。

π 的候选可以有逐步夹爪命令，应看实际动作序列。若希望严格先对齐再抓取，需要显式分阶段或增加到位判断。

### 15. 五步是 0.25 秒，真机是不是也只需这么久？

【E1】仿真控制频率为 20 Hz，所以五步推进 0.25 秒仿真时钟。当前一轮不一定执行满五步，提前结束或拒绝会减少实际步数。

【E3】真机只有在相同控制周期、轨迹可跟随等前提下，才能将五个周期解释为约 0.25 秒的命令时间窗。它不保证在此期间到达目标、夹紧物体，更不包括此前等待 GPT 的时间。仿真跑得慢也不能反推真机必然按这个时长完成操作。

## 四、时间统计到底统计了哪一段？

### 16. “保存观测与轨迹”就是机械臂执行时间吗？

【E1】不是。动作由环境 step 推进，保存观测与轨迹是把图像、状态、动作等证据写入文件的开销。二者在当前记录中分别计时。

读报告时应区分三种量：动作仿真时长、环境执行墙钟、整轮决策墙钟。它们回答不同问题。

### 17. 0.25 秒为什么不能直接放进墙钟分项相加？

【E1】0.25 秒来自仿真时钟；墙钟来自真实经过的时间。电脑可能花三秒才算完这 0.25 秒的仿真并生成观测。物理步进已经推进了仿真时钟，再把 0.25 秒加到墙钟上会混用单位含义、重复计算。

因此新版报告将仿真轴独立展示，并按实际步数核验，不统一硬写 0.25 秒。

### 18. “环境执行墙钟”是什么意思？包括 Jupyter 渲染吗？

【E1】它是 env.step 调用实际占用的时间，分为物理步进、图像渲染与像素读回、环境其他处理。这里的渲染是 MuJoCo 虚拟相机生成观测图像，不是 Jupyter 页面展示或浏览器绘制。

```text
环境执行墙钟 = 物理步进 + 渲染与读回 + 环境其他处理
```

保存文件、编码 GPT 输入和 GPT 请求往返另列。

### 19. 各项具体包含什么？

【E1／计时口径】

| 分项 | 测量边界与解释 |
|---|---|
| 物理步进 | sim.step / mj_step 包装范围内的物理推进计算 |
| 图像渲染与像素读回 | sim.render 生成相机像素并取回结果的墙钟 |
| 环境其他处理 | env.step 扣除前两项后的残余；包含该范围内其他逻辑，不能进一步精确归因 |
| 保存观测与轨迹 | 图像、状态、动作等证据的序列化与落盘 |
| 编码 GPT 输入 | 本地准备消息、读取图片、Base64/JSON 等处理，不是服务端视觉编码器耗时 |
| π 推理与同步 | 服务端策略调用及前后设备同步，并非纯芯片 kernel 时间 |
| π 文件交换等 | 客户端请求总耗时减服务端推理与同步；混合排队、文件读写、序列化等 |
| GPT 往返 | 请求发出至响应及用量收齐，含网络、服务等待、计算与输出传输 |
| 主机其他 | 整轮中未分配到上述项目的主机开销 |

最终视频编码不计入逐步保存项。差值类残余只能按其定义解释，不能强行命名为某个单一操作。

### 20. “数据传输时间”是单独精确测量的吗？

【E1】现有记录不能把 GPT 往返精确拆成上传、排队、输入处理、内部推理、解码、下载。π 的客户端与服务端差值也不是纯网络时间。

【E3】若要独立测通信，需要额外的传输边界打点；跨机器绝对时间对齐还需要考虑时钟误差。没有这些证据，报告只能保留复合耗时，不能用一个差值冒充纯通信。

### 21. 分项表是不是按真实时间顺序排列的？

【E1】分项汇总表是按类别归并，某类操作可能在一轮内发生多次，不表示单次连续执行顺序。真实顺序应看按原始起止时间绘制的 SVG 时间图。

完整一轮图用于查看 π、GPT 和执行阶段的先后；执行阶段放大图用于查看物理、渲染和保存的细节。父 span 包含子 span 时会重叠，不能把所有横条长度直接相加。

### 22. 单轮平均耗时能告诉我们什么？

【E1】新版罐子任务平均整轮约为 Direct 14.41 秒、Hybrid 18.82 秒、Student 4.20 秒；其中 GPT 往返约为 10.82 秒和 14.37 秒，渲染读回约 2.7–2.9 秒。完整分项表见逐轮实录，不在本文重复维护。

【E3】它说明这批运行的主要等待集中在 GPT 链路及渲染。它不是隔离的芯片性能测量，也不能把并发实验均值直接视为真机闭环延迟。

## 五、Token、TTFT、TPOT 为什么容易读错？

### 23. 每次决策的 Token 是怎么统计的？

【E1】新版每次决策使用独立 GPT turn，同一 thread 保留历史。从用量通知读取累计值，以本轮结束累计值减上轮结束累计值，获得本轮输入、缓存输入、输出、推理 Token。

缓存输入属于输入的一部分；推理 Token 属于输出的一部分。二者不能再加一遍。输入 Token 也不是页面“本轮新增文本”单独分词的结果，还涉及历史、图像和接口开销。

### 24. 所谓“接口”具体是哪一层？

【E1／采集链路】实验程序经本地桥接连接 Codex app-server，再由其访问模型服务。我们发送 turn/start，并从 thread/tokenUsage/updated 获取 inputTokens、cachedInputTokens、outputTokens、reasoningOutputTokens 等计数。

所以当前直接观测的是 app-server 返回值，并非独立读取了模型后端全部计算过程。

### 25. 推理 Token 为什么会是 0？是不是被保护了？

【E1】本次 0 表示采集到的本轮 reasoningOutputTokens 增量为 0，不是因为我们拿不到推理文本就自动填 0。新版缺少用量会报错，缺失与零不同。

【E3／尚未确认】它可能对应没有额外隐藏推理序列，也可能涉及服务或统计链路的计数行为；现有证据不足以确认这些具体回合的唯一原因。不能断言这是“隐私保护导致数量被清零”，也不能断言这些回合没有任何分析。

作为已记录的现象，罐子任务 Hybrid 的 51 轮均报告 0，Direct 也有部分轮次为 0。这是观测事实，不是内部机制证明。

### 26. 没有推理 Token，模型如何直接输出决策？

【E3／机制解释】神经网络推理计算与 reasoning Token 是不同概念。模型处理图像、指令和状态时会进行数值计算；这些计算本身并不逐项计成 reasoning Token。

假设零值忠实反映了该轮行为，模型仍可根据输入的内部表示，逐个生成可见 JSON Token；每一步生成都会利用输入及已经生成的内容。它可以不先生成额外的隐藏推理序列。

“没有另写草稿”可以帮助理解这种区别，但不能据此认为模型没有计算，也不能把这个类比当作 GPT 内部架构的证据。即使推理 Token 为零，输入处理、可见输出生成和服务等待仍会耗时。

### 27. reasoning Token 与 JSON 里的 reason 有什么区别？

【E3】reasoning Token 是服务计数中的隐藏推理类别；reason、assessment、execution_evidence 是可见 JSON 文本。后者虽然解释了判断过程，仍属于可见输出，不因内容是分析就转为隐藏推理 Token。

官方文档也区分不可直接展示的推理内容与 usage 中的数量。可见解释的完整性、真实性及执行效果仍要用观测和轨迹检验，不能把解释当作内部思维的逐字记录。参见 [OpenAI reasoning 文档](https://developers.openai.com/api/docs/guides/reasoning)。

### 28. TTFT 测的是“模型开始思考”还是“第一段输出到达”？

【E1】当前定义为请求开始至客户端读取线程收到首个非空可见 JSON 分片的时间。它不是首个隐藏推理 Token 的时间，也不是模型实际开始计算的时刻。

首个可见输出之前的网络、排队、输入处理以及可能的隐藏推理都会落在这个区间。因此不能把 TTFT 直接标为纯 prefill 时间。

### 29. TPOT 能估算吗？为什么还要标“估算”？

【E1】能。新版采用：

```text
可见 Token 估计数 = outputTokens − reasoningOutputTokens
TPOT 估算 = (最后可见分片到达时间 − 最早可见分片到达时间)
            ÷ (可见 Token 估计数 − 1)
```

分母需大于零。流式分片不等于一个 Token，计数可能涉及不可见格式开销，接收过程还受缓冲和网络影响，因此它是客户端可见输出的平均估计，不能称为服务端逐 Token 解码实测。

若一次请求出现流重发，等待与废弃输出会让计时、计数范围更复杂，报告应保留相应标记，不与正常轮次无条件混比。

### 30. 输入、输出 Token 与 TTFT、Decode 有什么关系？缓存越来越大会影响 Prefill 吗？

【E1／记录派生，2026-09-28 补充】重新计算当前九回合报告中的三个 Hybrid 回合。输入/缓存取每轮接口计数，Decode 取首末可见分片的客户端到达间隔。各回合分别分析，不将不同任务、路线和运行负载混成一条因果规律。未重新运行模型。

**实际现象：总输入明显增加，但 TTFT 没有按比例增长。** 以罐子任务 Hybrid 为例，取最前12轮和最后12轮（共51轮中的两端，零起编号0–11与39–50），比较均值：

| 指标 | 最前12轮 | 最后12轮 |
|---|---:|---:|
| 总输入 Token | 21,494 | 67,806 |
| 缓存输入 Token | 19,040 | 66,475 |
| 未缓存输入 Token | 2,454 | 1,332 |
| TTFT / s | 4.38 | 4.90 |
| Decode 可见输出 / s | 9.57 | 9.61 |

总输入约增长到3.2倍，但新增历史大部分被计为缓存，未缓存输入均值反而减少。TTFT只小幅变化，Decode基本不变。前期包含缓存建立等潜在影响；此对比支持缓存减轻历史重复处理的解释，不能证明缓存是变化的唯一原因。

**缓存计数究竟代表什么？**

【E3／官方机制说明】Prompt caching复用匹配前缀的KV中间状态，避免重新计算相同旧前缀；新输入仍需处理，本轮输出仍需生成。缓存不是上一轮答案，也不是对文本做压缩。报告的cached input表示本轮命中了多少输入Token，不是服务端缓存显存大小，也不是到本轮为止累计写入了多少Token。[OpenAI官方缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching)

```text
总输入 = 缓存输入 + 未缓存输入
缓存命中比例 = 缓存输入 / 总输入

示意：旧历史60,000 Token命中缓存 + 新观测1,300 Token
      → 复用旧前缀状态，并处理新增输入，不必从头重算全部61,300 Token。
```

缓存命中量不保证逐轮增加；前缀变化或缓存可用性变化可能减少复用。仅看到命中量下降，还不能确定具体原因。

**缓存越来越长，会不会让Prefill变慢？**

【E3／机制解释与边界】可能增加部分成本，但不等于把历史从头重算。命中缓存减少重复计算；更长历史仍可能影响新增Token对历史状态的访问、缓存读取和内存开销。具体程度依赖模型及服务实现，不能用通用KV机制反推出本模型的精确复杂度。

本报告未采集服务端纯Prefill时间。TTFT还包含请求传输、排队、缓存处理、输入计算，以及首个可见输出之前的模型计算和返回等待；这些阶段未独立计时。因此，既不能把TTFT称为Prefill，也不能因TTFT没有增长就断言长上下文没有成本。

**输出Token与Decode的关系更明显。**

【E1／记录派生】按同一回合内全部轮次计算Pearson相关系数，比较可见输出Token估算值（outputTokens−reasoningOutputTokens）与客户端Decode间隔：

| Hybrid任务 | GPT轮数 | 可见输出Token与Decode的相关系数 |
|---|---:|---:|
| 罐子 | 51 | 0.82 |
| 底层抽屉 | 60 | 0.75 |
| 微波炉 | 51 | 0.56 |

【E3／解释】这些正相关表明该批记录中输出更长通常伴随更长的可见生成阶段。相关系数不等于因果效应，也不说明每个Token具有固定耗时；网络缓冲、服务负载及较窄的输出长度范围都会影响它。不能用包含隐藏推理的总输出Token直接解释可见Decode。高度缓存历史，也不会免除本轮约330个可见Token的生成工作。

**优化时应该怎么利用这些信息？**

【E3／待验证方案】降低Decode等待，先试按模式精简执行前必须输出的字段；优化TTFT，同时观察未缓存输入、缓存命中比例、推理计数和完整请求时间。需要控制历史长度时，可对照完整历史与结构化短历史，但不要仅按Token减少量估算收益：重写/压缩前缀可能降低缓存复用。官方建议保持可复用前缀稳定，以追加消息方式延续对话。[官方前缀复用说明](https://developers.openai.com/api/docs/guides/prompt-caching)

现有证据更清楚地支持长输出的耗时关系，尚不能确认长缓存已显著拖慢Prefill。下一步可固定一批观测与输出要求，比较完整历史和短历史的TTFT、缓存命中、完整响应时间与判断质量；这只是建议，尚未执行。

[本节完整精度统计与源数据SHA256](evidence/2026-09-28-cache-ttft-decode-analysis.json)。输入来自本地report_data.json；前后段取floor(轮数/4)且长度相等，相关系数使用各回合全部轮次，不跨回合合并。

### 34. 第 0 步停止，是环境或网络故障吗？

【历史讨论／E3】当时的解释是模型选择了停止，不能仅凭零步就认定为基础设施故障。stop 的语义是结束整个回合，不是暂停等待下一次推理。复跑仍零步也没有支持“重试后即可恢复”的判断。

## 七、GPT 有什么价值，下一步怎样验证？

### 37. GPT 哪些地方做得好，为什么仍然慢？

【E1】新版罐子任务中，Direct 完成了任务，能够随新观测调整接近、抓取、搬运和释放；其公开输出与结构化接口也便于追踪。但这只证明该回合表现，不能推出总体成功率。

### 38. 优化应该往哪里努力？

【E3／待实验验证】优先考虑精简不参与执行的固定输出字段、在关键事件触发审核、控制上下文增长，以及改进短程反馈控制；渲染和保存也值得单独优化。详尽采集版与低延迟运行版应分别比较，避免一边删诊断字段，一边把收益全部归给模型。

不要仅靠减少推理 Token 或加长动作段追求速度：前者未必是当前瓶颈，后者可能放大抓错、提前闭合和目标偏差。需要同时比较成功率、动作步数、接管效果和墙钟延迟。

### 39. 为什么后来选抽屉、微波炉，而不继续选碗？

【对话选择／E3】用户观察到 GPT 抓碗时难以选择碗沿抓点，因此希望换成更容易判断语义目标与操作阶段的任务。抽屉可检验是否选错层；微波炉包含抓取、放入和关门的连续要求。

【E1】本次底层抽屉三路线均未成功，π 与 Hybrid 实际打开的是中层；Hybrid 虽有 13 轮末端接管，仍未纠正结果。微波炉的 π 与 Hybrid 成功、Direct 未成功，但 Hybrid 全部 51 轮都是放行，没有执行修正，不能作为 GPT 纠错收益证据。

### 40. 论文成功率与我们跑一次的结果能直接比较吗？

【E3／文献解释】对话曾查询 LIBERO-PRO 的分任务结果，具体基线需核对论文版本、扰动、模型和指令协议。尤其 Task 条件：我们向模型提供与改变后目标一致的新指令，不能直接继承其他指令口径下的低成功率。论文链接留作追溯：[LIBERO-PRO v1](https://arxiv.org/html/2510.03827v1)。本文不重新复述其数值表，避免与本地实测混用。
