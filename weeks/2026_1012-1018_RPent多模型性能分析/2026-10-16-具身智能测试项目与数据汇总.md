## 1 各项目测什么及项目架构

### 1.1 机器人抓放评测

**测什么**：让不同模型观察同一个机械臂场景，独立决定怎样抓起红块、搬到碗口并释放，比较任务完成情况、动作决策过程与成本。环境是 robosuite Panda 仿真，模型使用前方、侧方和腕部三路图像，以及末端位姿、夹爪和关节状态。〔E2〕

**项目架构**：

> 三路图像＋机械臂状态 → 大模型输出目标位姿／夹爪指令 → inspect-robots 工具适配与 OSC_POSE 控制器 → Panda 仿真执行 → 新图像与状态返回模型。〔E1〕

这一项目由大模型直接通过 `move_to` 等工具控制机械臂，没有 π0.5 学生策略。标准预算为每次任务最多20次模型决策、900个控制步。〔E1／E2〕

### 1.2 GPT-as-Policy 三路线对照

**测什么**：在相同任务和初态下，比较纯 VLA、纯 GPT，以及 GPT 审核 VLA 动作三种控制方式。场景来自 MuJoCo／LIBERO，使用外部相机、腕部相机和机器人状态。〔E2〕

**项目架构**：

- **Student，纯 VLA**：图像＋状态＋任务 → π0.5 生成动作块 → 执行前几个动作 → 更新观测。〔E1〕
- **Direct，纯 GPT**：图像＋状态＋任务 → GPT 输出动作决策 → 合法性检查 → 仿真执行。〔E1〕
- **Hybrid，GPT＋VLA**：π0.5 先生成候选动作 → GPT 选择接受、修改或接管 → 合法性检查 → 仿真执行。〔E1〕

GPT 使用 Astra／medium，VLA 使用 π0.5。π0.5 每次输出10×7连续动作值，逐轮实验最多执行前5步，再获取新观测；Hybrid 中出现 GPT 调用，不代表一定发生了动作修改。〔E1／E2〕

### 1.3 RPent 任务规划与技能执行

**测什么**：让大模型把较长的机器人任务拆成工具／技能调用，比较不同大脑、不同任务套件和运行模式的完成情况与耗时。〔E2〕

**项目架构**：

> 任务＋观测＋冻结任务记忆 → LLM planner 选择工具／技能 → SAM3 提供目标定位，π0.5 技能或非π运动原语执行 → LIBERO 仿真返回观测与结果 → planner 决定下一步。〔E1〕

普通模式使用 GLM、Astra 或 Sol 作为大脑。Flash 模式使用冻结记忆回放和 Molmo2-8B，省去在线 LLM 规划；它仍有模型推理和机器人执行计算。〔E1／E2〕

### 1.4 RPent 中的 DeepSeek 性能专项

**测什么**：在 RPent 中换用 DeepSeek 大脑，比较开／关思考，并测清请求等待、可见思考、输出生成、载荷上传和本地执行的耗时。〔E2〕

**项目架构**：

> RPent API planner → DeepSeek API → 工具／技能调用 → π0.5／SAM3／LIBERO → 执行结果进入下一轮上下文。〔E1〕

非流式批次先记录整请求耗时；流式补测通过 transport shim 捕获响应分片，再重组响应交还 planner，以取得 TTFT、可见 thinking 窗口和 TPOT。Astra／Sol 的 Codex 接入批次与此 API planner 不同，分开比较。〔E1／E2〕

## 3 数据类型与统计口径审核

### 3.1 本次发现及修正

1. **请求重放数量已纠正**：`stream-probe.json` 包含9份请求体，各有6、6、6、4、4、4、4、4、4条记录，合计42次，42条均无error。旧报告“9体×42”的表述不能解释为每份请求体发送42次，已按实际JSON记录改正本汇总。〔E2〕
2. **抓放Token按来源区分**：GLM的20条是worker总量；DeepSeek的20条由session数据库聚合；Qwen的20条中13条标记complete、7条partial/empty-after-resume，其中5条总Token为0，不能当作真实零消耗。Astra首批的5个有效policy与管理、中断、复核会话分开，不能把用量表的19行全计入5次任务；有效policy累计7,484,353 Token。〔E1／E2〕
3. **TTFT／TPOT必须筛选来源**：DeepSeek原非流式306条没有可用TTFT／TPOT；流式178条中177条有效。额外代理CSV有479条非空`ttft_s`，但只有355条通过有效流式筛选；同名字段有值不代表首输出计时有效。〔E1／E2〕
4. **部分字段名会误导物理含义**：代理的`upload_s`止于响应头返回，包含请求发送、排队／处理和等响应头；`tpot_ms_p50/p90`是delta字段到达间隔，不是逐Token延迟。它们不能直接作为纯上传带宽或解码速度。〔E1〕
5. **估算与缺失分开**：`streaming-phases.csv` 的`prefill`取TTFT代理，`think_est`／`decode_est`为Token分配估算；独立8集Codex深测的`prefill_s`、`hidden_thinking_s`均为null。null／CSV空值不能当成0，也不能用区间相加闭合证明服务端阶段已被测出。〔E1／E2〕

审核依据为下表及第4节中的实际JSON／CSV、字段定义与采集源码摘录；没有重新读取受保护原始会话或重新判分任务。〔E1／E2〕

## 6 解包、查清单与校验

### 6.1 解包示例

每个包单独解压到一个新子目录，避免根部同名 `_ARCHIVE_MANIFEST.json`／`_SOURCE_PROVENANCE.json` 相互覆盖。示例从外接盘归档根目录执行，将包B展开到 `解包/GPT-as-Policy/`：

```sh
cd '/Volumes/Extreme SSD/huawei实习_测试报告与原始数据_20261016_150247'
mkdir -p '解包/GPT-as-Policy'
tar -xzf '原始数据/本机/GPT-as-Policy_实验批次与代码.tar.gz' -C '解包/GPT-as-Policy'
```

此时九回合首批数据的实际路径为：

```text
/Volumes/Extreme SSD/huawei实习_测试报告与原始数据_20261016_150247/解包/GPT-as-Policy/GPT-as-Policy-repro/data/decision_v2_20260922/episodes/
```

### 6.2 不解包也能定位文件

每个压缩包旁有同名 `.manifest.json`（包内路径、类型、大小、SHA256）、`.ready.json`（整包大小与SHA256）、`.source-provenance.json`（原来源指纹、图像省略与样例记录）。可先查清单再定向解压；压缩包根部也保存内嵌清单。报告文件的指纹见 `报告/reports.manifest.json`。〔E2〕

### 6.3 复核完整性与报告覆盖

从归档根目录运行：

```sh
python3 verify_backup.py
shasum -a 256 -c '校验/SHA256SUMS'
```

第一条需Python 3标准库，默认只读，检查报告和8个数据包的整包／逐文件指纹及内嵌清单；第二条核对交付时列入清单的散文件。解包后新生成的文件不自动加入原交付清单，macOS的 `._*`／`.DS_Store`也不计入实验数据。〔E2〕

本批覆盖核验记录位于 `校验/报告统计数据覆盖核验.json`：包括27个必需数据根、18格与后续3＋5＋1回合、120集选中产物来源指纹、25份代理原件和9个完整重放请求体。逐文件完整性结果见 `校验/完整性校验结果.json`，整批范围与数量见 `校验/完成记录.json`。原来源指纹通过provenance关联统计保留版，不表示处理后文件仍与原文件整文件哈希相同。〔E2〕
