## 1. 研究目标与前一轮讨论记录

### 1.1 本次澄清后的目标

**目标是在模型、必需的观测图像与任务要求、输出质量要求固定的条件下，加快一次 VLM 推理。研究应回答：时间消耗在哪些算子和数据搬运上，现有芯片的哪些执行单元或数据通路限制了速度，后续芯片应如何改进。** 减少调用次数、取消思考、删除必需输入、替换双脑架构，不作为这个问题的主要解法。〔范围确认／E3〕

“输入一定”需要分成两种情况：每次都必须提供图像和任务，不代表每次图像数值相同；任务文字、历史图像等如果确实重复，可以研究保持计算语义的缓存复用。对于新的观测图像，仍需研究如何更快完成原来的计算。〔范围确认与推断／E3〕

当前云端 API 的计时能提供负载线索，但没有给出服务端硬件、算子 trace 或权重结构。无法由这些计时直接判断是昇腾哪个单元慢。本地实验需要选择权重可得的 VLM，明确它是研究代理模型；不能称为已把同一闭源云模型部署到本地。〔推断／E3；目标模型权重与部署条件未核实〕

### 1.2 前一轮关于空间记忆与图像输入的讨论

以下保存为**待验证的系统研究假设**，避免与本次固定工作负载下的芯片研究混淆。各项均为〔推断／E3〕，不是已实现结果。

| 讨论点 | 保留的判断 | 边界 |
|---|---|---|
| 旧空间状态 | 物体被移动后，旧位置应成为带时间的历史记录，而不能继续充当当前状态 | 删除旧图不等于已经维护了世界状态一致性 |
| 稳定结构 | 房间拓扑、桌面几何等可作为长期记忆；当前位置、遮挡和接触状态需更新 | 桌子也可能移动；“稳定”应有有效性检查 |
| 记忆分层 | 可分为稳定几何、当前物体状态、短时轨迹／事件、按需查询的视觉关键帧 | 属于表示与算法设计，不能直接推出芯片应设“空间记忆单元” |
| 图像重复 | 完全重复的输入可探索解码结果或 vision embedding 缓存 | 相似帧、不同视角不等于相同张量；不能直接复用完整模型结果 |
| 局部变化 | 可探索 ROI 或 temporal feature reuse，减少重复计算 | 可能改变模型计算与精度；相机移动、遮挡和全局 attention 依赖需要单独处理 |
| KV cache | 与空间事实记忆不同；普通 causal Transformer 中修改前缀会影响其后的 KV | 固定前缀复用主要节省 prefill；不会自动消除后续 decode 对已有上下文的读取 |

上一轮提出“让记忆更新成本随环境变化量增长”的方向，适合作为算法与系统协同研究；用户本次强调的主线则是**所需推理计算本身的硬件加速**。后文以这个目标为准。〔范围确认／E3〕

## 2. 为什么同样的推理，在高算力芯片上仍可能慢

### 2.1 先把一次推理展开成真实计算

以下是采用 vision encoder＋projector＋自回归语言骨干的 VLM 分解；具体模型可能使用不同视觉接口、GQA、MLA、MoE 或混合 attention，必须以 checkpoint 结构修正，不能套给结构未公开的云端模型。〔推断／E3〕

```text
必需图像 → decode / resize / normalize → vision encoder → projector ─┐
任务与历史文本 ────────────────────────────────────────────────────┤
                                                                   ↓
                                      LLM prefill → KV cache → token decode 循环

vision encoder / prefill：QKV 与 MLP 的 GEMM → attention → Norm / activation
每个 decode token：读取权重 → 小 M 线性层 → 读取 KV → attention / reduction
                  → Norm / MLP → logits / sampling → 下一个 token
```

**单机器人 request batch=1，不意味着所有阶段都是 GEMV。** 同一个请求的多张图像、图像 patch 和 prefill token 可以提供并行计算；到了自回归 decode，每个请求通常只有一个新 token，线性层变成 M=1 或小 M，工作形状发生变化。推理分析与 Flash-Decoding 对这两种阶段作了明确区分。[S1][S1]、[S7][S7]〔文献／E3〕

### 2.2 一个足以解释“加 FLOPS 不一定快”的算式

对线性层 $Y=XW$，设 $X$ 为 $M\times K$、$W$ 为 $K\times N$，每个权重占 $b_W$ bytes，且本次须从 HBM 读取权重。忽略较小的输入／输出流量：

$$
F\simeq 2MKN,\qquad Q_W\simeq b_WKN,\qquad
AI\equiv F/Q_W\simeq 2M/b_W.
$$

BF16、M=1 时约为 **1 FLOP/byte**。假设某设备有效带宽为 1 TB/s，这条流式 GEMV 数据路径仅能供给约 1 TFLOP/s 的有用计算；即使矩阵阵列有数百 TFLOPS 峰值，也可能在等数据。这里的 1 TB/s 是演算假设，**不是 910B／950 规格，也不是本项目测量**。增加 GEMV 利用率与增加供数能力需要一起考虑。[原理来源][S1]〔推断／E3：条件演算〕

模型权重固定，不代表整个模型能留在片上 SRAM；已留在 HBM 的权重仍需被搬到计算单元。有限片上缓存更现实的用途是保留当前 tile、中间激活、query 与局部归约结果，或容纳经测量证明有用的工作集。对固定任务和图片的复用，应另计其到底省掉 encoder、prefill 还是仅省一次上传。〔推断／E3〕

另一个下限来自 KV。对于标准 full-context attention、未压缩 KV、单序列，假设全部 KV 均需从 HBM 读取，且每个元素每步只读取一次。令 $Q_W^{step}$ 为该 token **所有层**必须从 HBM 读取的权重总字节数，与上面的单个线性层 $Q_W$ 区分；不计片上常驻命中或 PIM 覆盖的流量：

$$
Q_{KV}\simeq 2L N_{ctx} H_{KV} d_h b_{KV},\qquad
T_{\mathrm{decode}}\gtrsim (Q_W^{step}+Q_{KV})/B_{\mathrm{HBM,eff}}.
$$

例如**假设** 32 层、8 个 KV heads、head dimension 128、BF16 KV、128 Ki tokens，单次 KV 扫描即为 16 GiB。若本步另须读取 8B dense 参数的 BF16 权重（16 GB），总流量下限约 33.18 GB；在假设的 1 TB/s 下，仅这些读取就需约 33.18 ms。这不是对云端 2–5 ms TPOT 的预测：模型结构、激活参数量、精度、跨卡切分与缓存驻留均可能不同。MLA、sliding-window attention 等也需重写这个模型。〔推断／E3：假设规模演算；没有推定现有模型结构〕

### 2.3 需要分辨的五类限制

下表均为〔推断／E3：候选机制〕，只有 profiler 和对照实验才能确定本项目属于哪一类。

| 限制 | 具体发生了什么 | 为什么多堆矩阵乘单元可能无效 |
|---|---|---|
| HBM 供数不足 | decode 反复读取权重和 KV | 算术单元没有足够数据可算 |
| 算子形状不匹配 | M=1／小 M、head 数较少，tile padding 或并行任务不足 | 峰值测于大 GEMM，不能代表这些形状 |
| 非矩阵流水跟不上 | Softmax 的 max/sum/exp、Norm 的 reduction/rsqrt、激活与重排 | Cube 算完后等待 Vector、归约或中间结果搬运 |
| 片上通路与启动开销 | L0／UB／L1 间转换，跨核同步，中间张量落回 GM，kernel 间空洞 | 总 FLOPs 很少，却多次传输、等待或启动 |
| 必须串行的依赖 | 下一层、下一 token 依赖前面的结果；多卡还可能增加 collective 延迟 | 增加并行峰值不能自动缩短依赖链 |

项目中 50k–230k 上下文 TPOT 上升，是调查 KV 读取与 attention 的线索；TTFT 拟合的约 7 秒截距混合了客户端／网络／服务等开销，**不能命名为芯片启动延迟**。[既有数据与边界](2026-10-13-VLM-VLA双脑架构与推理优化调研.md#03-批次与计时口径)〔实测摘要转引／E3；原始标定锚点待补〕

## 3. 应研究哪些具体单元和数据通路

### 3.1 候选硬件清单：算什么、改什么、何时值得改

**优先验证四条路径：小 M 线性层的供数与映射、长上下文 attention、矩阵与向量运算之间的数据通路、视觉编码流水。** 这是研究排序，不是已经确定的性能排序。下表“候选改进”“成立条件”均为〔推断／E3〕；硬件已有事实见 §4，相关研究见 §5。

| 单元／通路 | 加速的具体计算 | 候选改进 | 必须先看到的证据与代价 |
|---|---|---|---|
| **小 M／GEMV 执行路径** | decode 的 QKV、输出投影、FFN、LM head | 可分割矩阵阵列、适配 M=1 的点积及累加路径、减少 padding、权重分块流入 | 最优 kernel 下仍存在 shape 导致的空闲；若 HBM 已饱和，单加乘法器无效；细分阵列也增加控制和布线 |
| **流式 attention 与分段归约路径** | QK 点积、Softmax、PV 加权；长 KV 分片的结果合并 | KV 分块并行、片上保存 running max/sum/output、流水化 exp 与重标定、低延迟跨核 reduction | attention 是关键路径；split-KV 额外归约不能抵消并行收益；保持全部必需 KV 与标准 attention 数学语义 |
| **Vector／SFU／reduction 增强** | max/sum、exp、reciprocal、rsqrt、LayerNorm/RMSNorm、SiLU/GELU、RoPE | 增强归约树、特殊函数吞吐；矩阵输出直接进入向量流水；融合邻接 elementwise | Vector／归约限制被测出；这些运算已有通用执行能力，重点是比例与数据路径，未必需要固定功能新芯片 |
| **HBM 控制器＋片上 SRAM 层次** | 权重与 KV 的供数、中间激活暂存 | 增加有效带宽、并发访存、合并短请求；按访问模式分 bank；提高 scratchpad 端口／带宽和 tile 容量 | 实际必要流量与无效流量已分开；更大 HBM 容量主要解决驻留，只有减少 offload 等时才直接降时延；SRAM 面积和功耗必须核算 |
| **ND-DMA／地址生成／布局转换** | KV block 索引、patch/window 重排、张量 transpose、视觉 embedding 拼接 | descriptor 驱动多维搬运、间接 gather、预取、双缓冲、低开销事件同步 | 地址处理、小传输或格式转换占关键路径；原生 dense 连续读未必受益于更复杂的 gather 硬件 |
| **视觉前端＋ViT 执行流水** | 图像 decode/resize/CSC/normalize；随后 patch projection、attention、MLP、projector | 前端结果尽量直接供 NPU；ViT 片上 buffer 复用，Softmax/Norm 与 GEMM 流水；适配实际分辨率／patch shape | 图像前处理与神经网络编码分别计时；DVPP／ISP 无法替代 ViT；不得为提速偷偷减少分辨率或视觉 token |
| **设备侧任务派发与依赖管理** | 每层小 kernel、算子间依赖、循环内启动 | 更细粒度 producer–consumer 事件、graph replay／persistent 执行支持、降低 host 往返 | 先排除 Python、框架和编译配置问题；保留多任务公平性，避免占满设备拖慢 VLA |
| **条件选项：低比特供数／近存计算** | 已量化模型的反量化与矩阵乘；HBM bank 内 attention GEMV | 随路 scale/dequant、压缩格式读取；PIM bank MAC 与外围 Softmax／归约 | 低比特需单列精度准入；PIM 需面积、功耗、刷新、时序与数据布局验证；不是现有 dense 模型的默认无损收益 |

这里最值得形成的芯片设计问题是：**用多少矩阵资源、向量／归约资源、片上带宽和 HBM 带宽，才能降低 batch=1 的完整决策延迟？** 这些单元本身通常不是具身独有；具身的约束让资源配比和验收指标不同于大 batch 吞吐业务。只有与同等上下文的文本 agent、通用多模态任务对照后，才能主张某项硬件要求是具身特有。〔推断／E3〕

### 3.2 一个更具体的 attention 数据通路设想

候选设计为：`KV block DMA → 片上 tile buffer → QK 点积 → max/exp/sum → PV 累加 → 分片结果归约`。让 Softmax 的统计量和部分输出留在片上，下一块 KV 的搬运与当前块计算重叠；避免完整 score matrix 往返 HBM。对于 prefill 采用多 query tile；对于 decode 采用少 query、沿 KV 长度切分的映射。这描述的是需要验证的数据通路，不声称必须新增一个独立命名的“attention 芯片”。〔推断／E3〕

FlashAttention 的 IO-aware tiling、Flash-Decoding 的序列维切分、FlashAttention-3 的异步矩阵／搬运／Softmax 流水分别支持这些机制。它们的数学等价不保证浮点逐 bit 一致；还需比较数值误差和工具决策结果。[S6][S6]、[S7][S7]、[S8][S8]〔文献／E3〕

### 3.3 固定图片和任务：缓存究竟能省哪一步

下表的“成立条件／硬件含义”为〔推断／E3〕；已有机制参考 [vLLM 多模态处理][S12]、[Dynamo embedding cache][S13]、[vLLM prefix cache][S14]。〔文献／E3〕

| 可复用结果 | 成立条件 | 省去的计算 | 芯片研究含义 |
|---|---|---|---|
| 图像 processor 输出 | 相同实际图像、相同 resize/crop/grid 与 processor 配置 | 重复 decode／resize／预处理 | 缓存层级、DMA 与命中判定；不自动省 ViT |
| 独立 vision encoder 输出 | encoder 的全部输入、权重／adapter、数值配置一致；该 encoder 不依赖变化的文本或跨图联合状态 | 重复 ViT／部分 projector，具体边界按模型 | 复用存储和低开销读取；不要求发明“识别房间”的硬件单元 |
| LLM prefix KV | 整个前缀及位置、图像身份、模型配置一致 | 命中前缀的 prefill | 稳定 block 索引、驻留与高效读取；decode 仍要访问相关 KV |
| 相邻近似图像的 feature | 仅仅“看起来差不多”不满足精确命中 | 可能省局部计算 | 属近似算法，须另立质量对照；不计入本轮固定计算语义的主结果 |

相同任务文字能复用多少 KV，取决于它在序列中的位置及之前输入是否一致；相同图片出现在不同文本前缀后，也不能直接复用其后的 LLM KV。把输入改排成稳定前缀可能改变位置和模型行为，应另设对照。缓存查找还需覆盖模型／processor 版本并校验身份；具体 key 的构造首先是软件正确性问题，只有查找或搬运成为热点才支持增加硬件。〔推断／E3〕

## 4. 910B／950 已经有什么，真正还缺什么证据

### 4.1 公开架构事实与待测项分开

以下“公开事实”均为〔文献／E3〕。A2 系列的编程架构说明不能充当所有 910B 板卡 SKU 的完整规格表；目标板卡的具体型号、频率、缓冲区容量和版本支持还需实机核对。右栏为〔推断／E3：待测问题〕。

| 对象 | 已核实的公开事实 | 对本研究还不能回答的问题 |
|---|---|---|
| A2／A3 AI Core | 已有 Cube、Vector、Scalar；L0A/L0B/L0C、L1、UB，以及 MTE／FixPipe 等搬运与输出路径。[S2][S2] | 原有算子究竟卡在哪条路径；不能概括为“只有矩阵核、没有向量计算” |
| 950 片上组织 | 相对 A2／A3 的 Memory-based 模型，增加寄存器层、Cube–Vector 数据通路、Warp Scheduler、ND-DMA；支持 SIMD／SIMT 混合编译。[S3][S3] | 本模型 kernel 是否使用了这些路径，持续带宽与同步代价是多少 |
| 950 小矩阵计算 | CANN `Mmad` API 公开 M=1 GEMV 模式及 `disableGemv` 参数，该参数适用于 950PR／DT。[S4][S4] | GEMV 模式的实际收益与剩余利用率；不能把“新增 GEMV”当成 950 已证实缺口，也不能由此断言 A2 完全不能做 GEMV |
| 950 向量与离散访问 | 官方披露增强向量算力、结合 SIMD/SIMT，并把访存粒度从 512 B 缩小到 128 B。[S5][S5] | 不能推广到每一级存储／所有指令；`Mmad` 文档中 L0A/L0B 起始地址仍有 512 B 对齐要求。[S4][S4] |
| 图像前处理 | 官方提供 DVPP／AIPP 的图像处理能力，覆盖相应配置下的解码、缩放、色彩及像素处理。[S15][S15] | 当前模型 processor 的数值路径能否等价映射；这些单元不执行 ViT 的 QKV／MLP |
| 型号规格 | 2025 官方 roadmap 给 950DT 的 HiZQ 2.0 HBM 为 144 GB／4 TB/s，并给出 Q4 2026 时间计划。[S5][S5] | 属官方公布值，不是实机有效性能；本次未核实目标 DT 板卡交付与可用性，亦未核实目标 910B SKU 的完整规格 |

原始 910、910B、910C、950PR、950DT 不能混用数值。主报告 [Q1 规格表](2026-10-13-VLM-VLA双脑架构与推理优化调研.md#13-910950-公开规格对照)保留已有公开来源和未核实项；本节新增的是执行单元与编程架构信息，不用 roadmap 峰值预测 batch=1 时延。〔文献与推断／E3〕

### 4.2 “不足”应该写成可证伪的命题

不能先写“昇腾不适合具身”或“缺少空间专用核”。当前可以提出三类具体命题：①某算子尚未充分使用已有单元；②在最佳实现后，Vector、片上通路或 HBM 的资源配比仍限制关键路径；③新增硬件能在给定面积／功耗预算内优于继续增加 Cube。三者需要不同证据。〔推断／E3〕

| 假说〔推断／E3〕 | 必须收集的证据 | 可反驳它的结果 |
|---|---|---|
| 小 M 映射低效 | 真实形状下不同 GEMV／GEMM 路径的时间、有效 MAC 和字节数 | 最佳已有路径接近必要访存下界，则优先研究供数而非更多 MAC |
| Cube–Vector 交接限制 attention | 依赖时间线、中间 GM 字节、CV 通路和同步成本 | 交接已充分重叠且占比很小，则加宽通路收益有限 |
| Softmax／Norm 吞吐不足 | exp、reduction、rsqrt 相关流水占用与关键路径占比 | 其开销被矩阵／搬运隐藏，则增加 SFU 不会明显缩短整模型 |
| KV 搬运需要更强内存系统 | KV 读取随长度的斜率、有效 HBM 带宽、页访问放大与 bank 冲突 | 权重或 host 间隙占主导，或软件重排已消除大部分损失 |
| 视觉编码需更强片上流水 | ViT／projector 分段时间，重复加载与中间 spill | encoder 占比很低，或主要瓶颈只是 CPU 图片前处理 |

## 5. 文献提供了哪些“具体单元”的证据

### 5.1 保持必需输入的主线依据

下表均为〔文献／E3〕；“可借鉴”是〔推断／E3〕。论文比较基线、shape 与实现年代各异，因此不列一张跨论文“加速倍数排行榜”。

| 工作 | 具体机制 | 证据类型与适用边界 | 对芯片研究的启发 |
|---|---|---|---|
| FlashAttention，2022 [S6][S6] | 分块、online Softmax，使 attention 中间量尽量留在 SRAM | 现有 GPU 上的算法／kernel；保留标准 attention 数学语义，非逐 bit 一致承诺 | scratchpad 与 IO 路径设计同矩阵吞吐一样需要量化 |
| Flash-Decoding，2023 [S7][S7] | 沿 KV 长度并行，合并局部输出及 log-sum-exp | GPU 实测；特定 attention kernel 收益不能当整模型收益 | 低 query 数下，跨块归约和 KV 供数是具体目标 |
| FlashDecoding++，2023/2024 [S9][S9] | B=1 FastGEMV 与小 M flat GEMM 分流；窄 tile、double buffering | 多种 GPU 上实测的软件优化，不是新芯片；统一 Softmax 缩放另有越界重算，不能省略稳定性处理 | 矩阵／向量执行模式应匹配 shape；先检验现有单元再考虑新硅 |
| FlashAttention-3，2024 [S8][S8] | 异步 Tensor Cores、TMA、warp specialization，交叠 matmul 与 Softmax | H100 实测；FP16 与 FP8 分开，FP8 需数值准入 | 有用的硬件是可并行的计算、搬运与同步能力，而非仅乘加峰值 |
| ME-ViT，2024 [S16][S16] | 多用途片上 buffers；Softmax／LayerNorm 纳入处理单元，降低重复访存与停顿 | FPGA ViT 架构及论文评估；不能外推为昇腾或大 VLM 的实测 | 视觉编码器可研究 matrix＋nonlinear＋buffer 的协同组织 |
| Hopper 官方架构 [S18][S18] | TMA 多维异步搬运，不必由计算线程逐项搬运数据 | 已有商业架构文档；收益仍需具体 kernel 流水配合 | 独立搬运引擎和低开销同步有明确硬件先例；昇腾已有 MTE，需比较具体能力 |
| Rubin 官方架构，2026 [S19][S19] | 增强 exponential throughput、TMA descriptor 更新与细粒度依赖执行 | 厂商架构披露，非本项目实测；不采纳其中整机宣传倍率作为预测 | 厂商也在补非矩阵运算与依赖路径，支持研究资源配比 |

例如，Rubin 官方声明相对 Blackwell 基线增加 FP32 及 BF16／FP16 exponential throughput。这支持“Softmax 所需的特殊函数能力值得单独设计”的方向；它并不证明本项目的 Softmax 已经是瓶颈。该文还讨论 activation sparsity，后者涉及改变计算，不能并入本文固定 dense 计算语义的主线。[S19][S19]〔文献与推断／E3〕

### 5.2 真正的新硬件路线：attention Processing-in-Memory

AttAcc 在 HBM bank 侧配置 GEMV，配合层次 accumulator、buffer die 的 FP32 Softmax 与 buffer。其性能来自改造 Ramulator 等建模，计算单元经过 RTL／综合评估，**不是流片芯片上的机器人实测**。[S10][S10]〔文献／E3〕

NeuPIMs 把 attention GEMV 放在 PIM、Softmax 放在 NPU Vector，利用 MEM／PIM 双 row buffer 等机制交叠访问与计算。主要评估包含 batch 64–512 的子批交叠，不能当作单请求 B=1 TPOT 的证明；其架构性能来自周期级模拟。[S11][S11]〔文献／E3〕

对我们可检验的设想是：KV 在存储侧参与点积与累加，减少经外部接口搬运完整 KV 的需求，而不是丢掉历史 KV。它仍消耗 bank 内带宽与能量，FFN／权重流量也仍然存在。应比较相同容量与功耗预算下的普通 NPU、bank GEMV、bank GEMV＋更近的 Softmax／归约，计入 KV 追加、刷新、bank 冲突和中间结果传输。没有这一步，不能提出可靠的 PIM 面积分配或加速承诺。〔推断／E3〕

### 5.3 与此前空间记忆讨论相关、但不纳入主线的边界案例

V-Rex（2025 预印本／HPCA 2026）确实提出 DRE：Hamming-distance 聚类单元、bucket 排序／权重累加单元，以及 KV 管理与预取单元。但它服务于动态选择历史 KV；early exit 指其中的排序过程，并不等于“芯片提前结束模型思考”。其性能使用 cycle-level simulator、DRAMSim3／MQSim，另有 RTL 综合与 pre-layout 时序评估，不能当流片实测。[S17][S17]〔文献／E3〕

它说明：当算法明确产生聚类、筛选和间接读取时，可以设计对应专用单元。但这种方法不与 full dense attention 完全等价，不能借其整体收益证明“同模型完整计算”的硬件加速，也不能把收益全部归于 DRE。它适合作为上一轮记忆／视觉冗余方向的后续分支。〔推断／E3〕

## 6. 如何从 profile 走到芯片设计结论

### 6.1 三层对照，避免把软件问题写成芯片缺陷

以下为〔推断／E3：研究方法〕。

1. **原部署实现**：冻结 checkpoint、所有必需输入、processor、精度、上下文和解码条件，测出每阶段关键路径。
2. **同硬件最佳可用实现**：验证算子融合、tiling、GEMV／GEMM 选择、图执行、数据布局和异步搬运。收益属于实现改进；剩余瓶颈才用于设计新硬件。
3. **硬件反事实**：用经基线校准的延迟模型或模拟器，只改变一项资源，如 HBM 有效带宽、CV 通路、reduction 吞吐、SRAM 容量／端口；再进行等面积或等功耗的组合比较。

一个可交付的结论应该形如：“冻结 workload 后，最佳实现的 X% 关键路径被某通路限制；增强该通路后模拟收益为 Y，代价为 Z，误差和适用范围如下。”不能把“kernel 比未经优化的框架快很多”直接解释为同等幅度的新芯片价值。〔推断／E3〕

若某阶段在关键路径中占比 $f$、该阶段加速 $s$，在其余部分不变、无新增开销的简化条件下：

$$
S_{\mathrm{end}}=\frac{1}{(1-f)+f/s}.
$$

假设 attention 占 30%，即使其加速 2 倍，整体也仅约 1.18 倍；无限加速的上限约 1.43 倍。这里是 Amdahl 演算，不是实测。含重叠的流水应重算依赖时间线，不能把各硬件活跃百分比直接相加。〔推断／E3〕

### 6.2 需要采集的最少指标

**完整工具决策延迟、TTFT、TPOT**与 `processor → H2D → encoder → projector → prefill → decode → sampling` 分段时间并列；对串行依赖的单机器人，吞吐增长不能替代完整决策延迟下降。性能计时与重型 profiler 采样分开，避免采样改变所测时延。〔推断／E3〕

算子层记录真实 shape、dtype、有效 FLOPs、实际内存流量、kernel 启动／等待、跨卡通信，并检查 Cube、Vector、MTE／FixPipe、L2／各片上存储的数据。官方 msOpProf 已提供 ArithmeticUtilization、PipeUtilization、Memory、MemoryL0、L2Cache 等数据说明；不同硬件、工具版本与采样模式可用项需核实，不能承诺所有计数器都能一次获得。[S20][S20]〔文献与推断／E3〕

“有效 HBM 带宽”必须说明是硬件计数得到的实际 bytes/time，还是由模型必要字节估算；后者不能混称真实流量。峰值利用率低也不等于应加算力，可能只是并行度、依赖或带宽限制。〔推断／E3〕

## 7. 下一步最小实验清单

下表均为〔推断／E3：建议实验，尚未执行〕。优先做 H1、H2；H3 只在已定位硬件限制后启动。主报告四个问题的总实验清单继续保留在 [§6](2026-10-13-VLM-VLA双脑架构与推理优化调研.md#6-四个问题的最小实验清单)，本表细化并优先推进 Q1。

| 实验 | 最小工作量与控制 | 输出什么 | 停止／失败判据 |
|---|---|---|---|
| **H1：固定请求的完整计算 profile** | t0/t9 × 2 seeds × 早／晚决策各一次，冻结 **8 个请求**；原实现冷路径、优化实现冷路径、优化实现精确命中热路径，各重复 4 次，得 **96 次定长 token 重放**；另 8 请求×两实现冷路径各一次自由生成，合计 **112 次计时推理** | 找出 processor、ViT、prefill、decode 的实际瓶颈；冷路径与缓存收益分开；自由生成另报真实长度与结果 | 没有固定输入／输出计算量，或重型采样明显扰动计时，则先修测量链；少量重复仅用于筛选，不能稳定报告 p99 |
| **H2：热点算子的形状与数据通路对照** | 从 H1 取 QKV、FFN、attention、Norm 的真实 shape；主测 B=1，另用 B=2/4/8 作形状诊断；上下文选三个模型原生支持长度；每条件先预热再做至少 20 次短重复 | 比较 GEMV／矩阵模式、split-KV／归约、融合／非融合、DMA 重叠；分出已有硬件未用好与资源上限 | 数值超差、完整推理不受益或短上下文明显退化，不能只报最快 microbenchmark |
| **H3：两条硬件反事实** | 仅挑 H2 最重的两类限制；对有效带宽、CV／归约通路等逐项扫 1×/1.5×/2×；若研究 PIM，先复现作者基线再加入 B=1 与本模型布局 | 给端到端收益曲线及面积／功耗约束，比较“加矩阵算力”与“补供数／归约” | 未校准到现有实测，或仅提高吞吐而不降 B=1 决策延迟，则不作芯片立项依据 |
| **H4：闭环回归** | 对入选实现，两实现×两场景×5 个合法独立初态＝**20 集独占**；相同配对再跑 **20 集 VLM–VLA 共置**，合计 **40 集** | 数值变化是否影响工具动作与成功；共置是否产生控制 deadline miss | 任务失败、动作错误或控制超时增多，不能称有效提速；每条件少量初态只用于回归筛选，不证明成功率非劣 |

H1 先采原实现冷路径，再由 H2 得到优化实现并补齐对照；112 次为计时调用，编译预热、热缓存填充与 profiler 专用运行另计。“冷”是**模型权重常驻、编译已预热，但 processor／encoder／prefix cache 清空**。每组交错运行；设备时钟、功耗模式、温度和并行度记录一致。〔推断／E3〕

热路径记录实际命中 token、残余重算 token／blocks、logits 与 sampling 时间。普通 prefix KV 缓存不必然使 prefill 归零，例如 vLLM v0.10.1 为得到 logits 至少重算最后 token，block 对齐还可扩大重算范围；另缓存 hidden／logits 的实现需另列。[官方 KVCacheManager 说明][S21]〔文献与推断／E3〕

固定计算量分两步：算子／TPOT 比较重放同一 token continuation，保证相同数量的 decode steps；完整工具时延另跑自由生成并记录真实输出长度、工具合法性与结果差异。重放 token 的耗时不能冒充自由生成的任务完成时间。精度改变、token pruning 或视觉近似复用均另设组，不与同精度硬件收益混合。〔推断／E3〕

8 个请求应从获准的脱敏导出或同初态重渲染获得，不为本研究遍历受保护的原始会话。目标模型若不支持 50k–230k 上下文，先在原生上限内验证机制，并明确无法验证该长上下文区间；不能通过截断后仍声称覆盖原负载。〔推断／E3〕

**最先动手的是 H1：把一次固定 VLM 请求画成带时长、字节数和等待原因的算子时间线。** 这张图才能决定后续优先增强 GEMV、归约、片上互联还是 HBM；目前没有足够证据将其中任何一个写成已经确认的 910B／950 缺陷。〔推断／E3〕
