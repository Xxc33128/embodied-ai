# 术语、保留配置与复现说明

整理日期：2026-10-22。配置记录对应 2026-10-19 的最终验收，不是今天的在线巡检。

## 1. 术语对照

本节概念解释为 E3；“本次对应”列的具体设置与数字为 E2，来源见 [指标与证据.json](指标与证据.json)。

| 术语 | 怎么理解 | 本次对应 |
|---|---|---|
| BF16 / bfloat16 | 每个数占 16 bit 的浮点格式；保留较大的指数范围，但有效数字较少。存储格式不等于每个内部运算都使用完全相同的累加精度 | 权重及服务 dtype 保持 BF16，没有改成 INT8/INT4 量化 |
| 27B | 大约 270 亿个参数；参数规模决定权重内存的主要部分，不包含全部运行时开销 | 单卡权重分配约 51.08 GiB，MTP draft 加入后相关占用约 54.24 GiB |
| TP / Tensor Parallelism | 把同一个模型的张量计算拆到多张卡，生成时需要协作通信 | TP=2，物理卡 3、7；不是每卡各部署一个完整服务 |
| DP / Data Parallelism | 多份模型副本各处理不同请求；更偏向增加总吞吐，通常不减少单副本权重内存 | 本次没有增加独立 DP 副本 |
| PP / Pipeline Parallelism | 把不同层放到不同卡，按流水线执行 | 本次未启用 |
| Prefill | 读入并处理 prompt，为后续生成准备 attention KV 或线性注意力状态 | 260081-token 冷输入首 token 等待约 109 秒，主要耗在输入处理 |
| Chunked Prefill | 将长输入分多轮处理，平衡吞吐、临时内存及其它请求等待 | 全局每轮 token 预算 16384，单长请求阈值 8192 |
| Decode | 输入处理完成后继续生成输出 | MTP 主要加速这一阶段，不能消除全新长文的 Prefill |
| MTP / Multi-Token Prediction | 先提出多个候选 token，再由目标模型验证；一次可推进的 token 数取决于接受率 | `qwen3_5_mtp` 路径，4 个候选；不是把同一个词复制 4 次 |
| TTFT / Time To First Token | 请求发出到第一个内容 token 的等待，可能包含网络、排队、输入处理等 | 冷 260K 109.46 s；热前缀 2.42 s；二者条件不同 |
| TPOT / ITL | 每个输出 token 的平均时间 / 相邻输出的间隔；实现和统计口径会影响数值 | MTP 的 SSE 可能成组返回，短答案的流式间隔不能直接当稳定单 token 速度 |
| Throughput | 单位时间生成的输出总量，必须说明是单请求还是多请求合计 | 166.90 tokens/s 是四请求合计 |
| KV cache / state cache | 保存此前 token 的注意力键值或线性注意力状态，避免 Decode 每步重算全部历史 | 共享池；最大并发数不等于能同时容纳同样数量的满长输入 |
| Prefix caching | 不同请求具有相同开头时，复用已算出的前缀 | 同文追问约 2.4 s；换新文档仍需首次输入处理 |
| cache_salt | 给缓存键附加隔离标记；不同标记可用于验证冷输入，防止误把缓存收益算成计算加速 | 冷对照使用独立 salt 并检查命中为零 |
| HBM | 卡上的高带宽设备内存；容量与读写带宽是不同指标 | 每卡容量 64 GiB，最终整卡峰值约 59.9 GiB |
| Context window | 一次请求允许的总 token 长度；输入、对话模板、图像表示和输出都要占用 | 262144=256×1024，不是 256000 字，也不是 256K 输入外加无限输出 |
| RoPE / YaRN | 位置编码及一种扩展上下文的方法 | 使用保存配置的原生 RoPE/default，没有做 YaRN 扩展 |
| Graph execution / eager | 复用捕获的执行流程 / 按即时流程执行；捕获形状需适配请求与 MTP | 目标 Decode 保留 FULL_DECODE_ONLY；MTP draft 的 enforce_eager=true 是另一项设置 |
| Warmup / cold / warm | 预热用于稳定启动状态；冷/热还需分别说明编译、媒体处理和前缀是否已缓存 | 图文五次对照先各预热一次；260K 冷/热指前缀是否命中，不是重启机器 |
| mm_encoder_tp_mode=data | 视觉编码器在 TP 服务中的工作模式设置 | 保留 data；单次请求最多一图，未配置视频 |

## 4. 怎样公平复测

以下为基于本次经验的复测要求〔E3〕，不是已执行的新实验：

1. 固定权重 revision、镜像、原始文本/图片、sampling 和输出长度。每次对照只改目标配置；图像预处理改变时单独记录视觉 token 数。
2. 短题先预热，再至少五次统计端到端耗时与 TTFT；同时核对答案。长输出固定 1024 tokens，分别测不同内容类型，不以短答案的成组 SSE 速度替代。
3. 全新长文使用独立 cache_salt 并核对零前缀命中；热缓存单列。更换追问顺序、部分字段和文中值，防止把旧答案复用误判为检索成功。
4. 进行四请求突发、长短混合和四条不同长文三类并发负载，确认实际活动请求数达到 4。记录所有请求的首 token、结束时间和格式问题。
5. 对图片同时检查总数、各颜色数量与用途猜测；对检索分别记录“字段值正确”和“格式遵循”。保留失败结果，不只保留最后成功摘要。
6. HBM 记录 MiB/GiB、采样频率和整卡/增量口径。出现性能或质量退化时使用已保存的回退配置，不改权重、不扩大验收阈值来掩盖差异。
