## 3. 单卡为什么从约 5.8 tokens/s 改善了

〔E2〕最初用户观察到约 5.8 tokens/s。随后冻结样例的 eager 基线测得流式 Decode 估算约 5.53 tokens/s。启用 `FULL_DECODE_ONLY` 后估算约 19.8；加入 MTP3 后短输出估算更高，但 MTP 会成组返回 tokens，不能把这个流式估算当作稳定的逐 token 吞吐。因此以相同输入、相同完整答案的端到端耗时作为主要对照。

| 单卡阶段，五次中位数 | eager 基线 | Decode 图执行 | 图执行 + MTP3，最终复核 |
|---|---:|---:|---:|
| 数学题总耗时 | 3.657 s | 1.176 s | **0.630 s** |
| 图片总耗时 | 4.390 s | 1.387 s | **0.759 s** |
| 数学题 TTFT | 0.408 s | 0.267 s | 0.315 s |
| 图片 TTFT | 0.420 s | 0.275 s | 0.316 s |

〔E2〕文本题答案始终为 `7 × 0.4 - 0.6 = 2.2 米`；图像答案始终为五个椭圆物体、两青绿两橙一绿。预热各一次，正式请求各五次，前缀缓存关闭。最终文本/图片总耗时分别改善 **5.80× / 5.79×**。单卡 BF16 权重分配实测约 51.08 GiB，MTP draft 加入后模型相关占用约 54.24 GiB；64 GiB 卡的剩余空间较紧。

〔E3〕该结果支持“小批量 Decode 的执行与调度开销，以及一次验证能接受的候选 token 数，影响了这组短输出速度”。它不证明已精确分解 CPU、Vector、矩阵计算、HBM 和通信的耗时占比。一次算子级 profile 导出未完整闭环；后续 5 秒系统硬件采样也不能替代算子耗时 trace。BF16 27B 的纯权重粗算约 54 GB（约 50.3 GiB），实际部署还需视觉组件、draft、KV/state cache、激活和运行时开销〔E3〕。

## 4. 原生 256K 与 Prefill 分块

〔E2〕保存的模型配置 `max_position_embeddings=262144`、`rope_type=default`。本次直接使用该总长度，没有启用 YaRN 或 RoPE 扩展。总长度包含输入、模板、图像 tokens 和输出；不能输入满 262144 后再额外生成同等长度。

〔E2〕分块扫参固定 BF16、TP=2、最大活动请求 1、MTP3、前缀缓存关闭；同一文本输入 260081 tokens、输出 82 tokens，各档三次。分块参数对应全局 `max_num_batched_tokens`，不是模型的上下文长度。

| Prefill 全局预算 | TTFT 中位数 | 卡 3 / 7 峰值 HBM（MiB） | 检索 |
|---:|---:|---:|---|
| 2048 | 114.066 s | 60368 / 60355 | 每次 7/7 |
| 4096 | 110.779 s | 60388 / 60374 | 每次 7/7 |
| 8192 | 109.104 s | 60551 / 60534 | 每次 7/7 |
| 16384 | **109.025 s** | 61053 / 61039 | 每次 7/7 |

〔E2/E3〕16384 相对 2048 的中位数约少 5.04 秒；与 8192 仅差 0.080 秒，小于运行波动，不能声称明显快于 8192。最后保留全局预算 16384；四并发阶段再把单条长请求每轮 Prefill 上限设为 8192，给其它请求留出调度机会。

〔E2〕在一条冷长输入基线中，客户端 TTFT 为 108.282 秒，服务端记录 Prefill 107.319 秒、排队约 0.000031 秒；单独 tokenize HTTP 往返约 0.892 秒。口径不同，不做简单相减。该负载的首次等待主要在输入处理，而不是队列或 tokenize。〔E3〕没有缓存时，输入增加通常会增加首 token 等待；实际增长还受注意力结构、分块、队列和硬件利用率影响，不能用固定 tokens/s 线性推算所有长度。

## 5. 前缀缓存、MTP 与通信实验

〔E2〕开启前缀缓存及 `mamba_cache_mode=align` 后，相同长文档的重复查询、倒序查询与会话追问 TTFT 约 2.4 秒；最终热请求命中 258048 tokens。新文档仍需约 109 秒首次 Prefill。中部修改的文档只命中此前部分前缀，TTFT 为 71.809 秒、检索 7/7。缓存复用收益不能写成全新文档处理速度提高 45 倍。

〔E2〕MTP 扫参固定三个输入，各生成 1024 tokens、各重复两次；使用独立 `cache_salt` 并核对冷请求命中为零。下表是首个内容至响应结束的 Decode tokens/s 估算，不含 Prefill。

| MTP 步数 | 中文说明 | 代码 | 约 64K 输入后生成报告 |
|---:|---:|---:|---:|
| 0 | 30.39 | 30.39 | 28.63 |
| 1 | 39.42 | 45.27 | 40.23 |
| 2 | 图像事实验收失败，未保留 | — | — |
| 3 | 48.88 | 79.79 | 56.82 |
| 4 | **51.15** | **91.84** | **61.25** |

〔E2/E3〕MTP4 相对“同样开启前缀缓存的 MTP3”，三负载速度比的几何平均提高约 9.1%。相对本轮更早的“缓存关闭 MTP3”，中文和长文负载速度基本持平、代码约提高 13%；不能把 9.1% 当作所有阶段的整体增益。长输出内容有差异，测的是固定输入与固定输出 token 数，不是逐字同答案性能。

〔E2〕HCCL buffer 的 64/256 MiB 两组冷 TTFT 中位数分别为 108.634/108.513 秒，仅约 0.11% 差异，未达到有意义的改进门槛，保留 64 MiB。

## 6. 四并发如何通过验收

〔E2〕最初把活动请求数升至 2/4，吞吐提高，但原图片的“两青绿、一绿”有时变为“两绿、一青绿”，因此先退回单活动请求。后续分别关闭图执行、MTP、异步调度，以及尝试归一化拆分和内置批次一致性路径，均未使原 192 视觉 tokens 的固定图像回归全部通过；没有把这些候选保留为默认配置。

〔E2/E3〕独立算子探针在隐藏维度 5120 的融合 AddRMSNorm 上观察到批量相关差异；拆分探针稳定，但模型级拆分仍未解决图片问题。因此数值路径有可复现差异，完整模型根因仍未定位，不能把全部问题归因于该算子。完整 AscendC 注意力路径只准备了依赖，没有作为最终实测方案；最终服务不加载实验算子补丁。

〔E2〕最终保持原 JPEG、问题、BF16 和采样参数，调整图像处理预算：`size.shortest_edge=524288`、`size.longest_edge=16777216`。此处配置值是处理器的像素面积预算语义，不是把图片短边设成 524288 个像素。视觉 tokens **192→540**，完整 prompt **221→569**。262144 档计数虽对却猜“药丸”，经人工检查排除；更高预算也出现用途猜测或额外开销，保留经复核的 524288 档。

〔E2〕最终 39/39 次固定回归通过事实检查，随后 80/80 次压力请求通过（50 图片、30 数学题），独立混合四请求复核再次通过。这些是同一图像/数学题的多种重复、交错请求，不是 119 个独立的质量样本。原始逐字匹配仅 12/39，图片“个/颗”以及可见黑色图案的描述差异保留，事实检查没有放过颜色数量变化。

〔E2〕最终四请求突发吞吐为 166.897 tokens/s（基线 61.171），采样确认活动请求峰值达到 4。长短混合的短题 TTFT 由 16.220 降到 4.617 秒，但短题完成总耗时仍约 **13.044 秒**；更早出首 token 不代表同等幅度缩短整个请求。

〔E2〕四条不同的约 63K 文档三轮并发检索，共 **36/36 个字段值正确**，未观察到跨请求串值。其中 **3/12 个答案省略 KEY 标签**，仅按 A/B/C 顺序给出正确值，单独登记为格式缺陷。近上限 260K 主样例仍要求完整标签格式并通过。此结果不代表任意长度和任意内容的通用检索准确率〔E3〕。

## 7. 最后保留的配置和维护要点

〔E2〕保留 BF16、TP2、总上下文 262144、最大活动请求 4、全局 Prefill 16384、单长请求 Prefill 阈值 8192、MTP4、Decode 图执行、异步调度、前缀缓存 align、视觉编码器 data 模式和上述图片预算。显存利用率配置为 0.90，实际整卡峰值约 59.9 GiB。

〔E2〕排查中遇到持久化编译产物不匹配，报 `too many values to unpack (expected 20)`；最后按配置隔离 `VLLM_CACHE_ROOT`，并设置 `VLLM_DISABLE_COMPILE_CACHE=1`。运行时编译与 Decode 图执行仍保留，没有删除共享缓存。容器内逻辑卡号与宿主物理卡号分别处理，避免可见设备设置导致映射错误。

〔E2〕启动/核验辅助脚本和回退参数已保存于实验现场。最后核验了在线 argv 匹配、图文事实及重启入口在健康状态下的无操作行为；**没有完成最终四并发配置的完整重启周期验证，也没有安装系统重启后自动拉起的服务**。复现入口见 [术语与复现.md](术语与复现.md)。

## 8. 边界与后续方向

- 〔E2〕共享 KV 池记录为 694889 tokens，启动估算为 2.65 条满 262144 请求；实际验证四条约 63K，以及一条近 256K。`max_num_seqs=4` 不能解释为四条满 256K 都能同时驻留。
- 〔E2/E3〕图像输入的预处理已经变化；最终质量结论只覆盖固定图片的数量、颜色和不猜用途。尚缺多图、不同分辨率、复杂 OCR 与开放图像集合的独立回归。
- 〔E2〕HBM 采用 1 Hz 整卡采样，包含预分配缓存，短暂峰值可能漏采；不是单个请求的增量内存。
- 〔E3〕下一步先扩大冻结质量集、补检索格式遵循和长输入混合并发，再采集完整算子 profile，依据热点评估算子融合/批次一致性方案。当前没有足够证据指定通信、某个算子或硬件带宽为唯一瓶颈。
- 〔E3〕在维持 BF16 与 256K 的约束下，更多卡的收益需按目标重新实测：TP 增加会降低每卡权重，但引入通信；独立副本更偏向多用户吞吐。不能从本次 TP2 四并发结果推算 TP4 或额外副本的收益。
