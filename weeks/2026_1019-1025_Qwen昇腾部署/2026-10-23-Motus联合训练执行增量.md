## ② 八卡全参可行性验证（10-22）

前提：用户确认 npunew 同机 8×910B3（每卡 64 GiB）全部可用。探针目标为原版约 8B Motus 主策略的**全可达基础参数**。〔设计 E3；运行 E2〕

- 精度与分片：FP32；嵌套 Linear／Embedding FSDP 加外层剩余参数 FSDP，共 799 个模块；仅 CPU 构造，不先把整个模型搬上单卡；Adam 大状态驻 NPU，不启用 CPU offload。
- 数据：clean cache 中真实 TRAIN 的八个 clip，每 rank 一个（双相机 128×128、Wan 帧 128×256、H=8）；同一批次重复两步，仅作工程验收。
- 边界：VAE／T5 走已有缓存不进优化器；不参与两项 SFT 损失的语言输出头与最终 Understanding FFN／输出投影明确排除；严格加载 Stage2 后合并 LoRA，不覆盖已接受的 SFT200 checkpoint，此次更新不计作其续训。

## ③ 未适配框架基线并行评测（10-22 评测、10-23 复核）

- 对象：**未适配框架基线**——原始 Stage2 严格加载（每副本 1978 个张量逐值核对）＋新初始化 LIBERO 接口；Stage2 原生 14 维动作，当前为 7 维动作／9 维状态的新接口，沿用 TRAIN-only normalizer 与初始化 seed 1731；不加载本轮 SFT／RL checkpoint、不创建 optimizer、全部参数冻结（前后哈希一致、八副本初始化哈希相同）。〔配置 E2〕
- 协议：LIBERO-Spatial task 0 的 20 个固定 DEV root；每集最多 200 物理步、确定性 Euler K=10、H=8、FP32；官方 `env.check_success()` 首次成功终止，未成功须跑满 200 步。〔配置 E2〕
- 并行：8 张卡各驻留一个完整模型＋VAE、独立 CPU 仿真，`roots[worker::8]` 固定分配，随机噪声按 root 与 chunk 绑定；推理无需 HCCL／FSDP，副本间不互相等待。〔设计 E3〕

**结果：成功 0/20＝0%，Wilson 95% 区间 0–16.11%。**

- 任务控制共 4000 步（另 8 步运行前诊断单列，不进成功率分母）；基础设施异常 0、未知控制 0、参数更新 0。〔E1/E2〕
- 显存：单卡 reserved 峰值均为 34.8848 GiB／64 GiB（allocated 最大 33.03 GiB）。
- 耗时：有效第三轮约 27 分 23 秒含分配／诊断／加载与汇总；单集用时中位数约 4 分 56 秒。
- 原始记录：20 份逐步日志、500 个采样 chunk、20 份 GIF 完整保留在节点。

执行与修复（三轮）：

1. 首轮临时八卡容器缺少仿真 runtime（CPU 预检在另一容器通过，未覆盖该路径）；无任务控制，不计成功率。
2. 第二轮 CPU 哈希侧车误导入 `motus_rl.contracts.digest`，触发 Torch／NPU 扩展加载（CPU 环境缺 HCCL）；逐步日志证明实际控制数为 0。
3. 第三轮改用生产 worker 同款的 `qualification.digest` 后完成全部 20 集。

收尾与复核：10-22 20:18 恢复原服务；10-23 复核逐个匹配 root／hash、重统计 step-attempt／returned／complete、核对执行动作与汇总轨迹逐值一致、每集 200 次官方失败判定、源码仍为固定提交且工作树干净、录像与采样文件完整；临时容器已停、Qwen 健康检查 HTTP 200。〔E1/E2〕

**结论：** 这是未适配接口（新 7 维动作接口未经训练）在单任务开发集上的起点基线，不是官方 Motus LIBERO 成绩，也不是正式 G2；且经 10-23 方向审计（下节）后，范围进一步收窄为「旧 OpenGL 未翻转、128×128 输入下」的基线。〔测量 E2；定位解释 E3〕

## ④ 观测方向与录像清晰度审计（10-23）

用户指出样例视频模糊且上下倒置。审计区分原始相机、模型输入与展示视频三层，确认两个独立问题：

1. **清晰度**：旧录像来自每路 128×128 的模型观测，拼接转 GIF 后再放大三倍导出；放大与 GIF 调色板均不增加细节，属展示选择不当。〔E1/E2〕
2. **方向**：robosuite `IMAGE_CONVENTION="opengl"` 读入的 RGB 数组按通常展示约定应逐路竖直翻转（不可用改变左右的 180° 旋转代替）；旧展示程序直接交给 PIL 遗漏了此步。〔E1〕

问题不止于视频，模型输入同样未翻转（源码 pin `f8fab09058cf1ad63a65cd11c03ac7512e21d8e4`）：`motus_rl/env_adapter.py:13` 观测不翻转；`formal_rollout.py:157` 观测直接转 PIL 送 Qwen；`trajectory.py` 拼接像素不翻转；`formal_sft_tensors.py:29`、`formal_sft_runtime.py:138` SFT 图像直接复制／送 processor 与 VAE；`dataset.py:187` 视频像素拼接不翻转。〔E1〕

对旧结果的影响：

- 0/20、4000 步、零更新仍是实际记录，但**范围收窄为旧 OpenGL 未翻转、128×128 输入下的基线**；正向图像输入下的基线尚未测量。〔E1/E2〕
- 训练与评测沿用同一旧方向的一致性不能证明其适合预训练视觉模型；但尚无对照可证明 0/20 由方向导致——新动作接口未训练同样是重要条件。原 SFT200 与八卡工程证据保留。〔解释 E3〕

展示修复与重放验证（不改旧基线输入）：

- 在既有 CPU 仿真容器内从相同 DEV root 恢复同一初态、执行原基线保存的动作；每路相机**原生渲染 512×512** 后逐路翻正，输出 1024×544、20fps MP4；无超分辨率／生成补帧，不占用 NPU、不暂停服务。〔设计 E3〕
- dev-0000／0007／0016 三集各 200 步完整重放通过：603 个机器人状态向量与 1206 张原始 128 图像逐值／逐像素匹配，官方成功判定均与原轨迹一致；额外 CPU 重放共 600 步，独立记账，不计作新的模型成功率样本。〔E2〕
- 展示修复不等于输入修复：新输入协议须定义新 preprocessing 版本、统一 VLM／Wan／SFT 与采样、生成匹配缓存并重新验收；旧资格不得沿用，本次未修改生产输入代码。〔边界 E2/E3〕
