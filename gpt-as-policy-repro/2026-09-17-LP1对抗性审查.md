## ③ P1/P2/P3 发现

### P1-1 lock 引用的 crc32c 结果文件（114 字节）极不可能是完整校验结果，且写盘后从未被任何人读过——12.4GB 权重内容校验实际仍未闭合

**证据：**
1. 结果文件实测：`/data_nv0/gpt-as-policy-repro/data/pi05_libero_crc32c_verify.json` **大小 114 字节、mtime Sep 17 23:32**（本轮 ssh `ls -la` 实测；早于 ssh 中断，此条为直接证据）。
2. 完整结果的应有大小：脚本（原文已恢复，见附录）对 GCS 列出的 16 个对象逐个输出 `{path(约 60–80 字节), size, crc32c_b64, crc32c_ok}`、`indent=1`——16 条目必然 ≥2.5KB；即使 GCS 返回**空清单**，`json.dumps({"files":[],"bad":[],"n":0,"note":…}, indent=1)` 本机复算也恰好 **113 字节**。114 字节只与"空清单/极短报错"两类输出吻合，与"完成校验"不兼容。
3. 时间线：任务 23:22:34（+0800）经 `docker exec -d gap-repro bash -c "pip install -q google-crc32c 2>/dev/null; python3 - <<PY > …verify.json 2>&1 …"` 启动；若 GCS 列取或路径缺失会**在数秒内**写盘（mtime 应为 ~23:23）；mtime 23:32 说明进程存活约 10 分钟后才有一次写入——与"pip 在弱网挂起数分钟后 python 才启动、随即失败/或空清单"吻合；若真做了 12.4GB 的纯 Python 表驱动 CRC（~20MB/s），写盘应是 ≥2.5KB 的完整 JSON，而非 114 字节。
4. **无人读过结果**：修复会话的最后一个动作（rollout 15:24:18Z = 23:24:18+0800）是 `sleep 420; ssh … print("n =", d["n"], "bad =", d["bad"])`，rollout 中**该命令没有返回记录**；commit `f6bdf1e`（23:32:31）信息写"running on server"、lock `weight_integrity.status` 写"验证进行中"——都只是"未完成"的诚实标注，但**没有任何一处记录过对该文件的读回确认**；本轮交付给我的任务简报在 2026-09-17 深夜仍称"crc32c 校验仍在跑"，而文件早已停止增长（23:32），即"仍在跑"是一个未经验证的假设。
5. lock 现状（`configs/libero_pro.lock.json:100`）：`"crc32c": "6 个大对象（复合无md5）以 crc32c 对 GCS 元数据校验，结果见 data/pi05_libero_crc32c_verify.json"`——以现在进行时+结果文件指针的形式，把一个**从未验证过内容的结果文件**立为方法与证据。
6. 脚本本身未入库：全仓库（含全部 git 历史）grep `crc32c`，仅上轮审查报告与 lock 两处提及，**无脚本、无方法记录、无 GCS 元数据快照**；脚本原文只能从会话记录恢复（本轮已恢复并验证算法，见 G8/G9），且其 `> json 2>&1` 把 stderr 混写进"结果 JSON"，错误输出会伪装成结果的一部分。

**影响：** 12.4GB 学生权重（LP-A0 数值验收的输入）的身份校验**实际状态未知，最可能是失败/空跑**。lock 的 `weight_integrity` 节会让人得出"crc32c 校验已按方法执行、结果在案"的印象——这正是"会导致错误结论"的形态。若后续 LP-A0 数值出现偏差，第一个该排除的"输入损坏"变量仍然没被排除。上轮 P2-1（"权重复验前 LP-A0 结果只许标记输入身份未验证"）实质未闭合。
